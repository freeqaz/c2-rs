recomputing bytes the other two gate rows have read off `work/capture-cache`
since 2026-08-04. `scripts/mode_cross.sh`'s own header has carried the sentence

per gate run, every gate run.

STRATEGY_REVIEW §4's "lane worth commissioning" — was a fork-server. Measured:
`c2rs` process startup is UNDER 1 ms (same number as /bin/true), so batching
cases into one process is worth under 2 %. The fix removes ONE SPAWN IN SIX and
75 % OF THE COST, because the expensive spawn is cl.exe under wibo mapping
c1xx.dll + c2.dll (3.06 MB of PE) inside one of the six.

RECOMMENDATIONS — the multi-lane case
--------------------------------------
1. Stop specifying --jobs 4 (item A).
2. Do NOT add a global lock or a shared job budget. A --jobs 4 gate uses
   283-382 % of an available 3200 %; four of them is under 40 % of the box. The
   box was never CPU-starved by gates — it was doing 78,000 redundant cl.exe
   compilations of 19,556 distinct sources across four lanes. That is now ~384.
   A lock would serialise lanes that are each 2.75x cheaper.
3. Do not treat load-sensitive test failures as flakiness. The only honest
   mechanisms here are shared mutable paths and shared work dirs; the tree has
   been swept for both and the one instance is fixed.
4. The shared capture cache HELPS between lanes; what it is not is shared,
   because case paths are per-worktree (see NOT TAKEN item 1).

PRICED AND NOT TAKEN — coverage-preserving
-------------------------------------------
1. WORKTREE-INDEPENDENT CASE DIRECTORIES — worth ~19 min per new lane, NOT TAKEN.
   A worktree's FIRST gate pays a cold mode cross (1,261 s of a 1,755 s run at
   --jobs 4) and now a cold sweep fill, because the cache key contains the source
   path and both case dirs live under $repo_root/work/. Pointing them at
   main_repo_root() would warm run 1 — and would put 3-4 concurrent lanes on one
   mutable corpus directory, where the lock's private-cold fallback fires under
   exactly the multi-lane condition that is normal here. It needs the corpus
   regeneration made non-destructive (write-if-differs) first. Board #3265.
   THIS IS THE LARGEST NUMBER IN THE DOCUMENT AND IT IS LEFT ON THE TABLE.
2. The per-process cache context — ~15 % of the warm sweep leg. CaptureCache::new
   runs `wibo --version` and FNV-hashes 3.16 MB of DLLs once per `c2rs diff`,
   i.e. 19,556 times. Memoising it touches the one thing capture_cache's docs are
   most careful about; wants its own lane and a stated invalidation rule.
3. The capture cache has NO EVICTION: ~21.5 M entries behind a 1.37 GB directory
   inode, order 150 GB / 170 M inodes. Not in this seam; interacts with #3249.
4. hatch-red still reads REFUSED HATCH-STALE on every run, both trees (#1389 /
   #3219). Not caused here, not fixed here, duration still unmeasured.
