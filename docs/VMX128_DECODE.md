# VMX128 — the decode specification, and the list of ways stock tooling lies

**Lane `w-vmx`, 2026-08-05.** Specification + harness only. **Nothing here is a
gate**; the sole judge of the port remains the real `c2.dll` under wibo plus a
byte-exact obj compare. Nothing here touches `crates/`. Nothing here is derived
from disassembling `c2.dll`, so **no `docs/whitebox/DISCLOSURE.md` row is
implied** — see §2.3.

Tooling: `tools/vmx/`. Companion measurement: §6 (prevalence) and §7
(recommendation).

---

## 0. The one-paragraph version

VMX128 is AltiVec with 128 vector registers instead of 32. The extra two bits
of each register number had nowhere to go, so they were scavenged from bits a
stock PowerPC decoder reads as **opcode extension**. The consequence is that a
VMX128 word is usually a *legal* stock-PowerPC word too — a different one.
`llvm-mc -triple=powerpc` decodes `18 00 07 10` (`vrlimi128`) as
`lxvp 0, 1808(0)` **and exits 0**. Measured here over 616 register-varied
encodings, LLVM is silently wrong on **177 (28.7 %)** and refuses **439**; it is
never right. On the 113 VMX128 instructions that are actually in the dc3
workload, it is silently wrong on **64** and refuses **49** — **0 correct, and
it warns about only 43 % of the ones it gets wrong.** Everything in this file
that is stated as fact was verified against `cl /FAcs` — Microsoft's own
listing of the bytes it just emitted — by `tools/vmx/vmxcheck.py`:
**6,701 of 6,701 in-scope instructions VERIFIED, 0 MISMATCH, 0 UNRECOGNIZED,
66 of the 77 opcode rows exercised.**

---

## 1. Bit numbering

IBM PowerPC convention throughout: **bit 0 is the most significant bit** of the
32-bit instruction word, bit 31 the least. A field spec `28..30,6..11` is a list
of half-open ranges concatenated **most-significant part first**.

Primary opcode is bits 0..5. VMX128 lives entirely in primary opcodes
**4, 5 and 6**. AltiVec proper also uses primary opcode 4 (and 31 for its
loads/stores). Primary 5 and 6 are unused in base PowerPC of that era, and are
where Power10 later put `lxvp`/`stxvp` — which is the whole problem.

## 2. Where the specification comes from, and what grades it

### 2.1 The table (a hypothesis)

`tools/vmx/vmx128_isa.py` is generated by `tools/vmx/gen_isa_table.py` from
**encounter/powerpc-rs `isa.yaml`**, commit
`4643ee0fd3275e3a89dee709185c37968acca83b`, file sha256
`5c3a3a7f8447b0b812f8012e422b941a8be095233a9634c906263dd95cb5e170`. 77 VMX128
rows plus the 178 non-VMX128 encodings that share primary opcode 4/5/6.

This is the same shape as `crates/c2-obj/src/reloc.rs`, which carries a
hand-ported 23-row `IMAGE_REL_PPC_*` table with `gimli-rs/object` and PE/COFF
rev 6.0 cited in the module header rather than taking a dependency. `tools/` is
outside the std-only workspace, but the *discipline* is the same: transcribe,
cite the exact revision, and never let the table be its own evidence.

`docs/PRIOR_ART.md` §3.3 already carries the ADOPT verdict for powerpc-rs and
notes that **every** public VMX128 table descends from one 2006 file
(Biallas `vmx128.txt`) with three known errata. Two independent community
tables agreeing is therefore *not* two pieces of evidence. Which is why:

### 2.2 The oracle (the evidence)

`cl /FAcs` makes the Microsoft back end narrate the bytes it just emitted:

```
  00000	102320c3	 lvx128       vr1,r3,r4
```

Offset, then the exact big-endian word that will appear in `.text`, then
Microsoft's own mnemonic and operand list for that word. That is the
**listing seam** already used elsewhere in this repo, and it cannot be wrong
about what `c2` emitted, because it *is* `c2` reporting what it emitted.

`tools/vmx/vmxcheck.py` decodes every opcode-4/5/6 word in a `.cod` and
compares mnemonic **and** operand text against the listing. Four verdicts, all
four counted and printed: `VERIFIED`, `MNEMONIC-ONLY`, `MISMATCH`,
`UNRECOGNIZED`. **A run that verifies zero instructions exits non-zero.**

Grading paid for itself three times — see §4.

### 2.3 Provenance: this is not whitebox

Decoding the **Xbox 360 ISA** from public tables and from the compiler's own
published listing output is black-box observation, in the same category as the
obj, the diagnostic text and the `/FAsc` listing that `docs/ROADMAP.md` §9.8
already names as observables. Reading **`c2.dll`'s own logic** would be
whitebox. Nothing in `tools/vmx/` or in this file does the latter, and no
`DISCLOSURE.md` row is claimed or needed.

## 3. The encoding

### 3.1 The split register fields — the actually interesting part

A 7-bit register number, assembled from disjoint pieces. **The pieces are not
in the same place for each operand**, and every one of the high pieces sits
inside what a stock decoder reads as opcode-extension space.

| field | bits (IBM) | as an expression | width |
|---|---|---|---|
| `VDS128` | `28..29` ++ `6..10` | `((w >> 2) & 3) << 5 \| ((w >> 21) & 31)` | 7 |
| `VA128` | `21`, `26`, `11..15` | `((w >> 10) & 1) << 6 \| ((w >> 5) & 1) << 5 \| ((w >> 16) & 31)` | 7 |
| `VB128` | `30..31` ++ `16..20` | `(w & 3) << 5 \| ((w >> 11) & 31)` | 7 |
| `VC128` | `23..25` | `(w >> 6) & 7` | **3** |

`VA128` is the pathological one: its two high bits are **single bits at 21 and
26**, six positions apart, straddling the extended-opcode field. `VC128` is
only three bits — in VMX128 the `vC` operand of `vperm128` can only name
`vr0..vr7`.

`VDS128` is named "DS" because in the VMX128 three-operand forms the
destination is **also a source**; `isa.yaml`'s `args` omits that operand and
Microsoft's listing prints it (`vmaddcfp128 vr126,vr0,vr126,vr125`).

Other fields, unchanged from base PowerPC / AltiVec: `rA` `11..15`, `rB`
`16..20`, `vuimm`/`vsimm` `11..15`, `SHB` `22..25`. VMX128-specific immediates:
`PERM` `23..25`++`11..15`, `D3DType` `11..13`, `VMASK` `14..15`, `Zimm`
`24..25`, and the record bit `Rc128` at bit 25.

**Worked example**, from the workload and verified by the listing:

```
0x138050cf   ->   lvx128 vr124,r0,r10
  primary   bits 0..5   = 000100                 = 4
  VDS128l   bits 6..10  = 11100                  = 28
  VDS128h   bits 28..29 = 11                     = 3      -> vr (3<<5|28) = 124
  rA        bits 11..15 = 00000                  = r0
  rB        bits 16..20 = 01010                  = r10
  opcode    w & 0xfc0007f3                       = 0x100000c3 = lvx128
```

Note what a stock decoder does with `VDS128h`: bits 28..29 are inside its
extended-opcode field, so `vr124` versus `vr1` moves it into a *different table
row*. This is why §5's collision measurement varies the register number — the
answer LLVM gives changes with it.

### 3.2 The three form families, by primary opcode

| primary | rows | what lives there | llvm-mc behaviour (measured, §5) |
|---|---:|---|---|
| **4** (`0x10……`) | 17 | the VMX128 loads and stores, plus `vsldoi128` | **16 of 17 rows** have silently-wrong samples; 53 % of sampled words |
| **5** (`0x14……`) | 25 | the float/logical three-operand ops (`vor128`, `vperm128`, `vmaddcfp128`, the pack family) | **0 of 25** — llvm-mc **refuses every one**. Safe. |
| **6** (`0x18……`) | 35 | compares, converts, splats, merges, rounds, `vrlimi128`, `vpkd3d128`/`vupkd3d128` | **35 of 35** rows have silently-wrong samples, **and every one of them decodes as Power10 `lxvp`/`stxvp`** |

That primary-5 row is the one genuinely reassuring line in this document, and
it is why a lane that happens to probe only `vor128` and `vperm128` will
conclude — wrongly — that llvm-mc is honest about VMX128.

### 3.3 Microsoft's spelling, where it differs

Found by the oracle as `MISMATCH`, four times each, on identical encodings.

| `isa.yaml` | Microsoft's listing | meaning |
|---|---|---|
| `vctsxs128` | **`vcfpsxws128`** | float → signed word |
| `vctuxs128` | **`vcfpuxws128`** | float → unsigned word |
| `vcfsx128` | **`vcsxwfp128`** | signed word → float |
| `vcfux128` | **`vcuxwfp128`** | unsigned word → float |

`cl` also annotates the `D3DType` immediate with the pack format's name; all
eight harvested by probing `D3DType` 0..7:
`0<D3DCOLOR> 1<NORMSHORT2> 2<NORMPACKED32> 3<FLOAT16-2> 4<NORMSHORT4>
5<FLOAT16-4> 6<NORMPACKED64> 7<UNKNOWN>`.

## 4. What grading against the real compiler bought

Three corrections to the community table, none of which a "did the disassembler
error?" check could have produced:

1. **Four mnemonics are spelled differently** (§3.3). Encodings fine, names
   wrong.
2. **`vupkd3d128`'s third operand is the wrong field.** `isa.yaml` says
   `vuimm` (bits 11..15). On `0x1be40ff4` that reads **4**; `cl` prints
   **`1<NORMSHORT2>`**, and 1 is `D3DType` (bits 11..13). Verified across all
   eight `D3DType` values.
3. **`vspltisw128` prints two operands, not three** — the `VB128` field is not
   an operand of that form. `vspltisw128 vr63,3` for `0x1be30774`.

And two facts about the *compiler* that no ISA table contains, both measured by
asking it:

* **Arity comes from `C4392`.** A wrong intrinsic declaration is answered with
  `'XMVECTOR __vmaddfp(XMVECTOR,XMVECTOR)' : incorrect number of arguments for
  intrinsic function, expected '3' arguments`. Every row of
  `genprobe.py:ARITY_OVERRIDE` was read off one of those.
* **The `128` suffix is a register-pressure phenomenon, not a different
  operation.** With two live vectors `cl` emits plain AltiVec `lvsl vr0,r0,r11`
  and `vmaddfp`; it emits `lvsl128` / `vmaddfp128` only when the allocator
  needs a register above `vr31`. A probe with no pressure cannot reach ~20 of
  the 77 rows, and would report their absence as coverage.
* **`__lvx`, `__lvxl`, `__lvlxl`, `__lvrxl` and `__vmaddcfp` are not intrinsic
  names in this compiler** — they compile to calls. That corroborates the
  workload's own `src/xdk/LIBCMT/vectorintrinsics.h`, which says `lvx` and
  `stvx` are the only two needing a hand-written body. `lvx128`, `stvx128` and
  `vmaddcfp128` are reachable only through plain pointer loads/stores and
  through the optimiser — which is exactly where the workload gets them.

### 4.1 Coverage, stated as a fraction and not as a silence

**66 of the 77** VMX128 rows have been emitted by the real `cl.exe` and
verified against its listing. The **11 that have not** are:

`lvlxl128 lvrxl128 lvsl128 lvsr128 lvxl128 stvlxl128 stvrxl128 stvxl128
vmaddfp128 vnmsubfp128 vsel128`

— the LRU (`l`-suffixed) loads/stores, for which this compiler exposes no
intrinsic name, and three three-operand forms whose plain-AltiVec siblings the
compiler preferred even at 40 live vectors. Their table rows are **unverified,
not wrong**, and `vmxcheck.py` reports the fraction on every run so this cannot
decay into an assumed 77/77.

## 5. The collision table — the list of ways this tooling lies

Two halves, deliberately separate because they answer different questions.

### 5.1 EXACT — computed, no sampling

Two `(mask, pattern)` rows admit a common word iff
`(patA ^ patB) & maskA & maskB == 0`. Decidable, so this is computed over all
77 × 178 pairs rather than estimated.

**Result: VMX128 and AltiVec proper are DISJOINT — zero colliding pairs.** The
only exact collision inside `isa.yaml` is `vsldoi128` (`0x10000010` /
`0xfc000010`, a mask only seven bits wide) against **17 Gekko/Broadway
PairedSingles rows**, which do not exist on Xenon.

**Reporting only this half would be a false all-clear**, and it nearly was one
here: on its first run `tools/vmx/vmx128.py` printed `ps_sel fr10,fr10,fr11,fr9`
for the real workload word `0x114a4aee`, which the compiler's own listing calls
`vmaddfp vr10,vr10,vr11,vr9`. Same failure shape as the LLVM one — a plausible
legal instruction, no diagnostic, wrong — in our own decoder, on the first
attempt. Hence the explicit `XENON_PROFILE`.

### 5.2 MEASURED — against the real `llvm-mc` 22.1.8

Eight register-varied samples per row (`0,1,31,32,63,64,96,127`), **because the
answer changes with the register number**: `lvx128 vr1,r3,r4` decodes as
`vucmprlb 1,3,4`, and `lvx128 vr63,…` is refused. A single sample per row would
report one of those and hide the other.

| | |
|---|---:|
| sampled VMX128 encodings | 616 |
| **silently mis-decoded, no diagnostic** | **177 (28.7 %)** |
| refused — you get an error | 439 (71.3 %) |
| correct | **0** |
| rows silently wrong for at least one register allocation | **51 of 77** |
| rows silently wrong for *every* sample | 2 of 77 |

`isa.yaml` could not have predicted any of this: it is a Gekko/Xenon table and
carries **no Power10 encodings at all**. Two independent methods, two disjoint
answers, both reported.

What LLVM says instead, by frequency: `lxvp` **105**, then `vucmprhb`,
`vabsdub`, `vabsduh`, `vucmprhn`, `vucmprln`, `vucmprlb` (3 each), then
`vcmpnew`, `vinswvlx`, `vcmpneb[.]`, `vcmpneh[.]`, `vinsbvlx`, `vinshvlx`,
`vcmpequd`, `vcmpgtud`, `vinsdlx`, `vcmpnezw`, `vinswvrx` (2 each).

### 5.3 On the real workload, which is the number that matters

Of the **113** VMX128 instructions actually present in the dc3 workload:

| llvm-mc verdict | count |
|---|---:|
| **silently wrong** | **64** |
| refused (safe) | 49 |
| correct | **0** |

The 36 plain-AltiVec words in the same objects, LLVM gets right (26 exactly,
10 via the documented extended mnemonic `vmr` for `vor vD,vA,vA`). So the
damage is precisely confined to VMX128, and within it, **43 % of the errors
announce themselves and 57 % do not.**

### 5.4 `docs/PRIOR_ART.md` §3.2's unverified pairing is now verified

`PRIOR_ART` claims opcode-4 `lvx128` → `vucmprlb`. `rungs/_2026-08-04-w-llvm.md`
records that lane as unable to reproduce it — *"I did not construct a verified
`lvx128` encoding, so that one mnemonic is unverified here, not refuted."*

It reproduces exactly. `0x102320c3` is `lvx128 vr1,r3,r4` in `cl`'s own listing
(`FFT.cod`, the `__lvx` thunk) and `vucmprlb 1, 3, 4` in `llvm-mc`, with no
diagnostic. **PRIOR_ART was right.** `docs/ABI_EDGES.md:300` — *"a tooling gap
to close before any VMX rung"* — is closed by `tools/vmx/`.

### 6.1 The trap in this number, stated because a census is a driver

`docs/` memory records that **a census is a driver, not a target** — c2 emits
7.23 % of IL bodies while TU match sat at 6/878. The same discipline applies
in the other direction here: 0.344 % of TUs is a *ceiling on the TUs VMX128
codegen could ever unblock*, not a measurement that it would unblock them. All
three of these TUs almost certainly have other blockers too, and none of the
three is in the current match set. **The honest reading of 0.344 % is "even a
perfect VMX128 back end converts at most 3 TUs, and probably fewer."**

The measurement is also **workload-scoped**. A different Xbox 360 title —
particularly one using XNAMath/`XMVECTOR` throughout its math library rather
than a scalar `Vector3` class — would land somewhere else entirely. dc3's
engine does its vector math in scalar floats; that is a property of Milo, not
of the platform.

## 7. Recommendation: do NOT build VMX128 codegen

**A well-evidenced "not worth it" is the deliverable here, and this is one.**

| argument | number |
|---|---|
| TUs it could ever unblock | **3 of 878 (0.344 %)**, and only if nothing else blocks them |
| functions | **7 of 217,878** |
| instruction words | **113 of 3,866,911 (0.0029 %)** |
| opcodes that would have to work | **8** of the 77 rows — but a back end cannot ship 8 rows and refuse 69 without a `NotImplemented` boundary as expensive as the rows |
| what else changes | a **third register file**. `docs/ABI_EDGES.md` §5.1 established that a `__vector4` formal consumes neither a GPR nor an FPR argument slot — so vector arguments renumber nothing, but the allocator, the save/restore helper pairs (`__save…vmx`, unprobed above two saved vector registers), the frame class and `docs/LABEL_COUNTER.md`'s +2-per-helper-pair rule all acquire a new axis |

Three TUs is not worth a register file. Compare the live board: `#160`'s
section-vocabulary ladder is worth 871 TUs, `#302`'s coupling is worth 91.
**VMX128 is three orders of magnitude below the cheapest thing on the board.**

**What IS worth having is what this lane built**: the decode is now correct and
*checkable*, so any future lane that meets a vector instruction — in a
`.cod`, in an obj, in a diff — can read it rather than guess. That was the
stated blocker in `docs/ABI_EDGES.md:300` and it is now closed for the cost of
a table and four scripts.

### 7.1 What would change the recommendation

Stated in advance so it is not re-litigated by vibes:

* **A different workload.** Re-run `tools/vmx/build_objs.sh` +
  `tools/vmx/vmxscan.py` against it. If VMX128 TUs exceed ~5 % the arithmetic
  changes.
* **VMX128 turning out to be a blocker for something else.** It is not today:
  all three TUs are outside the current match set for other reasons.
* **The vector register file mattering to the *frame* rather than to codegen.**
  If a future EH or `.pdata` rung needs to model saved vector registers, it
  needs §3's encoding but not a code generator — which it now has.

## 8. Can the patched LLVM decode VMX128, and what would it cost?

**Yes, and the honest answer is that it would be a real patch and it is not
worth building either — but for a completely different reason than §7.**

### 8.1 The mechanism

LLVM's PowerPC disassembler is TableGen-driven: `PPCInstrInfo.td` +
`PPCInstrAltivec.td` define instruction classes with fixed-position operand
fields, and `PPCDisassembler.cpp` consumes a generated decoder table.
`tools/llvm/ppcbe.patch` (89 added lines, upstream `llvmorg-22.1.8`) does
nothing of this kind — it teaches LLVM that machine `0x01F2` is PowerPC and
names PPC COFF relocations. It touches no instruction table.

Adding VMX128 needs three things, and the second is the expensive one:

1. **A subtarget feature** — `+vmx128` / a `xenon` CPU in `PPC.td` and
   `PPCSubtarget`. ~20 lines. Trivial.
2. **New instruction *formats***. Every existing PPC `VXForm_*`/`VAForm_*`
   class assumes 5-bit contiguous register fields. VMX128's are 7-bit and
   **split across three disjoint pieces in `VA128`'s case, with pieces inside
   the extended-opcode field**. TableGen supports arbitrary bit assignment
   (`let Inst{21} = VA{6};`), so this is expressible — but it is a new
   `MCOperand` decode hook per field and a new register class of 128 `VR`s
   (`VSRp`-style), i.e. **new formats, not new rows in an existing format**.
   Realistically **~600–900 lines** across `PPCRegisterInfo.td`,
   a new `PPCInstrVMX128.td`, and `PPCDisassembler.cpp` decode hooks.
3. **77 instruction definitions** using those formats — mechanical once (2)
   exists, and generatable from `tools/vmx/vmx128_isa.py`. ~400 lines of
   generated `.td`.

**Plus a conflict resolution problem that is not optional.** LLVM's decoder
table is built by `FixedLenDecoderEmitter`, which *fails the build* on
ambiguous encodings. §5.2 shows 51 of 77 rows overlap Power10 encodings that
LLVM already has. So the feature must be predicated (`Predicates =
[HasVMX128]`) **and** the Power10 rows must be predicated *against* it, or
TableGen will reject the table. That is the part that turns a mechanical port
into a real patch, and it is why the 2007 binutils VMX128 patch — the only
prior public attempt at this in a mainstream toolchain — is also structured as
a separate machine flavour.

### 8.2 The estimate, and its uncertainty

| item | cost |
|---|---|
| subtarget + register class | ~150 lines |
| new instruction formats + decode hooks | **~600–900 lines**, the hard part |
| 77 instruction definitions | ~400 lines, generated from `vmx128_isa.py` |
| predicating the colliding Power10 rows | unknown until attempted; this is where a day disappears |
| build + iterate | the 190 s LLVM rebuild per iteration is not the cost; TableGen conflict diagnostics are |
| **total** | **~1,200–1,500 added lines, 1–2 lane-days**, against `tools/llvm/ppcbe.patch`'s 89 lines |

**Prototyped only far enough to know**, per the brief. What was actually done:
the encodings were extracted and verified (§3, §4), the exact overlap set was
computed (§5.1), and the LLVM behaviour was measured per row (§5.2) — which is
what tells you the TableGen conflict set is 51 rows rather than "some". No
`.td` was written.

### 8.3 Why it should not be built anyway

`tools/vmx/vmx128.py` is **305 lines of stdlib Python** over a 361-line generated table and it decodes all 77
rows correctly, verified 6,701/6,701 against the compiler's own listing. An
LLVM patch would buy: integration with `llvm-objdump -d` so vector code appears
inline in a disassembly listing. That is genuinely nicer. It is not worth
1,200 lines and an upstream-divergence maintenance burden for **113
instructions in 3 TUs**.

**The cheap version of the same benefit** — if a future lane wants annotated
disassembly — is ~30 lines: post-process `llvm-objdump -d` output, re-decode
every word whose primary opcode is 4/5/6 with `tools/vmx/vmx128.py`, and
overwrite the line. That gets correct VMX128 in an objdump listing without
touching LLVM at all. Priced, not built.

## 9. Reproducing everything in this file

```sh
tools/vmx/build_objs.sh                       # 878 TUs, ~30 s, ~102 MB
tools/vmx/vmxscan.py work/w-vmx/objs          # §6 — the prevalence census

mkdir -p work/w-vmx/lst/fft
tools/vmx/listing.sh src/system/synth_xbox/FFT.cpp work/w-vmx/lst/fft
tools/vmx/genprobe.py --pressure 40 > work/w-vmx/probe2/probe2.cpp
tools/vmx/listing.sh "$PWD/work/w-vmx/probe2/probe2.cpp" work/w-vmx/probe2

tools/vmx/vmxcheck.py --llvm work/w-vmx/lst/*/*.cod work/w-vmx/probe*/*.cod
tools/vmx/vmxcheck.py --selftest work/w-vmx/lst/*/*.cod   # the instrument can fail
tools/vmx/collide.py                                      # §5
tools/vmx/collide.py --md                                 # §5.5

tools/vmx/gen_isa_table.py                    # regenerate the table (PyYAML + network)
```

With no toolchain, `listing.sh` prints `SKIP: toolchain absent` and exits 3.
With no LLVM, `llvmmc.py` and `collide.py`'s measured half print
`SKIP: llvm-mc absent` and the exact half still runs. **`vmxcheck.py` never
skips silently: zero verified instructions is a non-zero exit.**
