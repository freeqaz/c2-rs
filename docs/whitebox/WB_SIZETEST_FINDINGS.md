## 0. The answer in six lines

* **The mask is the constant `0x2000` — `__forceinline` — and it is not
  caller-supplied.** `mov edi,0x2000` at `0x10b5fc31` **dominates**
  `test edi,eax` at `0x10b5fc95`; the function has three `edi` writes and no
  other; **no call site writes `edi`**. `#3830`'s *"a caller-supplied `ATTR`
  mask … one of `FUN_10b5fb5f`'s five parameters"* is **wrong**, and the
  wave-21 brief inherits the error.
* **It was already named in this tree, two days before `#3830` published the
  opposite.** `P_INLINE` §6.5 (`w-inlmetric`, `#3717`–`#3722`, 2026-08-27)
  says so under a heading. *"Named nowhere in this repo"* is false.
* **There IS a caller-supplied mask in this function and it is a different
  instruction** — `param_4`, tested `& 0xf00` at `0x10b5fc01`. It refuses, it
  is `0` at two of the three call sites, and no page in this tree names it.
* **The size test does not decide candidacy on this workload — it does not
  RUN.** `DAT_10c2e310` skips it (`0x10b5fc84`), its image value is **`1`**,
  and bodies with `.gl SIZE` up to **211** inline at `/O1` against a ceiling
  of **128**. `[R]` + `[O]`, §4.
* **The brackets bracket nothing, exhaustively.** `DAT_10c46318` has **one
  reader and two writers**; its entire attainable value set is enumerated, and
  **no member of it reproduces the frozen verdicts on all three ladders** —
  the external ladder is unreachable by any `k`, and the one value inside the
  static ladder's span predicts the flip a rung early. §5.
* **`P_INLINE` §2.1b's mechanism is refuted a second way, and §4 of that page
  rests on an address its own 2026-08-18 correction struck.** §6.

## 2. The mask, settled by dominance rather than by proximity `[R]`

### 2.1 Why proximity was never going to settle it

`P_INLINE` §6.5 already concluded `edi = 0x2000`, and its argument is:

> `edi` is callee-saved and **nothing between the two writes it**.

That is a claim about an **address interval**. The question is a claim about
**paths**: a jump landing after `0x10b5fc31` and before `0x10b5fc95`, from a
block that never executed `0x10b5fc31`, would leave the interval statement
literally true and the conclusion false. `#3830` read the same 377 bytes and
concluded the opposite. **Neither page computed the thing that decides it**,
which is why this lane built a tool instead of reading harder.

[`work/w-sizetest/cfg.py`](../../work/w-sizetest/cfg.py) recovers the CFG from
the objdump listing and runs an iterative dominator fixpoint at **instruction**
granularity, and prints its blind spots (indirect branches — none here; unwind
edges; caller-saved registers — `edi` is not one).

### 2.2 The result `[R]`

[`grids/w-sizetest/edi_writes.txt`](grids/w-sizetest/edi_writes.txt) —
**three** writes to `edi` in the whole 377-byte body:

```
10b5fb83: xor  edi,edi        <- before, on every path (the delayed save is at 10b5fb82)
10b5fc31: mov  edi,0x2000     <- THE MASK
10b5fcd1: pop  edi            <- the epilogue
(edi is CALLEE-SAVED: calls in range preserve it)
```

[`grids/w-sizetest/dom_10b5fc95.txt`](grids/w-sizetest/dom_10b5fc95.txt) — the
dominator set of `0x10b5fc95` is 43 instructions and **`0x10b5fc31` is in it**:

```
...
10b5fc23: je     0x10b5fc31
10b5fc31: mov    edi,0x2000       <-- DOMINATES
10b5fc36: test   edi,ebx
10b5fc38: jne    0x10b5fc67
10b5fc69: cmp    DWORD PTR ds:0x10c3de20,0x2
10b5fc70: jne    0x10b5fc7e
10b5fc7e: cmp    DWORD PTR ds:0x10c2e310,ebx
10b5fc84: jne    0x10b5fcb9
10b5fc86: movzx  eax,WORD PTR [esi+0x50]
10b5fc8a: cmp    eax,DWORD PTR ds:0x10c46318
10b5fc90: jl     0x10b5fcb9
10b5fc92: mov    eax,DWORD PTR [esi+0x4c]
10b5fc95: test   edi,eax
```

> **`[R]` — the mask at `0x10b5fc95` is the immediate `0x2000`, i.e.
> `__forceinline`, on every path. It is not a parameter, it is not
> caller-supplied, and it is not a decision point c2 exposes.**

### 2.3 …and the call sites confirm it from the outside `[R]`

A Ghidra parameter list is a hypothesis about a convention. The evidence that a
register is *not* inbound is that **no caller writes it**.
[`grids/w-sizetest/callsites.txt`](grids/w-sizetest/callsites.txt) — all three
direct call sites, with 14 instructions each:

| call site | in | setup |
|---|---|---|
| `0x10b6025d` | `FUN_10b600e6` (the site collector) | `mov edx,[ebp-0x14]` · `push 0` · `push [ebp-0x24]` · `push [ebp+0x8]` · `mov ebx,eax` |
| `0x10ba18fc` | `FUN_10ba1430` | `push 1` · `push 0` · `push eax` · `mov edx,ebp` · `mov ecx,ebx` |
| `0x10baf63e` | `FUN_10baf51d` | `push 0` · `push 0` · `push eax` · `mov edx,esi` |

**`edi` is written at none of them.**

### 2.4 Where `#3830`'s "five parameters" came from, and why it is not `edi`

Ghidra's own signature (`decomp_all.c:54539`):

```c
undefined4 __fastcall FUN_10b5fb5f(void *param_1,int *param_2,int param_3,uint param_4,int param_5)
```

The count **5 is right** and reads straight off the prologue and the epilogue:
`ecx` (→ `ebx`, `0x10b5fb65`), `edx` (→ `[ebp-0x4]`, `0x10b5fb68`), and
`ret 0xc` (`0x10b5fcd5`) = **three stack dwords** at `[ebp+0x8]`, `[ebp+0xc]`,
`[ebp+0x10]`. **`edi` is none of the five.** `#3830` took a correct parameter
*count* and attached it to a register that is not in the list — a `#3505`-shaped
error (a census answering a different question than the one asked), on the same
register `#3505`'s sharpest instance is about.

## 3. The caller-supplied mask that IS in this function, and nobody has named it `[R]`

The brief asked for a caller-supplied mask. There is one; it is a different
instruction with a different job, and this page names it because the question
deserves an answer rather than only a refutation.

```
10b5fbf9:  8b 5e 4c              mov   ebx,DWORD PTR [esi+0x4c]   ; ATTR
10b5fbfc:  f6 c3 10              test  bl,0x10                    ; ATTR bit 4
10b5fbff:  74 0d                 je    0x10b5fc0e                 ;   clear -> skip
10b5fc01:  f7 45 0c 00 0f 00 00  test  DWORD PTR [ebp+0xc],0xf00  ; <- param_4, CALLER-SUPPLIED
10b5fc08:  0f 84 bc 00 00 00     je    0x10b5fcca                 ;   -> return 0
```

> **`[R]` — `param_4` is a caller-supplied bitmask; when the callee's `ATTR`
> carries bit 4, candidacy REFUSES unless `param_4 & 0xf00` is non-zero.**
> It is covered by **no clause row** in `CLAUSES.tsv`'s 24.

Its values, from §2.3's table:

| call site | `param_4` |
|---|---|
| `0x10ba18fc` | **`0`** (immediate) |
| `0x10baf63e` | **`0`** (immediate) |
| `0x10b6025d` | `[ebp-0x24]` in `FUN_10b600e6` — a **local**, `0` at entry (`0x10b6010b`), assigned at `0x10b6045b` |

and the assignment is worth reproducing, because it makes `param_4` **per-site
IL data**:

```
10b60446:  8a 46 08     mov  al,BYTE PTR [esi+0x8]     ; tuple kind
10b60449:  3c 17        cmp  al,0x17
10b6044b:  75 18        jne  0x10b60465
10b6044d:  81 7e 04 12 03 00 00  cmp DWORD PTR [esi+0x4],0x312
10b60454:  75 5b        jne  0x10b604b1
10b60456:  8b 46 20     mov  eax,DWORD PTR [esi+0x20]
10b6045b:  89 45 dc     mov  DWORD PTR [ebp-0x24],eax  ; <- param_4 for LATER sites
```

`FUN_10b600e6` is the **site collector** (`P_INLINE` §1: *"one linear scan"*),
so a value stamped on one tuple governs the call sites the scan reaches after
it. The same local is also stored into the candidate record (`puVar10[2] =
local_28`, `0x10b602b6`–`0x10b602b9`).

> **`[I]` — `param_4` looks like a scan-carried pragma/attribute word keyed off
> IL tuple kind `0x17`, opcode `0x312`.** This lane did **not** open the
> opcode tables to name `0x312` and does not guess. Ranked in §8.

Two of three callers pass `0`, so on any path through those two the `ATTR & 0x10`
arm is a **flat refusal**. That is a real, unclaimed clause and it is `[R]`.

## 4. What the size test decides — and the answer is *nothing, on this workload*

### 4.1 The tail, factored `[R]`

`ebx = 0` from `0x10b5fc42`/`0x10b5fc67` on every path into `0x10b5fc69`
(both predecessors `xor ebx,ebx`), so every `cmp …,ebx` below is `… == 0`.
Full listing: [`grids/w-sizetest/FUN_10b5fb5f.asm`](grids/w-sizetest/FUN_10b5fb5f.asm).

```
10b5fc7e:  cmp  ds:0x10c2e310,ebx        ; FAVOUR-SPEED
10b5fc84:  jne  0x10b5fcb9               ;   set  -> SKIP the size test entirely
10b5fc86:  movzx eax,WORD PTR [esi+0x50] ; the count
10b5fc8a:  cmp  eax,ds:0x10c46318        ; the ceiling
10b5fc90:  jl   0x10b5fcb9               ;   under -> join
10b5fc92:  mov  eax,DWORD PTR [esi+0x4c] ; over:
10b5fc95:  test edi,eax                  ;   edi == 0x2000  (§2)
10b5fc97:  jne  0x10b5fcb9               ;   __forceinline -> join
10b5fc99:  cmp  ds:0x10c2e2fc,ebx  / je  -> return 0
10b5fca1:  cmp  [esi+0x80],ebx     / je  -> return 0
10b5fca9:  test al,0x2             / jne -> 0x10b5fcb5
10b5fcad:  cmp  ds:0x10c2eaac,ebx  / je  -> return 0
10b5fcb5:  test al,0x10            / jne -> return 0
10b5fcb9:  cmp  ds:0x10c2e2fc,ebx  / jne -> return 1
10b5fcc1:  test DWORD PTR [esi+0x4c],0x2080 / jne -> return 1
10b5fcca:  xor  eax,eax                  ; return 0
```

**`#3830`'s block elides `0x10b5fc99`–`0x10b5fcb7` behind a `...`, and that
elision is where its conclusion comes from.** The over-ceiling path does not
"reach the same gate": it runs a five-test chain with **four routes to
`return 0`** and one fall-through. Written out:

> **`[R]` — candidacy returns 1 iff**
> ```
> ( DAT_10c2e310 != 0                       # favour-speed: size test skipped
>   OR count < DAT_10c46318                 # under the ceiling
>   OR ATTR & 0x2000                        # __forceinline
>   OR ( DAT_10c2e2fc != 0 AND [sym+0x80] != 0
>        AND (ATTR & 0x2 OR DAT_10c2eaac != 0) AND NOT (ATTR & 0x10) ) )
> AND ( DAT_10c2e2fc != 0  OR  ATTR & 0x2080 )
> ```

The **direction** is confirmed from the caller `[R]`: `0x10b60262`
`test eax,eax` / `jne` falls through to `FUN_10c2022a(7,0x20)`, the candidate
record allocation, and a zero return reaches `FUN_10b5bfc0` and skips the site.
**Return 1 = candidate.**

### 4.2 The two gate globals, read `[R]`

[`grids/w-sizetest/globrefs.out`](grids/w-sizetest/globrefs.out) and
[`optword_decode.asm`](grids/w-sizetest/optword_decode.asm). `FUN_10b82338`
(374 B, one caller) decodes a **per-function option word** `[fn+0x1c]`:

| global | bit of `[fn+0x1c]` | address | role at `FUN_10b5fb5f` |
|---|---|---|---|
| `DAT_10c2e310` | **23** (`0x800000`) | `0x10b8238b`–`0x10b82392` | **non-zero ⇒ the size test is skipped** |
| `DAT_10c2e2fc` | **21** (`0x200000`) | `0x10b823e0`–`0x10b823e7` | **zero ⇒ candidacy returns 1 only for `ATTR & 0x2080`** |
| `DAT_10c2e308` | 21, gated on `DAT_10c3cf68` | `0x10b823d0`/`0x10b823da` | the POGO arm at `0x10b5fb85` |

**`DAT_10c2e2fc` has exactly ONE SETTING writer and six CLEARING ones**, which
is a sharper statement than a raw write count and is what the census is for:
`0x10b823e7` is `mov …,edx` with `edx` = bit 21; `0x10b7e776`, `0x10b7e867`,
`0x10b7e89b`, `0x10b82469`, `0x10b824a0` are all `mov …,edi` with `edi = 0`
(verified: each function `xor edi,edi` early), and `0x10c21a9f`/`0x10c21ac1`
are an `and …,0x0` / restore pair. So the only way it becomes non-zero is
**option-word bit 21**.

### 4.3 The image values, read out of the PE independently `[R]`

[`grids/w-sizetest/readva.out`](grids/w-sizetest/readva.out) —
[`readva.py`](../../work/w-sizetest/readva.py) is a stdlib PE32 section walk, so
these are independent of both Ghidra and objdump, and it **refuses** to quote a
VA past `SizeOfRawData`:

| VA | section | image value |
|---|---|---|
| `0x10c2ea98` (`k`) | `.data +0xa98` | **3** |
| `0x10c2e310` (favour-speed) | `.data +0x310` | **1** |
| `0x10c2e2fc` (the second gate) | `.data +0x2fc` | **0** |
| `0x10c2eaac` | `.data +0xaac` | **0** |
| `0x10c46318` (the ceiling) | `.data +0x18318` | **UNINITIALIZED** — past `SizeOfRawData 0xec00`; reads 0 at load, **not an image value** |
| `0x10c3de20`, `0x10c6f1c8` | `.data` | **UNINITIALIZED**, same |

`k = 3` corroborates `P_INLINE` §6.8.6 by a third instrument, and gives
`DAT_10c46318 = 16 << 3 = 128` at run time.

**And `DAT_10c2e310`'s image default is `1`, not `0`.** No page in this tree
records that. The default state of c2 is *size test off*.

### 4.4 The size test does not run at `/O1` — `[R]` + `[O]`

Three published `[O]` facts, none of them this lane's:

* `P_INLINE` §2.1b: the `arith` family is **inlined at every rung to
  `.gl SIZE = 211`**, at `/O1` and `/Ox`.
* `WB_INSTRCOUNT` §5.1: the D family's `k=24` cell, callee count **183**, is
  **inlined** at `/O1` and `/O2`.
* `WB_INSTRCOUNT` §6: GRID-I static cells at **253** and **260** are
  **inlined** at `/O1 /GS- /c`.

All four counts are **above 128**. So if the size test ran, each needs the
over-ceiling escape of §4.1 — and the escape is closed for them:

* `ATTR & 0x2000` — no; these are ordinary functions.
* the `0x10b5fc99` chain needs `(ATTR & 0x2) OR (DAT_10c2eaac != 0)`.
  `WB_INSTRCOUNT` §2.4 **measured** `gl_attr = 104 = 0x68` on this family —
  `0x68 = 0b0110_1000`, so **bit 1 is clear**, and `DAT_10c2eaac`'s image value
  is `0` with no `-pg*` switch in c2's argv at any of 22 modes (`P_INLINE`
  §6.8.6, `[O]`).

> **`[R] + [O]` — at every profile this project has measured, `0x10b5fc84`
> jumps and `0x10b5fc8a`–`0x10b5fc90` NEVER EXECUTE. `DAT_10c2e310 != 0`, i.e.
> option-word bit 23 is set, and the ceiling `DAT_10c46318` is never read.**

Note the corroboration this makes retrospective sense of: `w-sizebracket`
§2.1c found `/O1` separates on emitted `.text` and **`/Ox` does not separate at
all** — 320 B inlined beside 196 B kept — and reached for *"consistent with
§2.1's favour-speed bit turning this very test off"*. It is turned off at
**both**.

**The one assumption left open**, named rather than buried: `DAT_10c2eaac` has
14 writers and this lane read none of them; the argument uses its image value
plus the absence of profile switches. If some path sets it, the `0x10b5fc99`
chain reopens and the conclusion needs re-deriving. It does **not** reopen the
mask result in §2, which depends on nothing here.

### 4.5 So what does the size test decide?

> **On this workload: nothing. It is dead code at every profile measured.**
> Structurally, if bit 23 were clear it would decide candidacy for exactly the
> callees that are not `__forceinline`, carry no `ATTR & 0x2` and reach no
> profile record — i.e. it would be the ordinary-callee boundary that four
> pages in this tree assume it already is. **`#3830`'s headline — "neither
> necessary nor sufficient" — is right, and it is right for a reason `#3830`
> did not have and understates.**

## 5. The brackets — what they exclude, exhaustively, and what this lane refuses to name

`WB_INSTRCOUNT` §6 published, in the read unit:

* **STATIC:** verdict flips in `count ∈ [261, 267]`
* **EXTERNAL:** verdict flips in `count ∈ [93, 99]`

and observed that *"neither contains any `0x10 << k`"* and *"no single value
satisfies both"*. That is a statement about one **form** of the ceiling. The
read makes it a statement about the ceiling's whole **range**.

### 5.1 The ceiling is a one-reader, two-writer global `[R]`

[`ceiling_writer.asm`](grids/w-sizetest/ceiling_writer.asm), `FUN_10b5e4cc`:

```
10b5e4cc:  mov ecx,ds:0x10c2ea98        ; k
10b5e4d2:  cmp ecx,0x6
10b5e4d5:  jle 0x10b5e4e3
10b5e4d7:  mov DWORD PTR ds:0x10c46318,0x3e8   ; k >= 7  -> 1000
10b5e4e1:  jmp 0x10b5e4ed
10b5e4e3:  push 0x10 ; pop eax
10b5e4e6:  shl eax,cl                          ; k <= 6  -> 16 << (k & 31)
10b5e4e8:  mov ds:0x10c46318,eax
```

and [`globrefs.out`](grids/w-sizetest/globrefs.out) shows `0x10c46318` has
**3 operands in the whole image**: these two writes and **one read**,
`0x10b5fc8a`. So the enumeration below really is complete.

*(A small correction owed to `WB_INSTRCOUNT` §5.2, which renders this as
`min(0x10 << k, 1000)`. It is not a `min` — `16 << 6 = 1024 > 1000`, and the
arms are selected by `k ≤ 6` rather than by magnitude.)*

### 5.2 The exhaustive check `[R]` + `[O]`

[`ceiling_range.py`](../../work/w-sizetest/ceiling_range.py) →
[`ceiling_range.out`](grids/w-sizetest/ceiling_range.out). It enumerates every
attainable `DAT_10c46318` (including the negative-`k` aliasing, which adds
nothing) and tests each against the three published ladders under the read
predicate `count < ceiling`:

| ladder | counts | frozen | ceilings inside the span | ceilings that reproduce it |
|---|---|---|---|---|
| GRID-I STATIC | 253, 260, 267, 274 | inl, inl, called, called | **256** only | **NONE** — 256 predicts `inl, called, called, called` |
| GRID-I EXTERNAL | 85, 92, 99, 106 | inl, inl, called, called | **NONE** | **NONE** at any `k` |
| D family (12 cells) | 183, 365, 855 | inl, called, called | 256, 512 | **256** (`k = 4`) |

> **`[R] + [O]` — `DAT_10c46318`'s attainable value set is
> `{16, 32, 64, 128, 256, 512, 1000, 1024, …, 2^30} ∪ {0, −2^31}`, and NO
> member of it reproduces the frozen verdicts on all three ladders. The
> external ladder cannot be moved by the size test at ANY `k`, because no
> attainable value lies in `(85, 106]` at all.**

Two things worth separating, because they are different strengths of result:

* The **external** ladder's exclusion is unconditional and needs no assumption
  about `k`, about profiles, or about §4.
* The **static** ladder is refuted by exactly **one cell** — the 260-count cell
  — and the D family is *consistent* with `k = 4`. So the two static datasets
  **disagree with each other** under the size-test hypothesis. That
  disagreement is itself the refutation, and it is more informative than either
  dataset alone.

### 5.3 What the brackets ARE consistent with

Everything above is negative. The positive statement the read supports:

1. **They are consistent with §4** — if the size test never runs, both ladders
   are moved by a predicate downstream of `0x10b5fc8a`, and **there is no
   reason a single value should fit both**, because there is no single value in
   play. The puzzle in `WB_INSTRCOUNT` §6's last paragraph dissolves rather
   than being solved.
2. **They are consistent with a linkage-sensitive predicate that is NOT in the
   candidacy function.** `P_INLINE` §6.5's negative result stands and this lane
   re-derived it from the full listing: **no storage-class or linkage field is
   tested anywhere in `FUN_10b5fb5f`'s 377 bytes** (`[gl+0x37]` appears zero
   times — checked over `FUN_10b5fb5f.asm`). The two brackets differ by ~2.8×
   between linkages, so whatever moved them reads linkage, and it is elsewhere.
   The standing candidate remains `0x10b60a81`'s `test DWORD PTR [edi+0x37],
   0x400`, in the accept/decline predicate, covered by no clause row.
3. **They are consistent with `WB_INSTRCOUNT` §6's own hedge, which should now
   be promoted.** That section wrote *"the 'if' in the first line is
   load-bearing"* — the antecedent *"if the size test is what moves along each
   ladder"*. **The antecedent is now FALSE, not merely unverified**, and the
   brackets should be published as measured verdict boundaries with the size
   test explicitly excluded as their mechanism.

**This lane names no ceiling value.** `#3732` refuted 128 with 8 counterexamples
in each direction, adopting it is a standing prohibition, and adopting 256 or
261 or 267 in its place would be the same error with a fresh number. The
deliverable here is the **exclusion**, and it is exhaustive.

## 7. A control this lane failed, and caught before publishing `[R]`

Reading `FUN_10b6242a` top to bottom, this lane wrote down that
`0x10b624c0`–`0x10b624dc` — the in-band save/override/restore of

**It is not dead.** `cfg.py`'s block enumeration

predecessor of the test.

**saves `DAT_10c2e310`, overrides it from the profile record's own stored
option word (`[prof+0x76] & 0x800000`, `0x10b624ce`–`0x10b624dc`) and restores
it at `0x10b6255a`** — a per-callee favour-speed override, live only under
POGO. Recorded because the false reading was one paragraph from publication and
because it is the same class as the two errors this page corrects: **a linear
