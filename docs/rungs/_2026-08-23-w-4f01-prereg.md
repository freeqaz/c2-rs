**Registered narrowing, so it is not discovered later and called a fix.** True
VI32 sign-extends a lead byte in `0x81..=0xFF` to a *negative* value in one

(`read_varint` returns `None`; `opt_line` returns). A source line is never
negative, so this is unreachable from c1xx-produced IL — but it is a real
narrowing of the read, and the fixed sites will **match the existing
fail-closed idiom rather than implement full VI32.** Stated here so that the
rung cannot claim more generality than it ships.

## 2. Predicted effect — the number that decides whether this went wrong

**Zero byte movement on the existing 386-fixture corpus, and zero on the
878-TU workload.** Below source line 128 a fixed-byte read and a VI32 read
consume the same three bytes and yield the same value, so the two rules are
**pointwise identical** on every input the corpus contains.

Concretely predicted, base vs tip, pinned binaries, same workload stamp:

* `c2rs gap` — every one of `match`, `mismatch`, `codegen-gap`, `vocab-gap`,
  `capture-fail`, and both census fractions: **identical**.
* `ir0-roundtrip-broken`: **0 before and 0 after** — and this is predicted to
  be *uninformative*, see §3.
* `scripts/gate.sh` verdict block: identical modulo the new fixtures'
  own rows.
* Fixture gate: denominator moves by exactly the number of fixtures added
  (386 → 386+N); no existing fixture changes verdict.

**If any existing-corpus byte moves, that is a FINDING and it gets reported as
one — it is not absorbed, and it is not explained away in the rung.** It would
mean the two rules are *not* pointwise identical below 128 and that the read is
wrong somewhere this file did not predict.

## 3. The red, registered before it is run

A fix that was never seen red proves nothing. Registered predictions about
**what can and cannot go red**, because getting this wrong is the whole hazard
board #3443 describes:

* **PREDICTED GREEN-AND-USELESS: the container round-trip control.**
  `ir0-roundtrip-broken` has a known answer of 0 and is predicted to stay 0
  **even on a stream that contains a wide marker, and even before the fix** —
  because the four mis-skipped payload bytes coalesce into a `Span::Opaque`
  run that re-encodes byte-identically. So the codec's own totality control is
  green *by construction* on this defect. If that holds it is a **stronger form
  of `STATUS.md` trap 0** than trap 0 states: not merely green over a
  population that lacks the shape, but green over the shape itself.
* **PREDICTED RED: the decoded token stream.** `IlModel::ex_tokens()` /
  `function_tokens()` on a segment carrying a wide marker. Before the fix the
  record decodes as one narrow `Stmt` plus four leftover bytes; `0x02`, `0x03`
  and `0x04` are `Add`/`Sub`/`Mul` in this very decoder, so a line number whose
  little-endian bytes contain one of them yields a **spurious arithmetic token**
  in the middle of the operand stream. Predicted concrete witness: **source
  line 260 = `04 01 00 00` → a phantom `ExToken::Mul`.**
  *(This prediction is registered without having been run. If line 260 does not
  produce it, the miss is reported as a miss.)*
* **PREDICTED NOT-RED: `Port=Match` on the port's own emit path.** The emit
  path goes through `readers.rs`, which is already correct, so a matching
  fixture pushed past line 128 is predicted to **still match**. Measured
  already on a scratch copy, before this file was written: `mvp_add3.cpp` at
  `#line 1000` and `mvp_edit_ab.cpp` at `#line 124` both read `Port=Match` at
  base. **So the byte judge alone cannot grade this fix**, and the rung must
  say so rather than quoting a green `diff` as if it were the proof.
* **Consequence, registered as the honest framing:** this is a **DECODE**
  defect on an instrument path (`crates/c2-harness/src/search/` — the permuter
  named in `CLAUDE.md` as a goal-(1) consumer — and `gap/scan.rs`), not a live
  wrong emit. The rung will grade decode against **real captures**, not against
  the lane's own expectation.

## 5. Decline criteria — registered so a decline is honest and not a retreat

This lane reports **`declined`** or **`FAILED`**, in those words, if any of:

1. **The VI32 rule fails re-verification.** (Discharged: 10/10, §0.)
2. **The fix moves existing-corpus bytes.** Then the two rules are not
   pointwise identical below 128, the model is wrong, and shipping the edit
   would be trading a known-narrow read for an unknown one. Report the
   movement; do not absorb it.
3. **No red can be produced.** If neither a real capture nor a hand-built
   stream can be made to decode differently before and after, then the "defect"
   is unobservable through every seam this lane owns, and the correct outcome
   is to say so — a fix nobody can see go red is a refactor, and it should be
   labelled one.
4. **The fixtures cannot be made to carry both widths.** If c1xx does not emit
   what the grid says it emits when the source is a tracked fixture rather than
   a generated probe, the fixture half is declined and the reason recorded.
5. **A crossing point with a peer lane.** `w-s1c2` owns `crates/c2-core`;
   `w-pwords` owns the harness instrument seam. This lane owns `crates/c2-il`,
   `crates/c2-reference` tests, and `fixtures/`. **`crates/c2-harness` is NOT
   this lane's** — if the fix turns out to require editing harness code beyond
   the mechanical follow-on of a changed `c2-il` enum, that is recorded as a
   crossing point and reported, not taken unilaterally.
