## 0. Bias, stated in writing

w-r1's §0 named "fitting to two TUs" and it still applies, but my specific risk
is different and sharper, because **I inherit a lane that already declined
once**. The pull is to convert *something* so the rung is not two declines in a
row. The concrete way that goes wrong here is **piece (c)**: `resolve_data` is
one function, widening it is a three-line diff, and it would immediately make
both TUs resolve. It would also move some part of **39,967** functions that file
under `data-sym-*` into the emitter, where the port's fixed shell has no `.bss`
and no `.data` — a wrong relocation against a real symbol, which prereg w-r1 §3.2
registers as *strictly worse than the refusal standing today*.

I therefore commit in advance: **`Bindings::resolve_data` keeps its current body
and its current callers.** If the TUs convert it will be through a *separate*
whole-TU recognizer that cannot be reached by an ordinary function, and if I
find myself editing `resolve_data` I am off the plan.

Second bias, weaker: I would rather report 8 than 6, same as w-r1.

## 2. What I measured before predicting (§6 has the bytes)

Three things w-r1 could not check, now checked:

1. **The `.gl` data record is a fixed frame** `<tag> [wide] <kind> 00 <02|04>
   <linkage> <size-varint> <attr>`, and the `size > 127` probe confirms `size`
   is `read_varint`'s escape (`80` + LE32): `char pad[200]` spells
   `82 06 00 02 04 · 80 c8 00 00 00`.
2. **The `.in` literal length is a THIRD varint** — `80` + **LE16**, not
   `read_varint`'s `80` + LE32. A 134-byte literal spells `80 86 00`. Reusing
   `read_varint` here would desynchronize every literal ≥ 128 bytes.
3. **An internal-linkage object's `.gl` name is `$`-prefixed** and its COFF name
   is that name minus the `$`: `$sL` → `sL`, `$sLicense` → `sLicense`,
   `$sL$initializer$` → `sL$initializer$`. This is why TomCrypt says
   `data-sym-unresolved` and Zlib says `data-sym-not-extern`: `gl_symbol_index`
   only opens a name run after `00` or `26`, so a `24`-introduced name is never
   seen at all.

## 4. The plan, and the boundary each piece is fenced at

* **(a) `.gl` data-symbol reader.** New `gl_data_object(gl, tok) -> Option<…>`
  yielding COFF name, `natural_align` (from the tag), `size`, and the linkage
  byte. Fails closed on: a missing `00 <02|04>` frame, a linkage byte outside
  `{01, 04}` (defined-external / static — `02` is *undefined* external and is
  not an object this TU defines), a negative/short-form-ambiguous size, an
  unknown tag.
* **(b) `.in` string-literal reader.** New `in_string_literal(in, tok)`. The
  record is `<tok> 00 03 <len> <bytes> 07`; the read is **self-checking** —
  the decoded length must land exactly on a trailing NUL followed by `07`, so a
  mis-decoded length refuses rather than returning a prefix.
* **(c) NOT a `resolve_data` widening.** A whole-TU recognizer that requires:
  exactly one function segment, whose name is `??__E<ident>@@YAXXZ`, decoding to
  `MultiArgTailCall` with exactly the slots `[SymAddr, SymAddr, Lit]`; slot 0's
  token resolving through (a) to an object this TU defines; slot 1's token
  resolving through (b) to a literal **whose computed `??_C@…` name `.gl` also
  carries**; and the callee token resolving to a constructor. Any deviation
  refuses. An ordinary function cannot reach this path.
* **(d) the caller.** `PortC2::build` tries the recognizer before
  `il.functions()`, and emits via `emit_dyninit_obj`. `PORT_WRITER_SECTIONS` in
  `gap.rs` stops being an accurate transcription the moment this lands (w-r1
  "found and not taken" item 3), so it must be published from `coff.rs` and
  imported — that is part of (d), not a follow-on.

**Outside the boundary the port refuses**, and an `Err(NotImplemented)` there is
a deliverable of this lane, not a shortfall. Explicitly out of scope and
declined in advance: ≥2 objects (§7.1's name-keyed `.bss` permutation), `??_G`
and the rest of the `??_` family, a destructor (`??__F`, +2 sections), `/Ox`,
and a TU that mixes ordinary functions with a thunk.

## 5. Binding decline clauses

Any one ⇒ **DECLINED**, whatever else the lane achieved. Carried forward from
w-r1's prereg §3 unchanged, because the brief restates them as binding.

1. TU match **< 6**.
2. **mismatch > 0 anywhere** — scan, gate, sweep, or a fixture. *Either license
   TU landing `mismatch` is the single worst outcome of this lane.*
3. A lost `gate.sh` lane, or a `SKIP`/`NO-RESULT` where the incumbent had `PASS`.
4. Any existing fixture verdict changing.
5. A K1 round-trip byte moving.

Plus one this lane adds, from §0:

6. **`Bindings::resolve_data`'s acceptance changing.** If the global data-symbol
   path widens, the lane is declined even if both TUs convert and every gate is
   green — because the risk it takes on is not bounded by anything this lane
   measured.

## 6. The bytes the plan is built on

`.gl` data records, name-NUL immediately preceding, one row per capture:

```text
  fixture /Ox   $sL\0                        82 06 00 02 04 01 00 61   align 1  size 1    static
  TomCrypt      $sLicense\0                  86 06 00 02 04 0c 00 61   align 4  size 12   static
  Zlib          ?sLicense@@3VLicenses@@A\0   86 06 00 02 01 0c 00 61   align 4  size 12   extern
  p_extern      ?gL@@3UL@@A\0                86 06 00 02 01 04 00 61   align 4  size 4    extern
  p_big         $sL\0                        82 06 00 02 04 80 c8 00 00 00   align 1 size 200
  (initializer) $sL$initializer$\0           86 04 00 02 04 04 80      always static
  (string)      ??_C@_0BK@PELMDOBM@…\0       82 06 00 04 01 1a a0 25   note `00 04`, not `00 02`
```

`.in` literal records:

```text
  fixture /Ox   ef 09 · 00 03 · 04       · 61 62 63 00                    · 07
  TomCrypt      fc 09 · 00 03 · 1a       · system/src/synth/tomcrypt\0    · 07
  Zlib          fc 09 · 00 03 · 10       · system/src/zlib\0              · 07
  p_biglit      f0 09 · 00 03 · 80 86 00 · 0123…ABC\0  (134 B)            · 07
```

The last row is the one that matters: `80 86 00` is `80` + **LE16** 134. The
statement varint would have read `80` + LE32 and desynchronized.

**The `/Ox` trap, in full.** The fixture at `/Ox` has the literal in `.in`
(`ef 09 00 03 04 abc\0 07`) and **no `??_C@` name anywhere in `.gl`**. Trusting
`.in` alone converts a fixture whose obj this lane has not modeled. That is
prediction C1 and it is the single most likely way this lane ships wrong bytes.
