## 1. What was asked, and the one thing that was wrong with the request

`scripts/debug_lane.sh` has existed since 2026-08-14, works, and **nothing ran
it**. It shipped deliberately unwired: the rung that shipped it
(`docs/rungs/2026-08-14-dbgassert.md` §"the blindness") recorded the reason in
the words that matter — *"making a debug panic a merge blocker is the user's
decision, not the coordinator's and not this lane's."* **The user has now made
that decision.** This lane is the wiring.

The request carried a cost figure: *"it was measured at 0.65 s warm."* **That
figure belongs to a different candidate.** §"the blindness" prices two things,
and only one of them is `debug_lane.sh`:

| candidate | what it is | cost | needs toolchain |
|---|---|---|---|
| **(b)** | a debug `cargo test --workspace --lib` **unit row** | **6 s cold, 0.65 s warm** | no |
| **(c)** | `scripts/debug_lane.sh`, 18 lanes × 381 fixtures | **125 s warm** | yes |

**0.65 s is (b). The thing named in the request, and the thing wired here, is
(c)** — recorded at ~190× that figure before this lane started, and re-measured
below at ~218×. Candidate (b) was never built and is still not built.

This was declared in the PREREG as a fact known at freeze time rather than
predicted, so the prereg cannot take credit for discovering it. **The wiring
proceeded anyway**, and that is the right call: the user approved
`debug_lane.sh` by name, and the decision they were asked for was a *policy*
decision — should a debug panic block a merge — not a cost decision. But a lane
that shipped a 142 s row against an 0.65 s authorisation without saying so would
be misreporting the price of the thing it built, which is this repo's own house
rule (`a figure carries the commit it was measured at`) failing at the moment it
matters.

## 2. Why the row exists at all, stated as the fault it catches

Every other row in `scripts/gate.sh` grades a `--release` binary. In a release
build `debug_assert!` is **compiled out** and integer overflow **wraps
silently**. So the entire verification apparatus — 18 mode lanes, the 19,556-case
generated sweep, the 90,812-cell mode cross, the 878-TU workload scan,
`scripts/status.sh`, the workspace test row — is *structurally incapable* of
reporting either fault.

That is not theoretical. Board **#3074**: the port's own emitter carried a
**FALSE** `debug_assert` for four days and every gate run in the window was
green, because no instrument could execute it. **0 of the 75 `debug_assert` sites
under `crates/`** were reachable by anything standing. The dev profile's
`overflow-checks` then found a `usize` underflow in `gap/fnbytes.rs` on the
instrument's first run.

`hatch-red` and `ladder-red` are the precedent for a gate row that grades an
instrument. This row is the precedent for a gate row that varies the **profile**,
which is the one axis nothing else here varies.

defect family (*absence read as success*, ~15 recorded instances) wearing the
face of the instrument built to stop it. So the row was not asserted to work. A

arithmetic underflow in `crates/c2-harness/src/gap/fnbytes.rs` — the exact class
#3074 is about), the gate was run, and the injection was reverted (`4dde6627`).

### Is it insurance? — the question answered in the terms it was approved on

The row was approved on the argument that it is **cheap insurance**. Both halves
of that are now measured rather than assumed, and they must be read together:

* **It is insurance.** The policy pays: a real fault of the class it exists for
  turned the gate **red**, at exit 1, with a message that names the lane, the
  file and the line — while every other row in the gate stayed green over the
  identical tree. Had the injection failed to redden the gate, this lane's
  `Outcome:` would read **`FAILED`** and the row would have been a net negative,
  because a gate row that cannot fire is worse than no row at all. It fired.
* **It is cheap, but "cheap" is 96 s and not 0.65 s.** §5. The figure the
  approval was quoted against was a different candidate's, by ~150×. At **+7.5 %
  of the gate's total** the honest word is *affordable*, not *free* — and the
  free one (candidate (b), still unbuilt) is in §10 item 1.

Both statements are needed. Either alone misrepresents what was bought.

## 4. THE SKIP PATH, verified live and not by reading the code

CLAUDE.md requires the toolchain-absent path to degrade cleanly, and the portable
lane has no toolchain BY DESIGN. The row is toolchain-**bound** — unlike
`hatch-red` / `ladder-red`, it drives `c2rs gap` against the real `c2.dll` — so
it is under the all-skip rule with the sweep and the cross. Checked by hiding the
toolchain with an env override, both directions:

```
$ C2RS_COMPILERS=/nonexistent/compilers C2RS_WIBO=/nonexistent/wibo \
  C2RS_CL_EXE=/nonexistent/cl.exe C2RS_C2_DLL=/nonexistent/c2.dll \
  scripts/gate.sh --jobs 8
EXIT=0
debug-lane           SKIP            0/18          0         0  DEBUG-profile lanes (0 graded, 0 panic)   <- toolchain absent
GATE: SKIPPED — all 18 lanes, the sweep, the cross and the debug row skipped,
  NOTHING WAS GRADED.

$ ...same env... scripts/gate.sh --jobs 8 --require-graded
EXIT=1
GATE: FAIL (NOTHING GRADED) — you asked for a graded run and got 0.
debug-lane           SKIP            0/18          0         0  ...   <- toolchain absent
```

**SKIP, not FAIL; exit 0 without the demand and exit 1 with it.** Nothing about
the documented exit-code contract moves. Two further rules make the skip
*honest* rather than merely quiet, and both are asserted in `--selftest`:

* all lanes skipped and the debug row **ran** ⇒ `GATE: FAIL — all 18 lanes
  skipped but debug-lane reported PASS`. One part resolving a toolchain another
  could not is a fault in the resolution, not a degradation.
* the lanes graded and the debug row **skipped** ⇒ `GATE: FAIL — N lanes graded a
  corpus and debug-lane skipped`. That is the row silently not running, which is
  precisely what wiring it in was for.

## 5. THE COST, re-measured here

Measured in this worktree at `4dde6627`. **The box was carrying three peer lanes
throughout** (load average 59–91, up to 7 concurrent `gate.sh` processes), so
every wall-clock below is quoted with the load it was taken at and the spread is
reported rather than averaged away.

| measurement | result | load |
|---|---|---|
| `debug_lane.sh` **warm**, 18 lanes, `C2RS_JOBS=16` | **162 s** | 65 |
| the same, again | **142 s** | 59 |
| the same, from a deleted `target/debug` | **125 s** | 66 |
| the debug **build alone**, warm | **0 s** (nothing to do) | — |
| the debug **build alone**, cold (all 5 crates) | **13 s** | 66 |

**Warm ≈ 142 s (spread 125–162 s). Cold ≈ warm + 13 s.** The cold/warm delta is
*only* the build, and it is 13 s because `CLAUDE.md`'s std-only,
zero-external-crates rule means there is no dependency graph to compile — the
same unbudgeted dividend `2026-08-14-dbgassert.md` P6 identified.

**Note the ordering in that table: the "cold" run came in FASTER than both warm
runs.** The build delta is 13 s and the run-to-run spread from peer load is 37 s,
so on a contended box the load term dominates the thing being measured. That is
reported rather than hidden, and it is why the gate totals below are decomposed
by leg instead of compared as two totals.

### The gate's total, before and after

Two full totals taken an hour apart on a box whose load moved 59→91 would not be
attributable to the change. So the delta is taken **inside one run**, from the
gate's own per-leg timings, which is exact by construction:

One full green run, `scripts/gate.sh --jobs 4 --require-graded`, at `4dde6627`,
box load ~66–86 throughout:

| leg | seconds | share |
|---|---|---|
| 18 mode lanes | **13** | 1.0 % |
| generated sweep (19,556 cases) | **747** | 54.6 % |
| mode cross (90,812 cells) | **496** | 36.3 % |
| **debug lane (NEW)** | **96** | **7.0 %** |
| overhead (builds, reap, hashes) | 16 | 1.2 % |
| **TOTAL AFTER** | **1,368 s** | |
| **TOTAL BEFORE** = total − the new leg | **1,272 s** | |

**So: 1,272 s → 1,368 s, +96 s, +7.5 %.** That decomposition is exact for this
run by construction — the row is appended after the cross, runs sequentially,
shares no work with any other row, and §7 shows it moves no other row's counts —
and it is far more trustworthy than two totals taken an hour apart on a box whose
load moved 59→91 in that window. A separate pre-wiring run was attempted and is
*not* quoted: it was killed mid-cross after 45 minutes at load 86, and even
completed it would have been a different box.

**P10 was WRONG, and comfortably so.** The prereg registered *"the added row is
the single largest line item in the gate"* at p = 0.45. It is the **third**
largest of four, at 7 % of the run — the sweep alone is nearly eight times
bigger. On the handed-down `--jobs 16` idle-box figures (gate 105 s, sweep 82 s)
the row would be the largest, and that is the arithmetic I had in mind; at
`--jobs 4` on a loaded box, the sweep and the cross swamp it. **The row is
cheaper, relative to what the gate already costs, than the lane predicted.**

## 7. The discriminating evidence — the row is ADDITIVE

`scripts/` is in `GRADED_DIRS` (`crates fixtures scripts`), so **the graded tree
hash MOVES by construction** and that is expected, not a defect. #3215's
"identical at both ends" check applies to revert-everything lanes; this lane
deliberately lands a `scripts/` change, so the hash moving is the correct
outcome and is not quoted as evidence either way. The evidence is instead:

1. **Per-lane counts identical, all 18 lanes.** Taken from a sampled run at
   `d8a2f562` (pre-wiring) and from the debug row's own per-lane lines at
   `4dde6627` — `graded/total` and `match` digit for digit on every lane:
   `O1 179 · O1-EHsc 180 · O1-Oi 181 · O1-Oi-EHsc 182 · Ox 150 · Ox-EHsc 150 ·
   Ox-Gy 150 · Ox-Gy-EHsc 150 · O2 156 · O2-EHsc 156 · Od 18 · Od-EHsc 18 ·
   O1-Oi-GR 181 · O1-Oi-EHsc-GR 182 · Ox-GR 150 · Ox-EHsc-GR 150 · Od-GR 18 ·
   Od-EHsc-GR 18`, all at `381/381`, `mismatch 0`.
2. **That same list is the cross-profile identity check the row buys for free.**
   The 18 numbers above are the DEBUG run's; they equal the release lanes' 18
   numbers exactly. A debug run that graded differently would be a fault in its
   own right, and now it is one the gate reports.
3. **Release binary sha256 unchanged.**
   `fc492ecf7aa73ad59f4170e53502e0c5452a4d39ea9a924265f6ed8dd25ddda4` at both
   ends. `git diff 7e541a54 -- crates/` is empty, so this is expected — and it is
   worth stating *why it is the load-bearing fact*: the scan below is a pure
   function of that binary and the workload inputs, so a byte-identical binary
   means the base scan and the tip scan are **the same program over the same
   inputs**, and the diff is a determinism check as much as a change check.
4. **878-TU scan identity diff: 0 deltas over all 394 anchored keys.**
   ```
   base 394 keys, tip 394 keys
   vanished 0
   appeared 0
   changed  0
   ```
   And the whole report body with it: **1,920 normalized lines identical**, the
   only surviving differences being the capture-cache hit/miss counters
   (`870 hit, 8 miss` vs `0 hit, 878 miss` — a property of the *run*, not of the
   tree) and the parallel scan's per-TU completion ORDER, which is why
   `keydiff.py` exists and why a raw `diff` of two scan logs (1,738 lines here)
   is the wrong instrument.
5. **`--require-graded`'s printed unit sum does not move.** The row grades the
   same fixtures the lanes already counted, so folding it into that sum would
   double-count them. It is deliberately excluded, and `--selftest` asserts the
   printed `graded:` line reads the lanes' own number (`394` for the two-lane
   fabricated registry) and not the lanes' plus the row's.

## 8. What the row does NOT establish

Stated because a row quoted as more than it is becomes worse than no row.

* **It covers the profile axis for the FIXTURE corpus only.** The generated
  sweep, the mode cross and the 878-TU workload scan remain release-only. A false
  `debug_assert` or an overflow reachable only from a generated case or a workload
  TU is still invisible to every standing instrument.
* **It is not a byte judge and does not replace one.** `mismatch` is still graded
  against real `c2` by the release rows. What this adds is the two faults a
  release build cannot express.
* **It says nothing about the 9 assertions the debug test suite already misses.**
  `2026-08-14-dbgassert.md` P3c measured the debug `cargo test` suite reaching
  88 % (66 of 75) of the assertion population, with the 9 misses concentrated in
  one emitter. This row raises coverage by executing the emitter over 381
  fixtures × 18 lanes, but it does not *measure* which of the 9 it now reaches —
  that is a separate instrument and it is in §10.

## 9. Board rows — left UNNUMBERED, deliberately

`docs/BOARD.md`'s live pointer is `w-guards`' block: *"`#3214`–`#3217` MINTED
HERE. **THE NEXT FREE NUMBER IS `#3218`, AND NO LANE IS IN FLIGHT.**"* That last

## 10. Found and not taken

1. **Candidate (b) — the debug UNIT row — is still not built, and it is the
   0.65 s the request was authorised against.** `cargo test --workspace --lib` in
   the dev profile: **0.65 s warm / 6 s cold, 1,386 tests, and NO TOOLCHAIN**, so
   it runs in the portable lane where nothing else can grade an assertion at all.
   `2026-08-14-dbgassert.md` recommended taking it *unconditionally* and it was
   not taken. It is ~220× cheaper than the row this lane wired, it is the only
   assertion check that would work on a box with no `compilers/`, and it catches
   #3074 (though not the `gap/fnbytes.rs` overflow, which no unit test reaches).
   **Not taken here** because the request named `debug_lane.sh` specifically and
   a lane that widens its own mandate on a shared gate is how the gate acquires
   rows nobody decided on. It is the cheapest remaining item on this board.
2. **The 878-TU scan and the generated sweep are release-only** (§8). The scan is
   the instrument the project's headline numbers come from and it cannot execute
   an assertion. A debug scan is ~1 line of wiring and an unmeasured amount of
   wall clock; the honest size is unknown because nobody has run one.
3. **`hatch-red` reports `REFUSED HATCH-STALE` in every run this lane took**, on
   an untouched tree — board **#1389**, live, pre-existing, and not caused here.
   It means `hatch.py apply` cannot hatch the current tree, so 14 arms of a
   standing gate row have not executed for as long as that has been true. The row
   correctly forfeits the unqualified headline (`GATE: PASS (HATCH-RED
   REFUSED)`), so this is legible rather than silent — but a row that has been
   `REFUSED` for an unknown number of days is a row that is not running, and
   nothing measures how long. **That is the same shape this lane was dispatched
   to fix, one row over.**
4. **`debug_lane.sh`'s header claims it uses `scripts/harness_bin.sh` and it does
   not** — it does a plain `cp` of `target/debug/c2rs` into its run dir. The
   effect (a run-private pinned copy) is the same and the comment's claim about
   *which mechanism* achieves it is wrong. One line to fix; not taken, because a
   comment correction inside the file this lane is wiring would be
   indistinguishable in the diff from the wiring itself.
5. **The debug row's 381 fixtures × 18 lanes is 6,858 gradings for a
   panic-detection job**, and a panic is a property of the code path, not of the
   lane. If the 18 lanes reach the same assertion set — which the identical
   per-lane `match` numbers hint at but do not establish — most of the 142 s is
   redundant for THIS row's purpose. Measuring assertion-site coverage per lane
   would price a cheaper row; that is candidate (b)'s question asked properly, and
   it is item 1.
