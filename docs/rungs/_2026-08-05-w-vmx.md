**One-line answer:** *VMX128 is **0.344 % of the workload** — 3 TUs, 7
functions, 113 instruction words of 3,866,911 — so a code generator for it is
three orders of magnitude below the cheapest thing on the board; what the
project actually needed was the ability to **read** the instructions, and that
now exists and is verified 6,701/6,701 against `cl`'s own `/FAcs` listing.*

---

## 1. The headline numbers, in the order they were earned

1. **The oracle is the compiler.** `cl /FAcs` prints the exact instruction word
   beside Microsoft's own mnemonic and operands. That closes the brief's central
   trap by construction: no decode is reported as correct unless the thing that
   emitted the bytes agrees. **6,701 of 6,701** in-scope instructions VERIFIED
   across six listings, **0 MISMATCH, 0 UNRECOGNIZED**, **66 of 77** opcode rows
   exercised against the real compiler.
2. **Prevalence: 3 TUs of 878 (0.344 %), 7 functions of 217,878, 113
   instruction words of 3,866,911 (0.0029 %).** Recommendation: **do not build
   VMX128 codegen.** §4.
3. **The collision table is measured, not asserted.** 616 register-varied
   encodings through the real `llvm-mc` 22.1.8: **177 silently mis-decoded with
   no diagnostic (28.7 %)**, 439 refused, **0 correct**. On the 113 real
   workload instructions: **64 silent, 49 refused, 0 correct.**
4. **The split is structural**, and it is the useful form of the answer:
   primary opcode **5 is safe** (llvm-mc refuses all 25 rows), primary **4** is
   dangerous in 16 of 17 rows, primary **6** is dangerous in **35 of 35** and
   every one of them decodes as Power10 `lxvp`/`stxvp`.
5. **Grading the community table against the real compiler found three errors
   in it** — four mnemonics spelled differently by Microsoft, one operand
   reading the wrong bit-field, one printing three operands where the
   instruction has two. §3.
6. **An LLVM patch is possible and is priced at ~1,200–1,500 lines / 1–2
   lane-days**, against `tools/llvm/ppcbe.patch`'s 89. Declined, with a ~30-line
   alternative that gets the same benefit without touching LLVM.
   `docs/VMX128_DECODE.md` §8.

## 2. The failure the brief named, reproduced — and then found in our own code

The brief's premise is that VMX128 fails **silently** in `llvm-mc`. Confirmed
exactly, and sharpened: LLVM is not merely often wrong, it is **never right** on
VMX128, and it announces only 43 % of its errors.

The instructive part is that the same failure appeared **in this lane's own
decoder, on its first run**. `isa.yaml` carries the Gekko/Broadway
`PairedSingles` extension in the same primary opcode 4, and `ps_sel` is
*literally the same 32 bits* as AltiVec `vmaddfp`. So `vmx128.py` printed

    0x114a4aee  ->  ps_sel fr10,fr10,fr11,fr9

for a real dc3 workload word that `cl`'s own listing calls
`vmaddfp vr10,vr10,vr11,vr9`. Plausible, legal, wrong, no diagnostic — the
identical shape, in the tool built to detect the shape. The oracle caught it in
the first minute; a "did it decode?" check never would have. Hence
`vmx128.XENON_PROFILE`, and hence the four-verdict counting in `vmxcheck.py`.

**The generalizing point, and it is the same one the coordinator raised
mid-lane about the sibling-worktree bar** (a truncated `cargo test` reports
*fewer targets AND fewer passes*, so it reads as a normal smaller passing run):
a wrong answer that looks like a smaller right answer is invisible to any check
that does not print its own denominator. `vmxcheck.py` prints four counts and
**exits non-zero when it verifies zero**; `vmxscan.py` fails on any
opcode-4/5/6 word it could not place. That is the countermeasure, and it is
cheap.

## 3. What grading against the real compiler bought

Three corrections to `encounter/powerpc-rs`' `isa.yaml`, all surfaced as
`MISMATCH` / `MNEMONIC-ONLY` on real compiler output:

| # | correction | evidence |
|---|---|---|
| 1 | `vctsxs128`/`vctuxs128`/`vcfsx128`/`vcfux128` are spelled **`vcfpsxws128`/`vcfpuxws128`/`vcsxwfp128`/`vcuxwfp128`** by Microsoft | 4 mismatches each, identical encodings |
| 2 | **`vupkd3d128`'s third operand is `D3DType` (bits 11..13), not `vuimm` (11..15)** | `0x1be40ff4`: `vuimm` reads 4, `cl` prints `1<NORMSHORT2>`. Verified over all 8 `D3DType` values, whose names `cl` also supplies |
| 3 | `vspltisw128` prints **two** operands, not three | `vspltisw128 vr63,3` for `0x1be30774` |

And two facts about the *compiler* that no ISA table contains:

* **Intrinsic arity comes from `C4392`** — a wrong declaration is answered with
  the arity `cl` expects. Every row of `genprobe.py:ARITY_OVERRIDE` is read off
  one.
* **The `128` suffix is register pressure, not a different operation.** At two
  live vectors `cl` emits plain `lvsl` and `vmaddfp`; the `128` forms appear
  only when the allocator needs a register above `vr31`. A probe without
  pressure cannot reach ~20 of the 77 rows **and would report their absence as
  coverage**. `genprobe.py --pressure 40` is the fix, and it took the verified
  row count from 14 to 60.

## 4. Prevalence, and the recommendation

871 of 878 workload TUs compile at the workload's own flags (the 7 that do not
are `soundtouch/**` and two `FxSend*360.cpp` — x86/SSE/3DNow sources that never
built for this target).

| | | |
|---|---:|---|
| TUs with ≥1 VMX128 instruction | **3** | 0.344 % |
| functions with ≥1 VMX128 | **7** | of 217,878 |
| VMX128 instruction words | **113** | 0.0029 % of 3,866,911 |
| plain AltiVec words | 36 | |
| AltiVec load/store under opcode 31 | **0** | stated, not omitted |
| distinct VMX128 opcodes used | **8** | of 77 |

`FFT.cpp` 96, `Skeleton.cpp` 15, `JointUtl.cpp` 2. `lvx128` + `stvx128` are
**57 of 113** and come from plain `__vector4` pointer loads/stores, not from an
intrinsic.

**Recommendation: do not build VMX128 codegen** — `docs/VMX128_DECODE.md` §7,
with §7.1 stating in advance what would change it. Three TUs does not pay for a
third register file, its save/restore helper pairs and its label-slot
consequences, when `#160` is worth 871 TUs and `#302` is worth 91.

**The census trap is respected.** `docs/` memory records that a census is a
driver, not a target. 0.344 % is a **ceiling on what VMX128 codegen could ever
unblock**, not a claim that it would unblock them: all three TUs are outside the
current match set for other reasons, and none was checked for a second blocker.
The number is also **workload-scoped** — dc3's engine does its vector math in
scalar floats, which is a property of Milo and not of the platform.

## 5. Things that refute or correct a premise

1. **`docs/PRIOR_ART.md` §3.2's `lvx128` → `vucmprlb` pairing is now
   VERIFIED.** `rungs/_2026-08-04-w-llvm.md` records that lane as unable to
   reproduce it — *"I did not construct a verified `lvx128` encoding, so that
   one mnemonic is unverified here, not refuted."* It reproduces exactly:
   `0x102320c3` is `lvx128 vr1,r3,r4` in `cl`'s own listing (the `__lvx` thunk
   in `FFT.cod`) and `vucmprlb 1, 3, 4` in `llvm-mc`, silently. PRIOR_ART was
   right. **`docs/ABI_EDGES.md:300`'s "a tooling gap to close before any VMX
   rung" is closed.**
2. **The brief calls the collision table "the list of ways this tooling lies",
   and the *exact* computation almost tells the opposite story.** Computed over
   all 77 × 178 pairs, **VMX128 and AltiVec proper are disjoint — zero
   colliding pairs**, and the only exact collision in `isa.yaml` is
   `vsldoi128` against 17 Gekko rows that do not exist on Xenon. A lane that
   reported only that half would have published a false all-clear. The real
   collisions are with **Power10**, which `isa.yaml` does not carry at all —
   they exist only in LLVM and are therefore only findable by *measuring LLVM*.
   Both halves are reported for that reason.
3. **The `dc3` VMX128 count is 113, not 149.** An early raw histogram of
   primary opcodes 4/5/6 gives 149; 36 of those are plain AltiVec (`vor`,
   `vmaddfp`, `vnmsubfp`, `vperm`) sharing primary opcode 4. Anyone re-deriving
   this from an opcode histogram will get 149 and should not.
4. **The brief's setup command put the worktree in the wrong place**, which the
   coordinator caught mid-lane: a sibling worktree trips
   `provenance.rs:481`'s `root.starts_with(&main)` and truncates
   `cargo test --workspace --release` to 2 targets / 159 passes — *fewer targets
   and fewer passes*, so it reads as a smaller passing run. The worktree was
   moved to `.claude/worktrees/wt-w-vmx` and the bar re-run there: **799 passed
   / 0 FAILED / 27 targets**. No result was taken from the sibling path.

## 6. What was deliberately not taken, priced

| not taken | why | price |
|---|---|---|
| **VMX128 codegen in `c2-core`** | 3 TUs; and the scope limit forbids `crates/` this session anyway | a third register file + save/restore helpers + label-slot rules; §4 |
| **An LLVM VMX128 disassembler patch** | `vmx128.py` already decodes all 77 rows correctly. The patch buys inline vector text in `llvm-objdump -d` and nothing else | **~1,200–1,500 added lines, 1–2 lane-days**, incl. predicating 51 colliding Power10 rows so `FixedLenDecoderEmitter` does not reject the table. `docs/VMX128_DECODE.md` §8 |
| **Annotating `llvm-objdump -d` output** | wanted, but nobody needs it this session | **~30 lines**: re-decode every opcode-4/5/6 word with `vmx128.py` and overwrite the line. Priced in §8.3 |
| **Wiring `vmxcheck.py` into `scripts/gate.sh`** | `scripts/` is w-ledger's seam, and memory records that `gate.sh` cannot see `expr_sweep` — adding a check the gate does not run would repeat the recorded failure rather than avoid it | one row in `scripts/lanes.txt`; the `SKIP` paths already exist |
| **Fixing `isa.yaml` upstream** | it is a third-party repo and the corrections are recorded here with their evidence | a PR |
| **The 11 unexercised opcode rows** | this compiler exposes no intrinsic name for the LRU loads/stores, and preferred plain AltiVec for three of the three-operand forms even at 40 live vectors | they are reported as **unverified, not assumed correct**, on every `vmxcheck.py` run |

## 7. Reproducing this

```sh
tools/vmx/build_objs.sh                        # 878 TUs, ~30 s, ~102 MB
tools/vmx/vmxscan.py work/w-vmx/objs           # §4
tools/vmx/listing.sh src/system/synth_xbox/FFT.cpp work/w-vmx/lst/fft
tools/vmx/genprobe.py --pressure 40 > work/w-vmx/probe2/probe2.cpp
tools/vmx/listing.sh "$PWD/work/w-vmx/probe2/probe2.cpp" work/w-vmx/probe2
tools/vmx/vmxcheck.py --llvm  work/w-vmx/lst/*/*.cod work/w-vmx/probe*/*.cod
tools/vmx/vmxcheck.py --selftest work/w-vmx/lst/*/*.cod
tools/vmx/collide.py
```
