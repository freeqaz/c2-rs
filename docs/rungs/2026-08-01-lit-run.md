Found while refuting the nine "one function from byte-exact" TUs
(`docs/GAPS.md` §9): it is the **first** of the three independent refusals
between the port and `src/xdk/nuispeech/xboxheap.cpp`'s constructor, and the
only one of the three that is a private limit rather than a phase.

## What it admits, and what it refuses

W38 (`docs/rungs/2026-07-31-store-run.md`) gave the store leaf a statement list
and refused **any** literal value in a run of more than one:

```rust
if stmts.len() > 1 && stmts.iter().any(|s| s.value_is_lit) { return None; }
```

That gate was right, and its own doc says why: with two or more **distinct**
literal values c2 hoists the `li`s, allocates r11/r10/r9 by some rule, CSEs equal
values, and *reorders the stores*. This rung does not lift it. It carves out the
**degenerate case where the rule cannot matter** — every statement stores the
*same* literal, so there is one materialization, one register, one live range,
nothing to allocate and nothing to schedule.

Admitted (MEASURED before anything was written, `/O1` and `/Ox` byte-identical):

```text
  { a=9; b=9; c=9; }                39600009 91630000 91630004 91630008
  { a=9; …5 stores… }               one `li`, five `stw`
  { a=7; …6 stores… }               one `li`, six  `stw`
  { a=0; b=0; }                     39600000 91630000 91630004
  { c=1; h=1; i=1; }   MIXED width  39600001 99630000 b1630002 91630004
  { c=0; h=0; i=0; q=0; }           …plus f9630008
  { s->a=3; t->b=3; s->c=3; }       39600003 91630000 91640004 91630008   TWO bases
  { a=100000; b=100000; } WIDE lit  3d600001 616b86a0 91630000 91630004
  { t->r.a=4; t->r.b=4; t->z=4; }   nested sub-object offsets (W35's walk)
```

The `lis`+`ori` pair for a wide literal hoists **whole**, ahead of every store —
so the region is not bounded by the 16-bit `li` field, only by `emit_load_imm`'s
own existing refusal of wide negatives.

## Why the boundary is at ONE value and not at three

Four allocation rules were fitted to the two-and-three-value grid and **each is
refuted by another member of it**. The grid is `wlr_lit_run_neg.cpp`:

```text
  { a=1; b=2; c=3; d=1; }        1->r11 2->r10 3->r9    first-use order
  { a=1; b=2; c=3; d=2; e=1; }   1->r10 2->r11 3->r9    PERMUTED
  { a=1; b=2; c=1; d=2; }        1->r10 2->r11          PERMUTED
  { a=1; b=2; c=1; d=2; e=1; }   1->r11 2->r10          back to first-use
  { a=1; b=2; c=3; d=1; e=2; f=3; }  1->r9 2->r10 3->r11  REVERSED
  { a=1; b=1; c=2; d=2; e=2; }   2->r11 1->r10, and the STORES come back
                                 2,0,1,3,4 — not source order at all
  { a=1; b=2; c=3; d=4; }        FOUR values into three registers: r11 is
                                 recycled and a store is hoisted between the
                                 `li`s to free it
```

*use count* is refuted by row 1, *live-range length* by row 2, *last use* by the
`{1,2,3,3,3}` neighbour, *first use* by rows 2/3/5. `GAPS.md` §6 instance #10 —
measure at the edge, do not fit the scheduler. The mixed literal/formal run is
refused for the same reason and a second one: at length 2 the two statements come
back in the **opposite** order to the source, and the position of the literal
store across lengths 2–6 is a two-queue schedule with a ready-time, which is a
fitted model with no mechanism.

## Estimate vs outcome

No estimate was registered for this rung, and that is worth stating plainly
rather than back-filling one: it was not on the plan. The pre-registered estimate
in this session (`docs/GAPS.md` §9.1) was about **TU conversions**, and it said
**0 of 9**. That estimate was exact — TU match is 6 before and 6 after.

The realized census is **+5,796 bodies**, of which **+86 are emitted functions**.
That ratio — 1.5 % — is the rung's most useful output and it is a warning to
whatever reads it next: a body-census rung of this shape buys almost nothing on
the metric `ROADMAP.md` §8.2 now steers by. A zero-initializing constructor
whose body is only stores is overwhelmingly a header inline that c2 never emits
standalone.

## The live wrong-bytes emit this rung's sweep fragment found

**`emit_load_imm` emitted a redundant `ori dest,dest,0` for every wide literal
whose low half is zero, and had done since it was written.** c2 emits `lis`
alone. MEASURED (`/O1` and `/Ox` identical):

```text
  s->a = 65536;      3d600001                    lis r11,1        <- port emitted
                                                                     3d600001 616b0000
  s->a = 131072;     3d600002                    lis r11,2
  s->a = 65535;      3d600000 616bffff           the HIGH half is emitted even when
                                                 zero — the elision is one-sided
```

Three things about it are worth more than the fix, which is one `if`:

* **It is not this rung's defect.** The smallest failing case is
  `void f(S* s){ s->a = 65536; }` — a run of **one**, the path WLR explicitly
  leaves alone (`func.ops.len() > 3`). Proven by stashing the two crate changes
  and re-grading: `Port=Mismatch @ offset 8` on the pre-WLR tree.
* **Nothing in the existing corpus varied a literal's low half.** 91 fixtures,
  12 mode lanes, 14,122 generated cases and 878 real TUs were all green over it.
  `docs/ROADMAP.md` §6n's "generated sweep axes found six live wrong-bytes emits;
  hand-written fixtures found none" now reads seven, and the new one has the same
  shape as the other six: it varies a value, not an operator and not a shape, so
  it is invisible to review.
* **It was reachable from every literal path in the port**, not just stores —
  `emit_load_imm` is the one locator for a materialized constant. The store run
  is only where the sweep happened to look.

Pinned by `wlr_lit_run.cpp`'s `kz1`/`kz2`/`kz3`/`kn2` (the run of one included,
deliberately, beside the runs) and by `84-lit-run.py` case 1's value axis, which
crosses `{0, ±1, 7, ±32767/32768, 65535, 65536, 100000, 2147483647}` with run
lengths 1..7.

## Found and not taken

* **The multi-value literal run** — refused above, and the refusal is the
  finding. Taking it needs a *designed, enumerated* allocation grid over
  (statement count × distinct values × repetition pattern), not more of the
  ad-hoc one in the negative fixture. Same category as `ROADMAP.md` §8.3's
  Phase 4 note: a fitted hypothesis with no mechanism.
* **The mixed literal/formal run**, which is the larger population and where
  `expr-op-0x27`'s store residue mostly sits. It is a scheduler, and it is the
  next thing anyone widening this file will reach.
* **The two rungs behind this one on `xboxheap.cpp`** (`docs/GAPS.md` §9.4): a
  local reference bound to an interior sub-object address, and a framed member
  call on `this` inside a statement list. Neither is a private limit; the second
  is Phase 4.
