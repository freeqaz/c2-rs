## 3. THE RESIDUE IS DECIDED, AND DECIDING IT FOUND TWO OPCODES

All **457** P desyncs land on `0x59` (446) or `0x08` (11), bytes outside the
judging vocabulary because `operand()` has no arm for them — `08` being one of
the six that file lists as **deliberately unwitnessed** and refuses on purpose.
So there are two readings and they are not the same claim:

* **G — an instrument GAP.** `59` and `08` are ordinary unpinned opcodes; `4C` is
  payload-free and `LEGAL_OPEN` is incomplete.
* **W — a real WIDTH.** The call-end carries a payload at least at these sites.

`work/w-4c/unwit.py` separates them with **a question that never mentions
`4C`**: does the byte occur at a token start that is *not* preceded by a `4C`?
The walk **breaks** at `4C`, so every position it reports was reached by
stepping some other token's width.

```text
  op      reached   after a 4C   NOT after a 4C
  0x59       6031            0             6031
  0x08       3819            0             3819
  0x07          2            0                2
  0x14          1            0                1
  0x25          1            0                1
```

**Zero after a `4C`, at 9,850 sites.** G, decisively. The predecessors are
`03`/`02`/`04`/`05` for `59` and `B9`/`30`/`2C` for `08`, and 2,265 of the `59`s
sit inside a call whose return TYPE is `86 45 40` — `float`. Both are float-side
operators this tree has never pinned.

**`LEGAL_OPEN` was NOT widened to make P look better, and that is the point.**
`w-bd` widened it once mid-lane for the `5C`/`5D`/`5E` family and recorded doing
so. Here the bytes are ones `operand()` refuses **deliberately**, so adding them
would be the guess the whole table exists to prevent. They go on the explicit
unpinned list instead, with a test — together with `0x07`, `0x14` and `0x25`,
which the same walk witnesses at token starts. **`0x14` is the byte
`control_flow.rs` carries as its named unresolved entry**; this is a witness that
it OCCURS, and no evidence at all about its width.

So on the argument-bearing population the desync attributable to this reading is
**0 of 1,978,436**.

## 4. What this does NOT settle

* **Decoding is not accepting.** The chain sink pushes no `IlOp` and poisons any
  walk that used it (`expr-chain-sink-poison`); `mismatch` is 0 at both ends and
  `IlBundle::functions()` is untouched. A ladder row reading READER-CLEAR means
  *the decoder walks this TU's bodies end to end with 11–12 sink grants*, not
  that the port accepts them.
* **`4C` is a closing BRACKET and this table is width-only.** A chain walk that
  steps past a `4C` is not thereby matching brackets, and nothing here gives the
  sink any notion of call nesting.
* **The NEST population is scored and NOT relied on.** Reaching a nested call's
  outer `4C` requires stepping over the inner one, i.e. assuming P. It reads
  **0 / 313,553** and is labelled circular in the instrument, in the commit and
  here.
* **The `NOARG` family is a different construct.** 160,539 sites whose region has
  no `55` at all — the by-value-return `9B`/`2C`/`64` shape. It reads 2 desyncs
  of 160,539 and is reported separately rather than folded into the claim.

### 4.1 The shared-semantics hazard, checked in both directions

The lane brief's standing caution is that `chain_skip_form` is read by the
completeness walk, the census and the blocking histogram, so widening it changes
what all three count — *report it as a measured delta, not as a surprise at
merge.* Measured, at both ends:

* **Sink OFF (every gate lane, every default scan, every published metric):**
  **nothing moves.** 187 of 187 `gap-metric` lines byte-identical, 0 of 671
  `fn_blockers` and 0 of 648 `emit_blockers` keys moved with both sums identical
  to the unit, `peerkeys.py` 0 families vanished, TU classes identical. This is
  structural rather than lucky — `C2RS_SINK_CHAIN` defaults off and the sink
  pushes no `IlOp`.
* **Sink ON:** it moves a great deal, and §5 names **every one of the 33 keys**
  with both numbers, with the total pinned identical to the unit so the movement
  is provably a relabelling.

**And board #139's rule — a measure's acceptance vocabulary must match its
emitter's — does not bind this change, for a reason worth stating rather than
skipping.** The shipped diff adds no acceptance vocabulary at all: it is one
*width*, in a table that is width-only, inside a sink that cannot reach
`select_function`. The rule *did* bind this lane's **instrument**, and it was
applied there: anchor B admits a `55 <TYPE>` at exactly
`readers.rs::eat_int_like_or_ptr4`, which is the gate
`shapes::calls::eat_call_args` applies at that same position — not a hand list.

## 7. Two instrument defects found on the way, one of them loud

### 7.1 `c2rs gap --cache <RELATIVE dir>` turns a `match` into a `mismatch`

This produced a `SCANFAIL` and a **`CORRECTNESS SIGNAL: 1 mismatching TU`** on
`xboxheap.cpp` in the first tip ladder run. On this project that is an alarm, not
a gap, and it was chased to the bottom before anything else.

**It is pre-existing.** `git checkout 2b1c89da -- expr.rs`, rebuild, re-grade:
the **base** binary reproduces it. Same binary, same entry, same flags, same
cwd; only the spelling of `--cache` moves:

```text
  --cache work/w-4c/cache        ->  [1/1] mismatch  (bytes diverge)     twice
  --cache $PWD/work/w-4c/cache   ->  [1/1] match
```

**Mechanism, read off the bytes.** A cache entry stores the captured IL *and the
reference obj*, and a COFF obj records its own `-Fo` output path. `strings` on
the two objs differs by **exactly one line**:

```text
  fresh compile  1169 B   Z:\tmp\c2rs-cli-compile-…\out.obj
  cached entry   1209 B   Z:\home\…\work\w-4c\cache\<hash>\out.obj
```

**Why nobody saw it, and it is not that nobody looked.** The cached IL is
**byte-identical** to a fresh capture — all five files — so every `fn_blockers`
number ever read through the cache is sound and no ladder rung count is affected.
Only a `match` TU has its obj compared at all, and every ladder TU was a
`vocab-gap` until `w-lineage` converted `xboxheap.cpp` (board **#1381**). A cache
MISS is always green, because the reference obj is compiled fresh at that run's
own path and compared against itself. The defect needs a **HIT**.

Both ends of §6 were re-climbed with an absolute cache path, and `xboxheap`
reads READER-CLEAR at both. `work/w-4c/cachebug.txt` has the full transcript.

### 7.2 `work/w-front3/hatch.py` FAILS CLOSED on this master — and that is it working

Both ends of §6 therefore ran with `W_FRONT3_SKIP_HATCH` naming all seven
