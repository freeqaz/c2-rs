**One-line statement:** *`ROADMAP.md` §10.19's `A∧B∧C∧D` was refuted by w-r1c
(conjunction 6, differential 8) and the known-answer control was left red on
purpose. The repair is a **fifth term, E — "at least one registered whole-TU
recognizer accepts this bundle"** — disjoined onto D rather than folded into it,
because **D was never the general form of its own question**: it is the
per-function reading of "does the port have an accepted route to this TU's
contents", and `PortC2` has had two acceptance paths since w-r1c landed.
`A∧B∧C∧(D∨E)` is **8, exactly the match set by name**, the control is green on
its necessary terms with `D 2` and `E 6` still printed as diagnostics, and **not
one of the 878 TUs changed class**.*

---

## 1. What the four factors were a factorization *of*, and where D was wrong

§10.19's four predicates are four questions the port must answer yes to before
its output can be the reference's bytes:

| | question |
|---|---|
| **A** | do the port and the reference agree on **what set of things is emitted**? |
| **B** | can the port **name** everything in that set? |
| **C** | can the port's writer **write the containers** the obj needs? |
| **D** | does the port have an **accepted route to the contents**? |

A/B/C are properties of the obj and the binding. **D is the odd one out and that
is the whole finding**: it is not a property of the obj at all, it is a property
of the port's *acceptance machinery*. `emit-class-complete` is
`emit-emitted == emit-in-class` — the per-function census's verdict, i.e.
"`PortC2`'s per-function path takes every COMDAT here".

§10.19 was measured when `PortC2::build` had exactly **one** acceptance path, so
"the port has a route to the contents" and "the per-function path accepts every
COMDAT" were *the same sentence*. They stopped being the same sentence at
`crates/c2-core/src/lib.rs:204`, where `build` now tries `IlBundle::dyninit_tu()`
**before** `functions()`.

So D was never the general form of question 4. It was the only reading of it that
existed. The fifth term is the other reading:

> **E — whole-TU acceptance.** At least one **registered** whole-TU recognizer
> accepts this bundle.
>
> **The model: a byte-exact obj requires `A ∧ B ∧ C ∧ (D ∨ E)`.**

Neither disjunct is necessary alone, and both are *measured* not to be: D fails
on the two whole-TU matches, **E fails on all six per-function ones**. The
disjunction is what is claimed necessary and what the control is taken over.

## 2. Why this is not "retuning D until the control goes green"

The brief's binding constraint, and four separable commitments answer it. Three
are structural and one is a measurement.

**(a) D's definition is byte-for-byte what it was.** `emit-class-complete` still
means `emit-emitted == emit-in-class` from the per-function census. Nothing in
`c2-il`'s `census.rs` was touched — it is another lane's seam and it did not need
to be. The scan's `census/gate disagreement: 0` line, which is exactly the
symmetry w-r1c declined to break, is **0 on both sides**, and the census is
`706402/2463318` on both sides. Widening D would have meant teaching the
per-function census a whole-TU fact; that is not what happened.

**(b) E reads a different oracle and shares no variable.** D reads the census's
`FnVerdict::in_class()` through the binding. E reads `c2-il`'s recognizer
directly through the registry's own function pointers, in step 1h, from
`captured.bundle`. §10.18 is this file's own record of what a shared reader with
two consumers costs — 865 TUs moved class with nothing red — so this is a
constraint, not fussiness. In particular E does **not** call `bundle.decodes()`,
whose job is a different question (*did anything decode*, the `vocab-gap`
bucket's predicate).

**(c) E is a predicate of the same KIND as D, not "the port emitted it".** D is
class membership for the per-function path, evaluated without running the
emitter. E is class membership for the whole-TU path, also evaluated without
running the emitter. Either "the port emitted it" or the class field would have
been circular and would have made the model unfalsifiable.

The accepted cost of that choice, registered in the prereg before measuring:
**exactly like D, E is not sufficient.** `PortC2::build_dyninit` carries the
`/GF` fence, which lives in `c2-core` and not in the recognizer, so an E-true TU
can still fail to emit. On this workload it never does (§3, D4) — the flags are
`/O1`, which implies `/GF` — but the model would have over-predicted rather than
silently absorbed it, and the printed set-identity line is where that would have
shown.

**(d) D's own violation count is still printed, as a number.** The control block
now reads

```
 known-answer control — matching TUs failing each NECESSARY term (all must be 0,
 over 8 matching TUs): A 0 B 0 C 0 D-or-E 0
   diagnostics, NOT required to be 0 (neither disjunct is necessary alone): D 2 E 6
   D 2 — the per-function census does not model the whole-TU emit path, so §10.19's
   A∧B∧C∧D conjunction stays refuted by these TU(s). That is the finding board #179
   repairs with E, not a defect E hides.
```

Moving a column from "must be 0" to "diagnostic" *is* the move a fitted control
would make to go green. What makes it legitimate here is that the **replacement**
column is strictly narrower than "anything the port emits" — see §3 — and that
the refuted quantity keeps being measured. `factor_abcd_tus()` and the
`A∧B∧C∧D: 6` count are both still printed beside the model's joint, on purpose:
*a refutation whose quantity stops being measured is a claim nobody can
re-check.*

## 3. The degradation argument, which is the actual deliverable

The requirement was: **when a new emit path lands that E does not model, the
control must go red again rather than silently absorb it.**

`WHOLE_TU_RECOGNIZERS` is a **closed, explicit, named registry** in `gap.rs`:

```rust
pub const WHOLE_TU_RECOGNIZERS: &[(&str, fn(&c2_il::IlBundle) -> bool)] =
    &[("dyninit-??__E", |b| b.dyninit_tu().is_some())];
```

A new acceptance arm in `PortC2::build` does **not** enter this table. Adding it
is a separate, deliberate edit in this file. Until that edit happens, a TU
converted by the new path is a `match` with **D false and E false**, the `D∨E`
column goes red, and the printed ALARM names it. That is precisely the event of
2026-08-04, when `dyninit_tu` landed and the `D` column went to 2 — the design
keeps it happening, one term further out.

**The rejected alternative is written into the code's doc comment so it cannot be
quietly adopted later.** The one-liner is

```rust
E := bundle.decodes() && bundle.functions().is_none()
```

It needs no registry and it is wrong for this purpose. `decodes()` is
`functions().is_some() || dyninit_tu().is_some()` and its own doc comment says
*"adding a third path means adding it here"* — so a third recognizer would enter
`decodes()` in `c2-il` and **E would silently absorb it**. That is the open-world
definition, and it makes the control green by construction. The registry is the
closed-world one. That distinction is the entire difference between an instrument
and a rubber stamp.

**No static completeness guard is claimed, and the code says so.** `gap.rs`
cannot enumerate `c2-core`'s match arms, and a test asserting
`decodes() == functions().is_some() || <registry>` would pass **vacuously** on
every bundle that exercises no new path — a green that means nothing, which is
the failure mode this project has now catalogued on eight instruments. The guard
is **empirical and is the scan's own control**, plus one executable
demonstration that it fires:

`the_control_goes_red_for_an_unregistered_whole_tu_path` puts three matching TUs
in one report — one taken by D, one by a registered recognizer (E), one by
neither — and asserts `D∨E` counts exactly the third while A/B/C stay 0 and the
joint stops being the match set. **The match population is grown, not mutated**,
so the red cannot be an artefact of the class filter (the shape §10.19's own
control uses, and the reason it is trustworthy).

Two smaller structural guards: the registry must be non-empty (an empty one makes
E identically false and the control green for the wrong reason) and its names
must be distinct (two entries sharing a name collide on the
`emit-whole-tu|<name>` key and report one marginal for two recognizers). Each
entry also gets its own printed marginal, because *a registry entry that never
fires and one that was never added are the same `|E|` and very different facts*.

## 5. What FRONTIER means now, and who moved

**Before:** `A∧B∧C ∧ ¬D ∧ ¬match` — "the only remaining factor is codegen
breadth".

**Now:** `A∧B∧C ∧ ¬(D∨E) ∧ ¬match` — **"no acceptance path the port has covers
this TU, and per-function codegen breadth is the whole remaining distance."**

The change is a **narrowing**. A TU that a whole-TU recognizer already accepts
but that is not a match is *not* on the codegen-breadth frontier: its blocker is
that whole-TU emitter's own fence (for `dyninit`, the `/GF` fence in `c2-core`),
which is different work from widening the function class. Leaving it in would
advertise per-function codegen as the route to a TU per-function codegen cannot
reach.

**Membership did not move.** 17 before, 17 after, **0 entered and 0 left**, by
name — because `|E| = 2` and both E-true TUs are already matches, so the
narrowing has nothing to remove on this workload. The list handed to lane w-front
is unchanged:

## 7. Found and not taken

1. **`??__F`, the atexit destructor thunk, will be the registry's second entry**,
   and it is the first real test of the degradation argument. w-r1c §4.4 prices
   it exactly: +2 sections (`.pdata`, `.text$yd`), +10 symbol records, a framed
   `??__E` with 14 relocations. When it lands, the control goes red *until*
   `("dyninit-??__F", …)` is added here — that is the design working, and the
   next lane should expect the red rather than treat it as a regression.
2. **E is recognizer-level, so `|E|` is an upper bound on whole-TU conversions,
   not a count of them.** On this workload the two coincide because the `/GF`
   fence never fires at `/O1`. A `/Ox` lane would separate them, and the honest
   place to see that is the printed set-identity line (the joint would contain a
   non-matching TU). Nobody has run the 878-TU workload at `/Ox`; that is a
   one-flag scan and it would price the gap between "the recognizer takes it" and
   "the port emits it" for the first time.
3. **The `emit-emit-path` key is per-TU in the JSONL and nothing consumes it
   yet.** It exists so `D∨E` is a carried fact rather than a join two readers
   could re-derive differently — the §10.18 shape. A longitudinal differ
   (`scripts/gt_relational_redist.py` diffs two `gap --jsonl` scans) could use it
   directly.
4. **The `ground truth VIOLATED: 2 emitted symbols on the 8 byte-exact TUs did
   not bind to an in-class row` line in the EMITTED CENSUS block is the same 2
   TUs, reported by a third instrument, and it is still red.** It is outside this
   lane's seam (`emit_set_*`, not the factorization) and outside its brief, but it
   is the same fact — the emitted-symbol binding has no whole-TU notion either.
   Whoever takes it should note that the fix there is *not* the one taken here:
   that instrument is about symbol binding, not acceptance.
