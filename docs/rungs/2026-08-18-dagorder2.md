### 4.1 The `fnbyte-exact` +2, and why it is not attributable to this lane

The registered baseline is `fnbyte-exact` **35,897** / `fnbyte-refused-parse`
**113,449**. This tip measures **35,899** / **113,447** — `+2` and `−2`, a
consistent pair: two functions moved from *refused by the parser* to
*byte-exact*.

**It cannot be this lane, and that is checked three ways rather than asserted:**

1. `git diff 44794fa4..HEAD -- crates fixtures scripts` is **empty** — the
   binary under test is the base's.
2. The gate's `graded tree` content hash is **identical at both ends** of the
   run, so nothing rewrote `crates/` mid-run either.
3. **The scan was run twice and the 394 keys are byte-identical between the two
   runs** (`work/w-dagorder/verify/gap-tip.txt` vs `gap-tip2.txt`), so the `+2`
   is **deterministic in this environment and not noise** — which is the more
   useful half of the result, because a flaky `+2` and a stable `+2` need
   different explanations.

**The cause, structurally confirmed and now board `#3249`.** The capture cache
is not per-worktree: `cli/gap.rs:116` resolves it to
`main_repo_root()/work/capture-cache` — **deliberately `main_repo_root()` rather
than `repo_root()`** — and `main.rs:132` documents it as *"shared by every
worktree"*. `work/dc3-workload/` is **entirely untracked**
(`git ls-files work/dc3-workload/` is **0**); its newest input predates the
baseline by two weeks, so the *inputs* did not move, but the shared, mutable
cache did, with peer lanes in flight.

**The coordinator reproduced it independently at clean master with a run-private
binary** — `fnbyte-exact` **35,899** / `refused-parse` **113,447** against
STATUS's **35,897** / **113,449**, sum conserved at **149,346**, with
`match`/`mismatch`/`vocab-gap`/`capture-fail` all holding — and filed
**`#3249`: `fnbyte-exact` is not a pure function of the commit**. Cited here,
not re-minted.

**What `#3249` leaves UNMEASURED is the thing this lane correctly did not
claim**: whether that cache is a *pure* cache or an *authoritative* one. The
`+2`/`−2` direction — **refusals becoming parses** — is what an authoritative
cache gaining better IL would look like. Settling it needs a controlled cache,
which is a `scripts/` change outside this lane's seam: **a lane, not a
footnote.**

The reading that made it worth raising rather than smoothing over: *"the

## 6. Found and not taken

1. **The A-series head/tail split** — `h g f | b a c d e` at n=8, with the head
   growing `0,0,0,1,1,2,2,3` over n=1..8. A composition of the schedule, the
   accumulation weights and (at n ≥ 6) register pressure; this grid does not
   separate them. The highest-value open item, and the cheapest next cell family
   is an n-series with the *live set* held at 2 while n grows.
2. **`cnd_s2` / `cnd_s2r`** — `a-b` and `b-a` give the *same* assignment, and
   both **invert** the `+` cells. The operator moves the assignment and the
   written operand order does not. `wb-dagorder`'s own found-and-not-taken item
   3 (*"`+`-reassociation is a grid fact; the code that produces it is
   unread"*) is the same gap reached from the allocator side, and closing it
   would close both.
3. **`0x10b2d630` does two jobs** — it narrows the allowed set (#3049) *and*
   accumulates the priority. `wb-live` characterized only the first. Reading the
   weights is F5's cost model and needs an obj cell nobody has built.
4. **A THIRD field-table correction is likely and was not chased.** Two were
   found by using two fields (`+0x18`, `+0x44`); `wb-live`'s table was
   enumerated in one pass and is **phase-flat** by construction. The table
   should carry a phase column, which is a doc change this lane's seam allows
   but whose evidence it does not have.
5. **~~`WB_REGALLOC_FINDINGS.md` §1 still says "There is no `sched.c`, and no
   instruction scheduler."~~ — TAKEN, on the rebase, with the coordinator's
