## 1. Deliverable 1 — two instrument fixes, and the size of what they were hiding

### 1.1 The raw-window verdict could not tell a measured zero from an unmeasured one

`crates/c2-harness/src/cli/stage.rs` skipped every function whose `sched2` and
`sched3` raw windows had different lengths (they cannot be aligned row-for-row),
then tested only `hot.is_empty()` — which is true both when the allocator wrote
nothing **and when nothing was compared**. It printed the first sentence over
the second.

**Fixed**, and then measured at 384 fixtures
(`work/w-restim/snap_all_fixtures_verdicts.log`, `--raw 128`):

| population | count |
|---|---:|
| fixtures snapped (2 ERR, the pre-existing `wmain_no_return` pair) | 384 |
| **RAW WINDOW VACUOUS at this tip** — the pre-fix binary printed the null here | **92 (24.0%)** |
| compared some pairs, skipped others (1–6 functions each) | 125 |
| nothing skipped at all | 167 |

**And `#3323`'s null does not generalise.** Of the 292 fixtures with ≥ 1 aligned
pair, **105 name at least one offset COLOR writes**. The `IDENTICAL 7/7 ·
offsets COLOR writes: NONE` on `il_call_perm.cpp` reproduces exactly at this tip
and is **unmoved** — it is a true statement about a fixture on which COLOR is a
no-op for all seven functions, and it was read as a statement about the
allocator. That is the same shape as `#1823`'s *"this c2.dll has no instruction
scheduler"* (a true statement about an instrument read as one about the image),
and it is the fourth time this project has made it.

### 1.2 The payload size is not the coverage

`tap_walk_tuples` terminates on `next == 0` — the end of the function's LIST,
not the end of the region it was handed — so region *k*'s walk re-reads regions
*k..n*. `TapReport::distinct_rows` publishes the distinct count beside the
payload size, and **checks** the nesting rather than assuming it: each block
must be a tail of the longest block in its `(phase, function)` group, and a
block that is not makes the distinct figure a declared FLOOR.

| over 384 fixtures | |
|---|---:|
| published rows (`stage-snap-tuples`) | **303,600** |
| distinct tuple positions | **117,174** |
| `(phase, function)` groups | 11,742 |
| suffix re-reads | **61.4%** · inflation **2.59×** |
| groups where the nesting model FAILS | **2** (`w42_shift_mask.cpp`, `wjson_utf8_copy_neg.cpp`) — those two publish a floor and say so |

The review's independent figures were 65.1% and ~2.9×; this is a second
derivation with a checked model, and it also re-derives the COLOR-pair figure
(2,936 pairs, **723 differing**, against the review's 736/2,949).

## 2. Probe A — where COLOR's output lives. **The lane's own P-A1 is HIT at scale and REFUTED on its control fixture, and both halves matter**

### 2.1 What was built

`C2RS_STAGE_OPS=1` walks the two operand lists a tuple points to
(`tuple+0x28`/`+0x2c`) and, from each operand, the symbol/candidate record —
`op+0x8` kind, `op+0xa` type word, `op+0x1c` symbol; `sym+0x4` kind,
`sym+0x1c` id, `sym+0x10 → +0x1c` the assigned register, `sym+0x8 → +0x1c` the
physical one. `DISCLOSURE.md` **W-STAGETAP-4**.

**Every read renders a value, a NULL and an unreadable pointer as three
different tokens.** This is not fastidiousness: the probe is a pre/post
comparison, so an instrument printing `0` for *"could not read"* would
manufacture both its nulls and its differences. It is the prereg's invalidation
rule 3 and it is the defect of §1.1 in a new place.

### 2.2 Two guards came out of the first run, and both are c2's own

The first armed run produced operand kind `0xf8`, symbol kind `0x88`, and — in a
stream whose entire schema rule is that it contains no addresses — the c2 static
data address `0x10c2f268`. Both causes were guards c2 itself applies and the
probe did not:

* operands are walked only when the tuple's `+0x9` bit 0 (real-instruction) is
  set (`FUN_10bfebf7`, `FUN_10b2ceb7` both gate on it) — without it the walk
  reads `+0x28`/`+0x2c` out of **label and region-marker tuples**, where they
  are not list heads;
* `op+0x1c` is followed only when `op+0x8 == 1` — the address came from a kind
  `0x0b` **call-clobber-set** operand, whose payload is a register bitset at
  `op+0x18` and whose `+0x1c` is not a symbol at all.

**Following a field c2 does not follow invented a finding and a schema violation
in the same read.** With both guards in, walk refusals go to 0.

### 2.3 The result

384 fixtures, 2,946 `color`→`sched3` function-pairs
(`work/w-restim/probeAB_all_fixtures_verdicts.log`):

| | pairs | share |
|---|---:|---:|
| spine IDENTICAL, full IDENTICAL | 2,045 | 69.4% |
| **spine IDENTICAL, full DIFFERS** | **771** | **26.2%** |
| spine DIFFERS (coalescing deletes tuples) | 130 | 4.4% |

**26.2% of the allocator's function-pairs have a footprint that is entirely in
the operand records** — invisible to every observable that existed before this
lane, and invisible to the 128-byte raw window `#3323` used.

And the write itself, verbatim (`work/w-restim/probeA_add3.log`, `add3.cpp` fn1):

    BEFORE: … | OP S 0 01 1004 02 00000002 none 00000002
    AFTER : … | OP S 0 01 1004 01 00000004 unread 00000004

The source operand's symbol goes from **kind `02`** (a candidate, id 2, assigned
descriptor `none`) to **kind `01`** (a physical-register record, value `4` =
`r3` in the `n = r+1` encoding). On the same function candidates `{2,3,4}`
become `{r3, r4, r11}`.

### 2.4 The correction this produces

`P_REGALLOC.md` §4.1 lists `cand+0x1c` as the **id** and `+0x10` as the
*"assigned register descriptor"*, and `#3323`'s consequence line said the
assigned register *"lives in the operand records the tuple points to, or in the
allocator's own candidate records (`cand+0x28`/`+0x3c`)"*. **It is neither of
the two guesses**: COLOR does not write the register into the candidate the
operand already points at — it **re-points the operand at a different symbol
record**. `cand+0x28`/`+0x3c` (first/last block, last defining tuple) are not
involved.

### 2.5 P-A1 scored honestly, both ways

P-A1 registered 0.85 that the pre/post-COLOR pair DIFFERS **on
`il_call_perm.cpp`**, the control fixture. On that fixture it is **IDENTICAL
7/7 at every fidelity** — spine, operands, symbols, candidate ids, both register
fields — so **P-A1 is REFUTED as registered**. It is a HIT on the population the
prereg did not name. That is `#1459`'s lesson taken twice: *a registered number
is a statement about the population that suggested it*, and this lane registered
against a population of one fixture that happens to be the one where COLOR has
nothing to do.

## 3. Probe B — the final schedule, and P10 answered in the affirmative

### 3.1 The eighth site

`0x10b7e701` (`e8 2c f9 ff ff` → `0x10b7e032`) in the per-function orchestrator
`0x10b7e6af` is the **first call after `0x10b7df57` returns**, and `0x10b7df57`
is run 4 (mode 0), which contains the `sched0` site `0x10b7e00c`
(`0x10b7df57 + 219 = 0x10b7e032`). `ecx` still holds the function record
(`0x10b7e6ff: mov ecx,esi`). `DISCLOSURE.md` **W-STAGETAP-3**.

It arms fail-closed and fires **7 times on `il_call_perm.cpp`** — equal to
`sched1`, to c2's own `/FAsc` `PROC` count and to the obj's `.text` COMDAT
count. **P-B1 (0.75) HIT.**

### 3.2 P10, which `w-stageoracle` reported NOT NEEDED, is needed and is answered

`C2RS_STAGE_FUNCWALK=1` walks a whole function from its record:
`func+0x8` → header, `header+0x4` → first block, `block+0x4` → next block,
`block+0x20` → the block's LAST tuple, `block+0x1c` → the stop value,
`tuple+0x10` → prev. `DISCLOSURE.md` **W-STAGETAP-5**. There is no region tap
after run 4, so this is the only observable that can exist at `after0`.

### 3.3 THE CROSS-DERIVATION'S FIRST VERSION WAS VACUOUS, AND IT PASSED 14 OF 14

It checked **multiset containment** of the region walk's rows in the function
walk. **14 of 14 AGREE** — and it would have agreed just as happily on a
reversed walk, on a re-blocked walk, or on any permutation. The direction is the
*entire content* of a backward walk that the reader reverses.

Replaced by an **order-sensitive** check, and the honest result is narrower and
came with a second finding:

* the region walk's opening rows ARE the **in-order tail** of a funcwalk block
  on **14 of 14** → the within-block direction is CONFIRMED;
* the region walk then continues into tuples that **`block+0x4` orders
  EARLIER** → **`block+0x4` is a traversal order, NOT the tuple list's order**.

So every phase comparison in §2.3 and §3.4 is *the same traversal read at two
phases* — never a claim about emitted order. The check prints both sequences
when it fails, so the next reader does not have to re-instrument to see what
this run already had in hand. **P-B2 (0.65) HIT, in the narrow form the
order-sensitive version licenses and not in the form the multiset version
would have granted.**

### 3.4 Run 4 does move the list, and now it is seen

2,946 `sched0`→`after0` pairs: **118 spine-differ (4.0%)**, **31 operand-only
(1.1%)**, 2,797 identical. **P-B3 (0.60) HIT** — the run that fixes emitted
instruction order changes something on 5.1% of functions, and before this lane
that was unobservable in principle rather than merely unmeasured.

**P-B4 (0.30, the `.cod` instruction-count equality) is NOT MEASURED.** The
`.cod` route needs the mnemonic table at `0x10b1b260` to map c2 opcode numbers
to printed mnemonics, and the direct observation made the count comparison
redundant for the go/no-go. Registered low, declined, and named here rather than
quietly dropped.

## 4. Probe C — the port cannot emit this trace, and the reason is coordinates

`crates/c2-harness/tests/stage_region_trace.rs`, on `w5_chain.cpp`, which the
port emits **byte-exact on 4 of 4 functions** — the test asserts that first,
because against a refused function the comparison would be vacuous in the most
ordinary way.

    PROBE-C fn1 ?c4_mul@@YAHHHHH@Z:  c2 tuples at sched1 = 19, port instructions = 4
    PROBE-C fn2 ?c4_sub@@YAHHHHH@Z:  c2 tuples at sched1 = 19, port instructions = 4
    PROBE-C fn3 ?c4_add@@YAHHHHH@Z:  c2 tuples at sched1 = 19, port instructions = 4
    PROBE-C fn4 ?c5_mul@@YAHHHHHH@Z: c2 tuples at sched1 = 22, port instructions = 5
    29 c2 regions over 4 functions; 4 with NO COMMON INDEX

c2 expresses a region boundary as a **tuple index at a pre-lowering phase**; the
port's most granular structure is `block_ir::BasicBlock`, whose `body()` is
`&[u8]`. A boundary given as a tuple index has **no image** in the port's
coordinates, so the port→trace projection is not *unequal* to c2's — it is
**undefined**. **P-C2 (0.85) and P-C3 (0.80) HIT; P-C1 (0.20) REFUTED**, as its
number implied.

Written as a **test** rather than as a grep over `crates/c2-core/` for the word
*region* (which finds zero occurrences in c2's sense): an argument from absence
is the thing this project keeps getting wrong, so both sides have to produce
evidence before the inequality is read. The assertion fails LOUD if the premise
changes and names the document that must then be re-priced — never the
assertion that must then be relaxed.
