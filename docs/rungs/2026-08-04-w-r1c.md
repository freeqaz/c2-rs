## `resolve_data` was never touched, and that is the result

The brief called (c) "the dangerous one" and it is. The obvious move is to let
`Bindings::resolve_data` admit a symbol the TU *defines*; it is a three-line
diff and it makes both TUs resolve immediately. It also sits on the ordinary
function path, where **39,967** functions file under `data-sym-*`, and the
port's ordinary shell has no `.bss` and no `.data` — so it would send some part
of that population into an emitter that relocates against a symbol whose section
it never wrote. Prereg §0 pre-committed against it and clause 6 declined the
lane if its acceptance moved.

So the join is a **whole-TU recognizer**, `IlBundle::dyninit_tu`, which an
ordinary function cannot reach: it requires the TU to hold exactly one function
and that function to be the thunk. `resolve_data` is byte-identical to what it
was. The evidence that this was the right shape is in the numbers — the census
is **+0** and `codegen-gap` is still **0**, so nothing outside the two TUs moved
in either direction.

## The `/Ox` fence is the whole safety argument, and it is structural

`/GF` is implied by `/O1` and `/O2` but **not** by `/Ox` (§4.3). Without it the
literal is a **non-COMDAT `$SG<n>` `.rdata` placed BEFORE `.text`**, with 5
relocations instead of 9 — a different obj this lane did not model.

The trap, measured: **at `/Ox` the fixture still carries `abc\0` in `.in`**
(`ef 09 00 03 04 61 62 63 00 07`) **and carries no `??_C@` record anywhere in
`.gl`**. A reader that trusted `.in` alone — which is the natural way to write
this, since `.in` is where the literal lives — would compute
`??_C@_03FIKCJHKP@abc?$AA@` and emit the `/O1` shape for a `/Ox` TU. That is a
wrong-bytes emit reached by doing the obvious thing.

The fence is one line: **the computed `??_C@…` name must be one `.gl` actually
spells.** It refuses on structure, not on a flag test, so it keeps working if a
later lane changes how flags reach the port. `/Ox` held at 100 on both its lanes
in every gate run of this lane, which is what proves it.

## What lane w-bss changed about this rung

w-bss landed mid-lane and refuted three claims in `OBJ_DYNINIT_SHAPE.md`, the
document this emitter was built from. **Audited against the reference obj rather
than against either document** — the compiler is the sole judge — using
`TomCryptLicense.cpp`'s own 1,403-byte obj:

| w-bss correction | does it reach this class? | evidence |
|---|---|---|
| non-COMDAT `.data` carries a real CheckSum | **no** | this obj has no `.data`; and its `.CRT$XCU` aux CheckSum is `0x00000000` **despite carrying 4 bytes of raw data**, so the rule does not extend to it |
| `.bss`/`.CRT$XCU` are not always last | **yes — and it became a gate** | the reference obj's order is `.drectve .debug$S .XBLD$W .XBLD$W .text$yc .rdata .bss .CRT$XCU`, exactly what the emitter builds, *for this class*; w-bss §2.2 rows 11 vs 12 show one extra `char b1;` moving `.bss` between the watermarks |
| `.bss` symbols not always descending | **no** | this class defines exactly one `.bss` symbol |

The second one is the important one and it added **two gates that were not in
the plan**: exactly one *uninitialized* object in the whole TU, and exactly one
*initialized* one (the `$initializer$` slot). The `.gl` attribute byte — `00`
uninitialized, `80` initialized — is what makes the count possible, and without
it the `$initializer$` record would have been miscounted as a second `.bss`
object. `fixtures/cpp/wr1c_dyninit_two_objects.cpp` is that gate's fixture and
it refuses at all twelve lanes.

## Three readings the IL gave up

1. **`24` (`$`) is a third `.gl` name separator**, introducing an
   internal-linkage symbol whose COFF name is the run after it, undecorated:
   `$sL` → `sL`, `$sLicense` → `sLicense`, `$sL$initializer$` →
   `sL$initializer$`. `gl_symbol_index` opens a run only after `00` or `26`, so
   a `24`-introduced name was **never seen at all** — which is the entire reason
   TomCrypt reported `data-sym-unresolved` and Zlib `data-sym-not-extern` from
   **byte-identical `.ex` files**. It is deliberately *not* added to
   `NAME_SEPARATORS`: that constant binds every callee in the corpus.
2. **The TYPE tag is ALIGNMENT, not size** — `IL_TYPE_TAGS.md` §1's owed
   aggregate capture, landed. Its table reads 1→`82`, 2→`84`, 4→`86`, 8→`88`
   under the heading `size`, true only because a scalar's size *is* its
   alignment. Three ints (`sizeof` 12) and one int (4) share `86`; two doubles
   (16) and one double (8) share `88`.
3. **`.in`'s length is a THIRD varint** — `80` + **LE16**, not `read_varint`'s
   `80` + LE32. A 134-byte probe spells `80 86 00`. Both target TUs are under
   128 bytes, so **nothing in this lane's own corpus would have caught the wrong
   width**; the probe exists only because w-r1's rung asked for it.

## A known-answer control went red, and it is right

> `known-answer control — matching TUs failing each factor (all must be 0, over 8 matching TUs): A 0 B 0 C 0 **D 2**`

**ROADMAP §10.19's claim that `A ∧ B ∧ C ∧ D` is exactly the match set is
refuted.** The conjunction is **6**; the differential grades **8**.

It is not a port defect. Factor D's proxy for "the port can emit this" is the
**per-function** census verdict, and that factorization was measured when
`PortC2` had exactly one acceptance path. A `??__E` TU is emitted by a
**whole-TU** path, so its thunk is byte-exact in the obj and out of class in the
census simultaneously — two true answers to two different questions.

**Left red on purpose, with the reason printed next to it.** Fixing it means
teaching the per-function census a whole-TU fact, which breaks the census/gate
symmetry `census.rs` maintains deliberately and that the scan's
`census/gate disagreement: 0` line tracks. Silencing it would hide a real
refutation. The honest reading is that **the factorization needs a fifth term
for whole-TU emitters** — not that D should be widened until it stops
complaining. That is a follow-on rung with its own brief.

`PORT_WRITER_SECTIONS` moved to `c2-core::coff` in the same breath, which w-r1's
"found and not taken" item 3 named as this rung's trigger: the port emits
`.text$yc`, `.bss` and `.CRT$XCU` now, and the stale six-name mirror in `gap.rs`
would have put both byte-exact TUs *outside* factor C. Its failure mode is
silent in both directions and the scan's control only catches one, so a portable
test now reads `coff.rs`'s own `Section { name: … }` literals and requires the
constant to be exactly that set.

## Found and not taken

1. **The factorization's fifth term.** Above. The cheapest honest version is a
   per-TU "the port has a whole-TU path for this shape" key written where the
   other `emit-*` keys are written, joined into `factors()` as a disjunct on D
   rather than a widening of it. Cost: one key, one join, one control line — but
   it needs a brief that says what the term *means*, because "D or the port
   emitted it anyway" is circular and must not be what gets written.
2. **`??__F`, the atexit destructor thunk, is refused and the price is known.**
   The decode already handles it (w-r1 widened the parser for the bare `4C` both
   share); the refusal is purely emit-side. §4.4 measures the cost exactly:
   **+2 sections** (`.pdata`, `.text$yd`), **+10 symbol records**, and a `??__E`
   that becomes framed — 0x40 bytes, 14 relocations, a `bl atexit`. That is a
   sized rung, not an unknown.
3. **≥2 objects is now *solvable* and was not before.** `OBJ_DYNINIT_SHAPE.md`
   §7.1 declined the `.bss` permutation as "a name-keyed ordering that would need
   the front end's hash reproduced". w-bss §5.2 dissolved it: ascending `.bss`
   address is `.gl` symbol-record order for eager objects and its **exact
   reverse** for deferred (dynamic-initializer) ones, never interleaved — and
   both are readable from IL the port already holds. This lane still refuses ≥2
   objects, because the *section placement* also moves (§2.2) and that is a
   second change, but the blocker that was called impossible is gone.
4. **The general two-symbol tail call is still declined**, unchanged from w-r1
   item 2: §17.3's 18,933 functions imply an argument emission order this port
   does not ship (`g(&gA, 7, "cc")` puts `li r4,7` *after* both `addi`s, where
   `permute_args_parts`' descending walk puts it before). This lane's
   `dyninit_thunk_text` encodes the three-block schedule — every `lis`, then
   every address `addi`, then every `li` — for the thunk only, and does not
   generalize it.
5. **Board rows, proposed rather than edited** (a lane is live on `BOARD.md`,
   `ROADMAP.md`, `STATUS.md` and `PHASE7_PLAN.md`, so this rung touched none of
   them):
