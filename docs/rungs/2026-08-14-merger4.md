## What it admits, and what it refuses

**No `crates/` change, no `DISCLOSURE.md` row, no fixture prefix, no function
class.** `git diff master..HEAD -- crates fixtures scripts` is **empty**.

The lane answers board **`#3103`**, `w-dagclients`' own stated relocation:
*with `0x10b3b167`, `0x10b3b41b` and `0x10b3b5fd` all ablated, `dk_join3` still
collapses three copies of a common tail store to two — find the fourth merger,
or establish that the residual has another cause.*

**`#3103` is CLOSED, and it resolves both ways at once.**

* **`dk_join3`: the fourth merger is `FUN_10b3baa8` @ `0x10b3baa8`**, worker
  `FUN_10b3a790` @ `0x10b3a790`. It is a **textual** tail merger over **every
  pair in a label's predecessor list** — it walks the two predecessors backwards
  in lockstep through `tuple+0x10`, compares each pair with **`0x10b36f7e`**,
  the same equivalence K1/K2/K3 use, and commits with `0x10b36e93` /
  `0x10bd417d` / `0x10bd5952` / `0x10bd5648`, the same commit pair as K1.
  **It calls `0x10b328da` nowhere** — no dependence DAG at all, which is
  exactly the "not a DAG-builder client" `#3103` predicted.
* **`dk_loop_join`: not a merge.** It collapses 2 → 1 even with the entire
  driver `0x10b3c2cc` dead, and the listing shows the store hoisted into the
  loop **preheader**. That is loop-invariant code motion. `#3103` read a
  copy-count drop as merging; this half is **corrected, not confirmed**.

**The lead was arithmetic, not luck.** `0x10b36f7e` — the pairwise
tuple-equivalence test — has **seven** callers. `w-dagclients` read the three
that build a DAG. `0x10b3baa8`/`0x10b3a790` and `0x10b3ab86`/`0x10b394f5` are
the two that do not, and both hang off `0x10b3c2cc`'s **label** class under
`mode == 2` — the same `0x10b7ded5` invocation, so their output is likewise the
scheduler's input.

It refuses three things by name:

1. **It does not claim the merger set is closed in general.** It claims

   coverage-bounded claim and §6.3 of the findings says so; `#3071` → `#3103` →
   here is the third relocation of exactly this caveat.
2. **It does not claim `0x10b3ab86` never fires.** It is entered 2/2 and never
   reaches its `call 0x10b394f5` on any of 13 cells. That is a statement about
   the grid, filed grey-zone in `#3101`'s shape, with no board claim.
3. **It does not score `0x10b36805`.** That candidate **cannot be ablated** —

## Found and not taken, ranked

1. **`0x10b3ab86` → `0x10b394f5` has never been seen to fire** and is a full
   merger by construction (it mints a label at `0x10b9a455` and commits at
   `0x10b39697`). It bails in `0x10b3ab86`'s own prologue on all 13 cells. Its
   gate needs a **join both of whose predecessors end in a conditional branch**
   *and* survive `0x10bd4461`'s test on the label's own predecessor — one grid,
   an afternoon, and it would close the last merger in the family.
2. **K3 `0x10b3b5fd` still has no firing witness**, but this lane read
   `0x10b35f88` and it is not a search: it is a **complementary-branch test**
   through the inversion table `DAT_10b189cc`. The shape to write is a join
   whose two predecessors are *the same test branched both ways*, not a
   multi-way chain — which is why `w-dagclients`' grid 2 missed it with six
   guesses.
3. **`0x10b3a790`'s budget units are not decoded.** The direction is measured
   (favor-speed needs a longer common tail: `mg_len1` 3 copies vs `mg_len2` 1),
   the constant is read (`2` vs `0x14`), but `iVar12` over `0x10bf96c6` and the
   `tuple+0xe` shorts are not.
4. **`DAT_10b189cc`, `DAT_10b189e0` and `DAT_10b18a30` were not dumped** —
   three condition-code tables read only from their use sites.
5. **The `/Od` and favor-speed `AFULL` residuals** (+1 instruction per function
   at `/Od`, +1 on `mg_loop3` at favor-speed) are attributed to the
   block-concatenation path by reachability (`XC2` traps at `/Od`, nothing else
   does) but not isolated further. They change **no copy count**, which is why
   the closure claim survives them.
