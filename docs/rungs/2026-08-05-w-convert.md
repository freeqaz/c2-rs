## 0. The headline, in one paragraph

The `2C` arm's own doc comment named an open rung — *"a reinterpret between the
two classes has never been graded across the widths, cv-spellings and argument
positions this parser reaches"* — and the one-away screen (#684) ranked
`expr-convert-target` **first on the board**: 8,181 one-away of 8,222 mass, at
1:1 purity, "nothing above +19" as a substitution. It was the only key measured
to be near-*terminal* rather than a fall-through.

**It was built. It converts zero.**

The reinterpret is real and byte-exact (§4). The guard it needed turned out to
be a guard that could be made exact, and that shipped too (§6). Between them
they release **5,712** of the 8,222 from `expr-convert-target` and every single
one lands on `expr-ptr-arith` — because the workload's population is
`(unsigned)(p - q)`, a conversion applied to the **result** of a pointer
difference, which c2 lowers as a subtract plus a divide by the pointee width.
The other 2,510 are `bool`→int and `int`→`unsigned short`: real instructions,
correctly refused, and no reading of "unblock the convert" ever reaches them.

So the screen's 8,181 realizes **0 functions, 0 TU match, 0 FBM**. §7 is why,
and it is a deeper defect than the one #687 named.

## 3. The matrix, run whole

Declared in the prereg §3 before it was run, and run at **two** profiles —
`/Ox` and the workload's `/O1 /Oi /EHsc /GR` — because a grid that only ever saw
one profile cannot contain its own counterexample. **The two are identical on
every cell below.** `work/w-convert/probe/m1.cpp`, `m2.cpp`, `m3.cpp`, `m4.cpp`;
extraction by `work/w-convert/probe/dis.py` off `c2rs listing`'s `.cod`.

### 3.1 The `ValueClass` 3×3 — the load-bearing table

"free" means c2's whole `.text` for `T g(U x){ return (T)x; }` is a bare `blr`.

```text
  source \ target |  Int4          Ptr4          Int1u
  ----------------+------------------------------------------
  Int4            |  free  (old)   free  (NEW)   clrlwi 24
  Ptr4            |  free  (NEW)   free  (old)   clrlwi 24
  Int1u           |  clrlwi 24     clrlwi 24     free  (old)
```

**Four of nine cells cost an instruction.** `Int1u` is the row that matters:
a pointer is one register, so `void *f(bool b){ return (void *)b; }` looks like
it must be free, and it is the **same `rlwinm r3,r3,0,24,31`** that
`unsigned u(bool b){ return b; }` is. A widening written as "a value class is a
value class" gets three cells wrong; `eat_reinterpret_type` bars `Int1u` in its
own `match` arm rather than by falling off the end, so the bar is legible.

> **P10 registered "1 to 4 cells of the full matrix turn out not free". Four.
> HIT, at the top of the range.**

### 3.2 The 31 free cells, and the axis that could have broken

| axis | values crossed | result |
|---|---|---|
| direction | `int→ptr`, `ptr→int` (+ the two shipped same-class controls) | all free |
| integer spelling | `int`, `unsigned`, `long`, `unsigned long`, a **typedef**, an **enum** | all free |
| pointee | `void`, `int`, `char`, `const char`, `S`, `S**`, a **function pointer**, `const S`, `volatile S` | all free |
| position | leaf return · four call-argument slots · permuted slots · a repeated operand · a nested call · **`this`** (`A6 43`) | all free |
| profile | `/Ox` and `/O1 /Oi /EHsc /GR` | identical |

**Signedness is the axis this target could plausibly have broken on** — the GPRs
are 64-bit and the pointers 32-bit, so a *signed* `int`→pointer is where an
`extsw`/`rldicl` would appear if it appeared anywhere. It does not:
`void *f(int a){ return (void *)a; }` is a bare `blr`, and so is
`int f(void *p){ return (int)p; }`.

### 3.3 The negative controls, from the same grid

`extsb` (`int`→`char`, `char`→`unsigned`), `extsh` (`int`→`short`),
`clrlwi 16` (`int`→`unsigned short`, `unsigned short`→`int`), `clrlwi 24`
(`int`→`unsigned char`, `bool`→anything but `char`), `extsw`
(`int`→`long long`), the five-instruction `fcfid` sequence (`int`→`float`), and
the scaled pointer arithmetic of §5. One free cell in the `Int1u` row —
`bool`→`char` — names a class this parser does not model, so there is nothing to
track the result as and it refuses with the rest.

### 3.4 What the probes silently hold fixed (#644)

Stated, because a population with an unstated restriction has cost three lanes.
Every cell is a **formal parameter** source: `IL_CAST_CONVERT.md` §2.3 measures
that c1xx *folds* a cast of a literal, so a constant source cannot reach the arm
at all. One conversion per function in §3.1–3.2; §3.3's stacked forms are the
counter-probe. **Not** held fixed: the optimization profile, deliberately.

## 4. Board #700 — what shipped

`crates/c2-il/src/func/readers.rs::eat_reinterpret_type`, one predicate, called
from the `2C` arm of `parse_expr_classed` only where `eat_value_type` refused.

* **Positive gate.** It admits `Int4→Ptr4` and `Ptr4→Int4` and returns `None`
  for everything else, `p` untouched.
* **Additive-ACCEPT, not additive-refusal — and the doc comment says so.** The
  arm is reached only on a path that previously refused, so no body master
  accepted parses differently; but a future wrong answer here would be a wrong
  emit and not a new refusal. That is written into the code rather than papered
  over with the guard's property, per the standing instruction.
* **Graded by the sole judge.** `fixtures/cpp/wcv_reinterpret.cpp` —
  **48 of 48 functions in class, `Port=Match`, byte-exact against real `c2.dll`
  under wibo**. `wcv_reinterpret_neg.cpp` — 19 functions,
  `Port=NotImplemented`, and **every one verified by `c2rs census` to block at
  the key it names** rather than at some earlier byte:

  ```text
    8 x expr-ptr-arith            1 x expr-convert-target-8211  (char)
    2 x expr-convert-target-8212  1 x expr-convert-target-8421  (short)
        (bool / unsigned char)    1 x expr-convert-target-8422  (unsigned short)
    1 x call-arg-duplicated       1 x expr-convert-target-8641  (int, from bool)
        (a pre-existing gap,      1 x expr-convert-target-8642  (unsigned, bool)
         named as an exclusion)   1 x expr-convert-target-8643  (void*, from bool)
                                  1 x expr-convert-target-8645  (float)
                                  1 x expr-convert-target-8881  (long long)
  ```
* **The measure was widened with it.** `mcall`'s `eat_int_operands` carries a
  second copy of the `2C` rule for the census; the enumerated measure-vs-emitter
  guard (#139) went red the moment the emitter moved and was repaired one token
  for one token, including the `saw_ptr` line.

The fixture pair is **two files on purpose**: a fixture's verdict is per-obj, so
one declined function turns the whole TU `NotImplemented` and would have hidden
the positive half's byte-exactness behind its own negative controls. That is not
hypothetical — the first version of this fixture was one file and graded
`NotImplemented` with 39 of 40 functions in class.

## 5. Board #703 — the lane's own registered concern, REFUTED

The prereg §5 asked *"what shape would break this, and can the corpus express
it?"*, answered **no** for four of five shapes, and registered the debt:

> `(S *)a + 1` — breaks H1 by *unscaled add against c2's scaled `addi`*. Can the
> corpus express it today? **no** — `saw_ptr` is only ever set by a LOAD, so no
> fixture can even build the shape.

The shape was built (`scripts/sweep.d/77-reinterpret-2c.py` §6a, 50 cases across
five pointee widths × five indices, plus four fixture functions). Then it was
**falsified**, which is the part the instruction is actually about: the
`saw_ptr = true` line was deleted and everything re-run.

```text
  233 sweep cases, guard DELETED      checked=233  mismatches=0  graded=229
     (the fragment as it stood that hour; 244 today — §9.1 removed 4 and
      added 15, and none of the 15 is a pointer-arithmetic case)
  8 hand-picked exotics, guard DELETED   every one Match or NotImplemented
     1 + (S *)a · ((S *)a) + 1 + 1 · ((S *)a) + 100 · ((double *)a) + 1
     (S *)(a + 1) · ((S *)a) + (k + 1) · (int)((S *)a - (S *)b) · p + (int)(char *)a
```

**Not one Mismatch.** The mechanism is in the IL:

```text
  (S *)a + 1   ->   b9 a <int> · 2c 86 43 81 20 00 · 33 86 41 12 08 · 02
                                                              ^^ EIGHT
```

**c1xx pre-scales.** The literal is already 8 for an 8-byte `S`, so a chain that
"added 1 unscaled" adds 8 and is right by accident. `IL_CALL_IN_EXPR.md` §21.1
measured exactly this for a pointer off a LOAD; this extends the measurement to
a **converted** pointer, which §21.1 never covered.

**The guard is kept**, and the reason is stated rather than assumed: pre-scaling
at every arity, pointee width and cv-spelling is a *second* claim on top of this
rung's, and without the line a pointer that reached the register through a `2C`
would be treated differently from one that was loaded — an unstated asymmetry in
a guard four rungs depend on.

> **The finding to carry forward: a negative control that reaches the shape it
> names is not the same as a corpus that can separate the rule from its
> absence.** The census confirms all eight fixture cases block at
> `expr-ptr-arith` and not earlier — the check #688 asked for, and it passes —
> and the sweep still cannot tell the two builds apart. #688's fragment failed
> the first test; this one passes it and fails the second, which is a distinct
> failure mode and now has a board row.

## 6. Board #701 — `expr-ptr-arith` becomes a class STACK

Between §4 and this, the reinterpret alone was measured on the workload:
**5,712 functions leave `expr-convert-target-*` and 5,711 land on
`expr-ptr-arith`.** Net census movement: **0.**

`saw_ptr` asks *did a pointer appear anywhere in this expression*. The guard's
actual subject is *was an arithmetic operator applied to a value that was a
pointer AT THAT MOMENT*. Those differ exactly where a `2C` moved the value out
of the pointer class first — and `(int)p + b` is `add r3,r3,r4`, an integer
addition with nothing to scale (measured, `work/w-convert/probe/m2.cpp`).

`IlOp` is postfix and each binary op pops two and pushes one
(`crates/c2-core/src/codegen/straightline.rs`), so simulating the **classes**
over the same discipline is exact rather than approximate.

* `cstack` / `fold_binary!` in `parse_expr_classed`; `Stream::fold_binary` in
  `mcall`'s measure. One rule, and the #139 guard holds them together.
* **`cstack_ok` is the model's own honesty.** Any token whose stack effect is not
  modelled clears it, and the end-of-walk guard falls back to the
  whole-expression flag unchanged. So the refusal can only get **narrower**
  where the model holds and is bit-for-bit the old one everywhere else. Nine
  clear sites: stack underflow, the off-add sink's *implicit* second operand,
  the two `chain_sink()=type` operand arms, the chain sink's skip-by-width, the
  relational sink, the three branch-sink arms — and a granted hypothetical class
  or an unclassified `IntrinsicRecv` operand on the measure side. **The five
  sink arms clear it even though the sink poison already refuses the body**, so
  that `cstack_ok` is the literal claim *every token was followed* rather than
  one that holds only because something else refuses first.
* It also retires an approximation the old code admitted to in its own comment:
  `class` was "the class of the last operand", with a note that it and the top of
  the stack "could differ (`(void *)(s + 1)`, whose last operand is the
  literal)". It is the top of the stack now.

Boundary, each cell graded byte-exact against real c2:

| accepts (`Port=Match`) | refuses (`Port=NotImplemented`) |
|---|---|
| `((int)p) + b` → `add r3,r3,r4` | `((S *)a) + 1` → `addi r3,r3,8` |
| `b - ((int)p)` → `subf` | `((S *)a) + k` → `slwi r11,r4,3 ; add` |
| `((int)p) * ((int)q)` → `mullw` | `(int)(p - q)` — pointer difference |
| `((int)p) & b` | `(void *)(p + 1)` |
| `(void *)(a + b)` → `add` | `p[k].m` |
| `(int)(void *)(a + b)` | |

### 6.1 The #139 guard could not have seen this drift, and now can

Every arithmetic case in that guard's enumerated domain put a **raw LOAD** on
both sides of the operator, where the coarse and precise models agree by
construction. A `convert-then-add` axis was added: the domain goes
**16,875 → 20,250** streams, and reverting the measure to the coarse expression
now reports **108 disagreements** (verified, then restored). Before the axis it
reported 0.

This is `sweep.d/10-int-chains.py`'s failure (#688) one layer up — an enumerated
guard whose domain cannot express the drift it exists to catch — and it is worth
saying that the *repair* of one instrument surfaced the same defect in another.

### 7.1 Why this is a deeper defect than #687's leak

#687 already priced the screen as *"an upper bound with a named leak"* — the
poison is raised **before** the pointer and one-byte-unsigned guards — and
proposed a one-line fix: *"move the poison below the guards, or count the guards
separately."*

**That fix would not have helped.** The guard those 5,712 functions land on is
**correct**. A screen that counted them below it would still have reported
5,712, because at that point in the walk the body has legitimately parsed to the
end and the thing standing in the way is not a *parse* obstacle at all.

The defect is structural to what a sink measures. A sink consumes a token and
asks what the census reports next. It cannot ask whether the construct the token
opened produces a value that can then be **lowered**. `expr-convert-target` at
1:1 purity means the convert is the last *parse* obstacle and says nothing
whatever about whether the value it yields can be computed on.

> **Mass pointed the wrong way (#684 established that). Purity points the wrong
> way too.** The 1:1 ratio that made `convert` the pick is exactly the property a
> key gets when its construct is a **type annotation on a value produced by
> something else** — annotations do not stack, so nothing is behind them, so the
> substitution histogram is flat. The screen reads that flatness as terminality.
> It is the opposite: it means the key is not where the work is.

Ten selectors are now refuted (#150 fixed point, #364, #420, #440, #622, byte
fraction/#465, depth/#666, union coverage/#681–#683, and now the one-away screen
itself). **Every one of them ranked BLOCKER KEYS.** The next lane to propose an
eleventh ranking over blocker keys should be asked what makes it different in
kind, not in construction.

## 10. Found and not taken

1. **`expr-convert-target` residue: 2,510 functions, and 809 of them are one
   cell.** `84 22` — `int`→`unsigned short`, `clrlwi r3,r3,16`. One instruction,
   one predicate, and it is the largest single un-taken conversion cell this lane
   measured. **Not taken because a narrowing changes the value**, so unlike every
   cell in §3.1 it cannot be "the same operand stream with a token dropped" — it
   needs a real `IlOp` and a real encoder, and the neighbouring widths
   (`clrlwi 24`, `extsb`, `extsh`, `extsw`) each need their own grading over
   their own sign axis. The `Int1u`→int4 cells behind it (1,659) are the *same*
   `clrlwi 24`, so the family is ~2,470 functions for one arm plus five
   encoders. **It is the honest next step in this seam and it converts 0 TUs**
   — every one of these bodies is on a TU with thousands of other blockers.

2. **The pointer difference, `(T)(p - q)` — 5,710 functions, the whole of what
   this rung unblocked.** c2's lowering is a subtract plus a divide by the
   pointee width, which is a shift for a power-of-two pointee and a
   multiply-high sequence otherwise. **The axes are {pointee width} ×
   {power-of-two or not} × {signedness of the target} × {position}, and the
   non-power-of-two corner is a magic-number division** — the same shape
   `op:30`'s strength reduction was refused on (#684 rule (c)). Sized here so the
   next lane does not have to re-measure it: it is worth 5,710 functions and,
   on the frontier evidence, **0 TUs**.

3. **`expr-ptr-arith` is now precise and worth 0 on the workload.** It releases
   `(int)p + b` and its siblings — real accepts, byte-graded, 4 fixture
   functions and 15 sweep cases — and the workload contains **none** of them.
   Recorded so that nobody re-derives the widening expecting movement.

4. **The `2C` census key names the wrong end.** `expr-convert-target-<tag><kind>`
   renders the *target*, and §2 shows 90 % of the mass is a target
   `eat_value_type` would already have taken — the discriminator is the
   **source** class, which the key does not carry. Splitting it
   (`expr-convert-int4-target` / `-ptr4-target` / `-int1u-target`) would have
   answered §2's question in one scan instead of a build. **Not taken here**
   because a key rename breaks cross-tree comparison for four rungs that have
   quoted this bucket, and the split is worth doing deliberately rather than as a
   side effect of a codegen lane.

5. **`c2rs listing`'s `.cod` is the cheapest oracle in the tree for a
   type-annotation question** and this lane used it for all 60-odd probe cells at
   two profiles in under a minute. `work/w-convert/probe/dis.py` extracts
   per-function instruction text from it; note that the obvious `^\?(\w+)@@`
   pattern misses every **member** function (`?c0@C@@QBAHXZ`), which silently
   dropped the four `this` cells on the first run.
