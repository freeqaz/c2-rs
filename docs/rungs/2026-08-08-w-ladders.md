## 3. `ladder.py` CANNOT SEE THE CODEGEN COLUMN — and the reason is not the poison

Board **#1417** says the four READER-CLEAR TUs' rungs are all poisoned sink
rungs, so a codegen ladder cannot be climbed on them. **That is true and it is
not the binding reason.** The stronger statement, measured:

`ladder.py` reads exactly three fields off each scan. Two of them are the same
column:

| field | what it actually is | on the 16 |
|---|---|---|
| `fn_blockers` | the **reader's** refusal key, every function | the ladder |
| `emit_blockers` | the **reader's** refusal key, restricted to emitted+bound functions (`gap/scan.rs:401` — `f.verdict.key()`) | 66 distinct keys on U, 68 on H; **every one of them an `expr-*` / `assign-*` / `call-*` reader key**, `noform-0x4F` chief among them |
| `fn_gate_refusals` | **not a codegen column at all.** `TuResult`'s own doc: *"the census/gate cross-check… It must be empty. Anything here is the census over-claiming."* Its target is **0** | non-empty in **0 of 186** rounds on U and **13 of 219** on H (§6) |

So the driver never had a codegen reading to lose. **The port's acceptance lives
in the IL parser by design** (`STATUS.md`, "Where the code is": `function_gate`
exists *"why `census/gate disagreement` is 0"*), so there is no per-function
field anywhere in `TuResult` that says *"the reader accepted this body and the
emitter could not lower it."* That verdict is not withheld by the poison; **it
does not exist to be read.**

**Plainly, because the brief asks for it plainly: `ladder.py` cannot price the
codegen column on ANY of the sixteen, on either instrument, and removing the
poison would not give it one.** #1417's four TUs are a special case of that, not
the whole of it. Pricing codegen needs what `w-clear` actually did — feature
isolation from the accepted class, graded by the differential (#1418) — and no
change to this driver produces it.

## 4. SIX OF THE SIXTEEN LADDERS END ON A RUNG THAT ADVANCES THE STREAM BY ZERO BYTES

`chain_step_with` (`expr.rs`) reads the byte, looks it up in `chain_skip_form`,
and on a miss returns `Err("expr-chain-noform")` **before moving the cursor**:

```rust
let Some(form) = chain_skip_form(b) else {
    return Some(Err("expr-chain-noform"));
};
let mut q = p + 1;                 // ← never reached on the miss
```

So granting an opcode this tree has not pinned changes the reported key from
`expr-op-0xNN` to `expr-chain-noform-0xNN` — **the same byte, at the same
position, under a second name** — and buys zero decode distance. `lift_for`
grants it anyway, the round's *"did the blocker set move"* test passes on the
changed key text, and the rung is counted.

**Six of the sixteen end on exactly one of these, identically on both
instruments** — `Biquad` and `EncryptXTEA` (`op:00`), `wordwrap` (`op:1C`, via
the *named* key `expr-and-and`), `Pool` (`op:10`), `IPP_basicmath` (`op:11`),
`keygen_xbox` (`op:13`). The `EXIT` line was always honest — it says
`(noform)`, *the instrument ran out* — and then the row charged a rung for
running out. That is board **#1285**'s shape a third time.

`is_rename()` classifies it, `PINNED` is **derived from `expr.rs`'s own match
arms** (46 opcodes at this master) rather than copied, and the derivation
**fails closed**: `LADDER-NOWIDTHTABLE` on an unreadable file, an empty table,
or a table that parses fewer than 20 arms. An empty width table would
reclassify every rung as a rename, which is trap 5 aimed straight at this
lane's own finding.

`net` is left alone so every published table still compares; `stepped` is
published beside it and is the number that is a price. **154 → 148 and
183 → 177.**

## 5. THE FIRST-PASS GRANT WAS NEVER VERIFIED, AND THE HATCH IS WHERE IT COSTS

`ladder.py`'s **second** pass (the tail-opcode rule, lane `w-one`) already
trials a candidate and files an inert one under `tail_inert`, with the rule
written in its own comment: *granting a byte is not the same as lifting the
refusal.* **The first pass never had that check.** `lift_for` maps a key to a
token and the token is granted unconditionally; the round advances as long as
*some* key moved, so a grant that bought nothing is booked as a rung whenever a
sibling key in the same round advanced.

`--verify` is the leave-one-out: drop each net rung's token from the **final**
grant set, re-scan on the real dc3 TU at the workload's own flags, compare
`fn_blockers`. Identical ⇒ the rung is not load-bearing for where the row ends.

| | inert rungs | which |
|---|---:|---|
| **U** | **1** | `Biquad` `op:26` |
| **H** | **6** | `Main` `op:26` · `Biquad` `op:26` · `negate_test` **`assign-store-type`** · `vsnprnc` **`call-arg-lit-permuted`** · `keygen_xbox` **`assign-store-type`** and **`expr-convert-no-value`** |

**Four of H's six are HATCH rungs** — that is, four of the eight clauses the
hatch is credited with lifting are, by the end of the row, doing nothing that
the sink tokens above them are not already doing. `negate_test` is the sharpest:
its round-0 blocker *is* `assign-store-type-8643`, so the clause genuinely
unblocked the row — and dropping it from the final 12-token set leaves the
blocker set byte-identical. The honest reading is not *"the clause is
worthless"* but *"the ladder's LENGTH is 12 and its rung set is NOT MINIMAL:
eleven of the twelve reach the same end."* `hatch.py`'s own header predicts the
mechanism for this one — `StoreTypeSink::Any` is that lift, committed, and the
docstring already says the hatch is **SUPERSEDED** by it.

**Two directions of error, both stated.** Leave-one-out is a **lower** bound on
inertness — two jointly redundant tokens both read load-bearing and no
single-drop test sees a pair. It is also an **order-blind** measure: a rung that
was load-bearing when granted and was later subsumed reads INERT, correctly,
because the price is quoted for the ladder that ends where this row ends.

## 8. UNREACHABLE RUNGS — FIVE FOUND, ALL IN THE INSTRUMENT, AND **NONE** PROMOTED FROM AN UNREPORTED KEY

(derived, §4). The bytes six ladders terminate on — **`0x00`, `0x10`, `0x11`,

That is `w-mrslot`'s finding relocated: not an input nothing in the crate can
