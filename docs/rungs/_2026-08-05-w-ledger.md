## 2. The defect: `gate.sh` never reaped its run trees

`scripts/gate.sh` writes a run tree per invocation, defaulting to
`/tmp/c2rs-gate-$$`, and **nothing had ever removed one**. Two observations, both
from other lanes, neither of which was this project's own instrument telling it:

* `rungs/_2026-08-05-w-reach.md` §8.1 — a *merge-base* run whose `mode-cross` row
  came back `NO-RESULT` on
  `/tmp/c2rs-gate-484396/cross/lane-results/Ox: No space left on device`, with
  ~190 leftover trees on the tmpfs. The lane reasoned its way out of the false red
  by hand and filed the defect in prose: *"`gate.sh` leaves its run tree in `/tmp`
  and nothing reaps it… a **correct** tree gates red."*
* Lane **w-alias**, 2026-08-05 — the same red, with the detail that decides the
  design: **19 GB free and `1048576/1048576` inodes used.** `df -h` looked healthy.

> ### **The brief for this lane specified a free-SPACE check. On w-alias's failure that check would have PASSED and the gate would still have gone red.** Space and inodes are different resources and this gate exhausts the second one first.

## 3. What actually exhausts it — measured, then CORRECTED BY 3×

### 3.1 The first measurement, and the object it was taken on

`work/w-ledger/CAUSE.md`. Two finished run trees on the real box:

| | |
|---|---:|
| one **finished** run tree | **112 MB**, **16,660 inodes** |
| `/tmp` | 47 GB, **1,048,576 inodes** |
| trees to exhaust **inodes** | **~63** |
| trees to exhaust **space** | ~430 |

> ### **Inodes bind ~7× before space does**, which is exactly the shape w-alias saw.

On that arithmetic, 6 concurrent gates are ~100k inodes — **9.5 %** of the ceiling
— so concurrency alone could not exhaust it and accumulation was the whole story.
That was reported to the coordinator as the diagnosis. **It was wrong.**

### 3.2 The correction, and the instrument that produced it

The low-water sampler added in §4 ran on this lane's first real green gate:

    /tmp free inodes at the run's start      853,187
    /tmp free inodes low-water in the run    802,937
    -------------------------------------------------
    ONE RUN'S PEAK DRAW                       50,250 inodes  = 3.0x its residue
    ONE RUN'S PEAK DRAW                      ~307 MB         = 2.7x its residue

A run **in flight** holds the 18 lanes' scratch, the sweep's corpus and the mode
cross's corpus at once; only a summary survives. **§3.1 measured a corpse.**

Two consequences, and the first is the sharper:

* **The inode floor had been set to 50,000 — exactly one run's peak.** The
  preflight would have passed a filesystem with 50,000 free inodes and the run
  would then have exhausted the filesystem it had just certified. *A check that
  licenses the failure it exists to prevent.* Raised to **150,000**, 3× the
  measured peak.
* **The concurrency hypothesis is not refuted**, and the confident answer in §3.1
  was too confident. ~**21** concurrent runs exhaust the inode table with no
  accumulation at all; 6 concurrent runs are **29 %** of it, not 9.5 %.

**Revised diagnosis — both mechanisms are real and they compose:**

    50,250 K  +  16,660 N  >=  1,048,576        K in flight, N left lying about

K=6 leaves room for only ~45 accumulated trees; K=20 exhausts it alone. **The
reaper answers N and the preflight answers K**, and K is the term that produces
*the red that does not reproduce* — it falls back to zero before anyone
investigates. The fix needed both halves and has both.

`CAUSE.md` carries the correction **appended, not applied in place**: the wrong
number and how it was caught is the useful part of the record.

### 4.1 The concurrency rule, which is the part that could do harm

Several lanes gate at once on this box, and a lane has already spent a day
misdiagnosing a red that came from another lane changing shared state mid-flight
(board **#294**). Deleting a running gate's tree would be a new instance of that
class, authored deliberately. So:

| pid state | verdict | why |
|---|---|---|
| not a number | reapable | a tree nothing can be attributed to |
| `kill -0` fails | reapable | dead |
| alive, `/proc/<pid>/cmdline` says `gate.sh` | **KEEP** | a concurrent lane |
| alive, cmdline says something else | **reapable** | **PID REUSE** |
| alive, cmdline unreadable | **KEEP** | **unknown must not mean delete** |

**The pid-reuse arm is not a refinement, it is load-bearing.** The tree names
*are* pids and this box mints hundreds a night; a naive `kill -0` keeps a stale
tree forever behind an unrelated process, and the reaper would degrade to a no-op
exactly on the busy nights it exists for.

Trees are additionally stamped with a `gate.pid` file. **The name is not a claim
and the file is** — but the fallback to the name matters, because every tree that
existed when this landed predates the file. §5.2 is that fallback working on real
data.

### 4.2 Preserving the logs of the run that just finished

The gate's own last line points at `/tmp/c2rs-gate-<n>/<lane>.log`. Reaping the
newest finished tree would delete the thing the previous line just told somebody
to read, so the `C2RS_GATE_KEEP` (default **3**) most recent finished trees are
kept, newest first.

### 4.3 Observability, and one number that had its sign thrown away

Every run prints one line per tree with the reason, and a summary carrying a
**count** plus the space and inodes freed as a `df` delta.

The delta is measured over a **shared** filesystem, and a real reap of two trees
with two other lanes gating came back at a **net negative** delta. The first draft
printed `${delta#-}` — stripping the minus — and so **reported a filesystem that
had got fuller as space freed**. A number whose sign is discarded is worse than no
number. It now prints the delta as it is, says why it can be non-positive, and
says that the **count** is the reliable signal.

## 5. Testing the reaper POSITIVELY — the situation constructed, not waited for

The brief and the standing rule are the same: *do not report that it works because
nothing broke.* And the coordinator's correction sharpened it — the real condition
is **transient**, so it cannot be found, only built.

### 5.1 In `--selftest`, against real processes and a fabricated tree directory

`--selftest` goes **15 → 67 cases** (floor 45 → 65), needs no toolchain, and drives
the real functions.

The pid rules run against **real** processes, because the whole point of the rule
is what the operating system says and a mocked `kill` would only prove the mock
agrees with itself:

| case | driven with | expects |
|---|---|---|
| `pid-live-gate-is-kept` | **this gate's own pid** | LIVE |
| `pid-reuse-is-reapable` | a **real live `sleep`** | not a gate |
| `pid-dead-is-reapable` | a pid launched, waited on, then asked about | dead |
| `pid-unattributable-is-reapable` | `""` | not a live gate |

The reaper runs against a fixture holding one tree of every kind it must tell
apart — a stale tree, a reused-pid tree, a live-gate tree *whose name carries no
pid at all*, a within-window tree, the current run dir, and a sibling that is not a
run tree — with the ages stamped by `touch -d` so the ordering is a fact of the
fixture and not of how fast the `mkdir`s ran. Seven assertions, **including the
summary count**:

    reap:   3 stale run tree(s) removed, 3 kept (1 live, 1 recent, 1 this run)

> ### **That count is what caught my own expectation being wrong.** I registered `2 live`, counting the reused-pid tree as owned. The reaper classified it as stale and **the reaper was right**. Asserting the count rather than "some trees survived" is the only reason the disagreement surfaced at all.

`reaper-keep-0-still-spares-live` asserts the concurrency property separately at
the aggressive setting rather than inferring it from the `keep=1` case.

### 5.2 On the REAL, occupied `/tmp`, with other lanes' gates genuinely running

The coordinator's constraint was explicit: three lanes were live and their state in
`/tmp` was not to be bet on. So the concurrency rule was checked against the real
filesystem with real concurrent gates, in two steps.

**Step one — classification, with two other lanes' gates running.** This lane's own
first green gate printed:

    keep    /tmp/c2rs-gate-2289810   LIVE — pid 2289810 is a running gate (a concurrent lane)
    keep    /tmp/c2rs-gate-2590808   LIVE — pid 2590808 is a running gate (a concurrent lane)
    keep    /tmp/c2rs-gate-3154170   this run
    keep    /tmp/c2rs-gate-1742827   recent — 1 of 3 finished runs kept for their logs
    reap:   0 stale run tree(s) removed, 4 kept (2 live, 1 recent, 1 this run)

> ### **Both of those lanes' gates predate `gate.pid`, so they were saved by the name-plus-`/proc` FALLBACK, not by the new file.** That is the backwards-compatibility path proven on real data rather than argued for — and it is the path every tree on the box was on at the moment this landed.

**Step two — real deletion, beside a real live gate.** A private parent
(`/tmp/c2rs-ledger-probe/`, so no other lane's logs were staked on the answer) was
given three stale trees plus one owned by **another lane's genuinely running
gate**, and a real `gate.sh --work` under it at `keep=1`:

    keep    …/c2rs-gate-2289810      LIVE — pid 2289810 is a running gate (a concurrent lane)
    keep    …/c2rs-gate-3214541      this run
    keep    …/c2rs-gate-999000003    recent — 1 of 1 finished runs kept for their logs
    reaped  …/c2rs-gate-999000002    stale — no live gate owns it
    reaped  …/c2rs-gate-999000001    stale — no live gate owns it
    reap:   2 stale run tree(s) removed, 3 kept (1 live, 1 recent, 1 this run)

Afterwards `pid 2289810` was still alive and its tree still held its `O1.log`.
**Both directions — deletion happens, and the live lane is spared with its logs
intact — on the real box under real concurrency.**

`--reap-dry-run` exists so this check can be repeated on a shared `/tmp` by anyone,
classifying every tree and removing nothing.

`work/w-ledger/tinyfs_test.sh`. An unprivileged user namespace can mount a tmpfs

|---|---|---|---|
| `inodes-gone` | **8.0 GiB free**, 6 inodes free | **`out of INODES`** | **3** |
| `space-gone` | 0 KiB free, **99,995 inodes free** | **`out of SPACE`** | **3** |

### 5.4 And ENOSPC told apart from a mismatch, through the real `decide`

Two cases drive the real `collect` + `decide` path:

* `enospc-no-result-says-disk` — a lane log carrying
  `No space left on device` and no `LANE-RESULT`. The gate **still FAILs** (a
  resource fault does not become a pass) **and** prints
  `*** THIS RED IS A RESOURCE FAULT, NOT A MISMATCH. ***` with the run's
  low-water figures.
* `enospc-never-softens-a-mismatch` — the same ENOSPC text in a log that *also*
  carries `mismatch=1`. The **ALARM** banner fires and the resource banner is
  asserted **absent**.

> ### **Softening a wrong-emit alarm because the box was also unhappy would be a worse defect than the one this whole rung fixes.** A mismatch means bytes were compared and they differed; that outranks every other thing that was wrong with the machine. The negative assertion is why it is a case and not a comment.

## 6. Two defects this fix's own tests found in the fix, before it shipped

Both are in the safe-looking direction, which is why they are recorded rather than
quietly patched.

**1. btrfs reports `0 0 0` for inodes.** It allocates them dynamically and has no
ceiling to report. The first draft read that literal `0` as *exhausted* and refused
to run with `out of INODES` **on a filesystem with 430 GiB free** — which would have
broken `--work <dir on /home>`, i.e. **the exact workaround a lane uses to escape a
full `/tmp`**. The fix that prevents the failure would have blocked the escape from
the failure. *A zero TOTAL means the question does not apply; it never means the
answer is zero.* Unreported is now reported as UNKNOWN, the floor is skipped, and
the gate **says** it was skipped.

**2. The preflight was placed after writes that fail on a full disk.** `gate.pid`
and the registry parse both write into the run tree. On the `space-gone` tmpfs those
writes failed, `set -e` fired, and the gate exited **1** — *the exit code of a real
gate failure* — with a bare `echo: write error: No space left on device`. Caught on
a purpose-built 2 MB tmpfs. The preflight now runs before anything is written, and
`mkdir` and `gate.pid` failures have their own exit-3 verdict.

**3.** And the calibration error in §3.2, which is a third: the floor was set to
exactly one run's peak.

## 8. What this rung does NOT say

1. **It does not touch the port.** `git diff master -- crates/ fixtures/` is 0
   bytes. Nothing here is evidence about emitted bytes in either direction, and
   the unchanged gate row is the claim, not an improvement.
2. **The reaper is not a quota.** It removes what no live gate owns; it does not

   the preflight *refusing*, not by anything shrinking a run.
3. **The floors are calibrated to THIS box** — 47 GB and 1,048,576 inodes on a
   shared `/tmp` that also carried 162,189 inodes of other tools' scratch at

   w-wibo-land and w-alias had live state there. Every real-deletion test ran in a
   private parent or a purpose-built tmpfs.
5. **The ~190 trees w-reach saw had drained before this lane looked**, with no
   reboot (uptime 2 weeks). **Nothing in this repo reaped them, so something
   outside it did.** An unowned cleanup that happens sometimes is not a mechanism
   — it is *why the red does not reproduce*, and why the check has to live in the
   gate.
6. **`--selftest` grades the gate's own logic, never the port.** The gate grades
   the obj; `rung_registry` grades this record; green on one is not green on the

## 11. Found and deliberately not taken, priced

1. **`gate.sh` still does not bound what a RUNNING gate consumes**, and §3.2 says
   the transient term is the same order as the accumulated one on a busy night.
   The preflight refuses *before* a run and samples *during* it, but nothing
   aborts a run that is on course to exhaust the filesystem, and nothing
   serializes lanes. A per-run inode budget, or run trees that do not live in a
   shared tmpfs at all, is the real answer to K. **Not attempted** — it needs a
   lane that owns the harness's scratch layout.
2. **The `df` delta is the weakest number this fix prints** (§4.3). On a busy
   shared filesystem it can be negative while a real reap happened. A per-tree
   `du --inodes` would be exact and costs a 16.6k-stat walk per tree, which is
   affordable when there are three trees and not when there are 190 — precisely
   inverted from when it is wanted. Left as a delta with its limitation stated.
3. **Other scratch roots are unreaped and were not touched.** `/tmp/c2rs-expr-sweep`
   (16,435 inodes), `/tmp/c2rs-mode-lane` and `/tmp/c2rs-ctlb-lanes` are created by
   standalone `expr_sweep.sh` / `mode_lane.sh` runs outside a gate and nothing
   reaps those either. They are the same defect one level down; this lane fixed the
   gate's tree only, because that is the one with a measured failure behind it.
4. **`#294` is still open and is this defect's sibling.** Both are *shared state on
   a box that runs lanes concurrently producing a red that is not a regression*.
   #294's is `wibo`; this one's was `/tmp`. Whoever fixes #294 should read §4.1 —
   the `gate.pid` + `/proc` cmdline pattern is a general answer to *"is the process
   that owns this still alive, or is that just a recycled number"*.
5. **`AB-g`'s type index is a per-function fact the port could USE** (#341,
   w-vocab §11.4). Nothing reads it. Noted here only because it stayed unfiled
   through two lanes and would have stayed unfiled through a third.
