### 3.2 THE WRITE SET IS LATENT — the second registered axis does not exist

Prereg §3 named the write set as an axis: the producers return two values, only
the first is instructions, and a dropped `writes.push` beside correct moves would
move bytes elsewhere. **Mutation M-W tested exactly that and came back GREEN**,
and so did two escalations:

| # | mutation | `cargo test -p c2-core` | 391 fixtures vs real c2 |
|---|---|---|---|
| M-W | `sym_slots_ops` drops **every** `writes.push` | GREEN | **391 pass, 0 fail** |
| M-W2 | `permute_args_parts_ops` drops the cycle's pushes | GREEN | **391 pass, 0 fail** |
| M6 | the passthrough returns **all eight** `ARG_REGS` | GREEN | **391 pass, 0 fail** |

`w-s1c2` §2.2's rule is that **green proves nothing** until the edit is
independently shown to be semantically different — and these are: poisoning the
set with eight registers flips *every* callee-saved copy from trailing to
hoisted at the one site that reads it. So the question is why nothing moved, and
the answer is that nothing reaches that site:

* `call_seq_parts` refuses `permuted || has_lit` whenever `seq.saved` is
  non-empty (`calls.rs:1303`), and
* `c2_il`'s `seq_call_arg_slots` refuses a `SymAddr` slot **by name**
  (`callseq-multiarg-sym`), so `sym_slots_ops`' write set never arrives either.

The only list left is the **identity**, whose marshalling is the passthrough and
whose write set is empty.

**Measured as well as read, and the first probe asked the wrong question.** An
`assert!(writes.is_empty())` at the read site **fired 8 times** on the workload
and killed the scan — because `writes` there is also fed by the
single-argument arm's `vec![RET_REG]` (`calls.rs:1371`), which has nothing to do
with the marshalling. Narrowed to ask only about a *marshalling* write set, the
assert **never fired across all 878 TUs**: scan exit 0, `match 25`,
`mismatch 0`, `fnbyte-exact 35912`. That is an instrument-defect catch on this
lane's own probe, of exactly the class the standing rule names.

**So the doc was wrong, and it had been since `d2c3917a4`.** *"which Class B
needs in order to decide whether a callee-saved copy has to be hoisted"*
describes a coupling two later refusals closed; the version this lane wrote
three commits earlier inherited it. It now says **latent**, says why, and says
what would reactivate it. **The set stays computed here** rather than derived by
a second walk, for `GAPS.md` §6 #9's reason: the day either refusal widens, a
re-derived set is the copy that drifts.

**This is a documentation defect about a DEPENDENCY, not a placement** — so it
is not §5.1's shape — and unlike §5.1 it was found by **a mutation coming back
green**, which is a finder this project has and rarely reads that way. Prereg §6
item 7 registered the write set as the control this project lacks; the truer
statement is that it is not under test **because it is not reachable**.

## 4. Criterion B — the COST CLAUSE axis: RESOLVED on the third run, and the first two were measuring the instrument

Protocol: `scripts/cost_arms.py`, three arms including a `cmp`-verified null,
balanced `--rounds 9`, per-fixture minimum over rounds, paired, reference column
discarded. **n = 157** in every run.

**Both refusals watched failing on deliberately broken input first**
(`CLAUDE.md`): `--rounds 8` over 3 arms → *"the rotation does not complete"*,
**exit 1**; a null arm that is not byte-identical → *"it cannot be the null"*,
**exit 1**.

| run | arm list | box | **null arm** | **null split** | **tip** | tip split |
|---|---|---|---|---|---|---|
| 1 | `base, nulldup, tip` | load 4.4 → 2.4, **CPU-contaminated** | +0.29 % [+0.14, +0.44] | **62 %** | −0.49 % [−0.70, −0.29] | 32 % |
| 2 | `base, nulldup, tip` | load **1.4 → 2.1**, idle | +0.46 % [+0.32, +0.61] | **71 %** | −0.44 % [−0.62, −0.26] | 32 % |
| **3** | **`base, tip, nulldup`** | load 2.2 → 1.4 | **+0.06 % [−0.05, +0.17]** | **54 %** | **−0.55 % [−0.72, −0.39]** | **27 %** |

**Run 3 is the answer**, by the protocol's own doctrine: *"what certifies a
given run is the null arm's own reading — CI containing zero and a split near
50 % — and that is a check to perform per run, never an assumption."* Run 3's
null contains zero and splits **54 %**; runs 1 and 2 fail that check.

**THE COST OF S1c (i)'s LAST PRODUCER IS −0.55 %**, CI **[−0.72, −0.39]**,
median −0.57 %, aggregate −0.63 %, slower on **42 of 157 (27 %)**. The port got
**faster**, and the direction is the same in all three runs (−0.49 / −0.44 /
−0.55, splits 32 / 32 / 27), which is the second reason to believe it.

**What −0.55 % is and is not.** The population is 157 fixtures and almost none
of them enter the argument-marshalling path at all, so this is **not** a
measurement of the six converted functions — it is at least as likely to be
whole-binary layout and inlining moving under `rustc`. It is reported as the
tip's cost because that is the quantity the COST CLAUSE asks for, and it is
reported with that caveat because the alternative is to let a real number carry
a false attribution.

### 4.1 #3468's fix was necessary and is NOT sufficient — a cyclic rotation balances POSITION, not ADJACENCY

`cost_arms.py` rotates as `arms[r % n:] + arms[:r % n]`. Over 9 rounds each arm
holds each position exactly three times, so #3468's balance criterion is met and
the script's own refusal is satisfied. **Adjacency is not balanced.** One
3-round cycle of `base, nulldup, tip` has adjacent pairs:

```text
  r1  base nulldup tip     base -> nulldup ,  nulldup -> tip
  r2  nulldup tip base     nulldup -> tip  ,  tip -> base
  r3  tip base nulldup     tip -> base     ,  base -> nulldup
```

`nulldup` runs immediately **after** `base` twice per cycle and **never
immediately before it**. Any order-dependent carryover lands on the arm axis
exactly the way #3468's incomplete rotation did, and completing the cyclic
rotation does not remove it.

### 4.2 The diagnostic — registered before the run, and it is a CONTROLLED REVERSAL

Registered before run 3, verbatim: *"I am re-running with the arm list reordered
to `base, tip, nulldup`, which reverses exactly one thing: `nulldup` then always
precedes `base` and never follows it. **If adjacency is the cause the null's
sign flips negative; if it is the box or the binary, the null stays around +0.3
to +0.5 %.**"*

Reordering to `base, tip, nulldup` gives `base→tip ×2`, `tip→nulldup ×2`,
`nulldup→base ×2` per cycle — the exact reverse of the one relation under test.
**Nothing else changed**: same three binaries, same 9 rounds, same
`--port-iters 2000`, same box, same fixture set.

**The null went from +0.46 % / 71 % to +0.06 % / 54 %.**

**The registered prediction is a MISS as worded and the hypothesis is
confirmed.** The sign did not flip negative; the artefact **collapsed to zero**.
That distinguishes two mechanisms the prediction did not: "whichever arm follows
`base` pays a penalty" predicts a flip and is **refuted** — in the new order
`tip` follows `base` and read −0.55 %, slightly *more* negative, not less.
What the data support is weaker and sufficient: **an arm's reading depends on
its place in the declared list, and a byte-identical arm's is not zero unless it
happens to sit in the right one.** For a null arm, any nonzero reading is an
artefact by definition, so this localizes the artefact to the rotation.

**Three alternatives are excluded by the design rather than argued away:**

* **The box.** Run 2 *started quieter* than run 3 (1.4 vs 2.2) and produced the
  **worst** null of the three. Load does not order these runs.
* **The contamination.** It touched run 1 only; run 2 was clean and worse.
* **The distinct inode.** Named in advance by the coordinator: `nulldup` is a
  byte-identical copy *at a different path*, so it has its own inode and page
  cache entry. That is true in **all three runs equally**, so it cannot explain
  the difference between them. (It remains a candidate for any residue; run 3's
  residue is +0.06 % with a CI containing zero, so there is none to explain.)

### 4.3 What this does to #3468 — a qualification carried beside it, not over it

#3468's **measurement stands** (`rounds=8` null +0.57 %/76 %; `rounds=9` null
+0.09 %/51 %). Its **conclusion** does not: *"The floor is not the box. It is
the rotation… The protocol can resolve well under half a percent on this box. It
never could not."* The first half is now better supported than that lane could
show — the floor is the rotation, and this rung reversed one rotation relation
and watched the floor vanish. The second half is wrong as stated: **completing
the cyclic rotation is not what makes it resolve**, and `w-s1c3`'s single clean
null reads as one draw from a distribution whose mean depends on arm order.

That is the same shape as the error #3468 itself corrected — a predecessor's
number inherited as a property of the hardware — arriving one level up.
**#3468 is merged and pushed, so the amendment is carried in #3495 citing it,
never by editing it** (`w-r8idiom`'s convention).

**The fix is DIAGNOSED, NOT BUILT.** A rotation that balances adjacency — all
`n!` orders, or a sequentially-balanced Latin square — changes an instrument
four lanes depend on and owes a re-run of their numbers against it. §9 prices
it. What this lane leaves behind instead is a **cheap standing procedure**: run
the null arm in at least two different list positions, and believe the run whose
null certifies itself.

## 6. `scripts/scan_pair.sh` — committed, and then a defect filed against it

**#3451's complaint applied to the other instrument.** `w-s1c3` committed
`cost_arms.py` because a protocol retyped every lane cannot accumulate its own
corrections. It did **not** commit the scan pair — the instrument that had
already produced two live defects (#3426's four-valued corpus, #3470's arm that
graded nothing and exited 0). Four lanes have retyped it. It is committed.

Every guard was watched **failing on deliberately broken input** before the
script was trusted, with fake binaries so nothing depends on a real scan:

| case | input | result |
|---|---|---|
| g1 | arm logs `SKIP: toolchain absent`, exits 0 | VOID, **exit 4** |
| g2 | arm emits no `gap-metric` line | VOID, **exit 4** |
| g3 | two identical arms | IDENTICAL, exit 0, `0 lines over 2 / 2` |
| g4 | one metric value differs | DIFFERS, **exit 1** |
| g5 | arm exits 7 | VOID, **exit 4** |
| g6 | workload edited mid-arm, HEAD unmoved | VOID, **exit 3** |
| **g7** | **a SECOND edit to an ALREADY-DIRTY file** — HEAD *and* path set both unmoved | VOID, **exit 3** |

**g7 exists because g6 was not enough, and that is a defect against this lane's
own commit from four hours earlier.** The first version digested
`git status --porcelain -uno`, which is the **set of modified paths**. It does
not move when a file already listed as modified is edited again — the porcelain
line is byte-identical either way. That is precisely `w-3475`'s hazard: HEAD
stable across all four reads while the compiled bytes changed. Reproduced on
`../dc3-decomp` in 4 ms:

```text
  after edit 1   porcelain 183619428431   content  344768490326
  after edit 2   porcelain 183619428431   content 2974227181337
                           ^^ UNCHANGED            ^^ MOVED
```

`git diff HEAD | cksum` costs **0.004 s** on this workload, so the weak version
was never buying anything. The stamp is HEAD + path set + **content** now.

**This lane's own pair is unaffected and was not re-taken**: `../dc3-decomp` was
**clean** — porcelain empty at all four reads — and a clean tree at a fixed
commit is content-pinned by the commit id, so the hazard structurally cannot
reach it. That is luck about the corpus state, not a property of the guard,
which is the whole reason the defect was filed.

**NAMED AND PRICED, NOT BUILT:** pin the corpus rather than observe it —
reflink the workload into `work/<lane>/dc3-pin` and scan that, so a mid-pair edit
is *impossible* rather than *detected* (`w-3475`'s valid pair). ~14 GB
CoW-shared plus a reap step. The script header says so, so a reader does not
mistake detection for immutability.

## 8. What these controls could NOT catch

1. **A producer conversion is required-zero BY CONSTRUCTION** — `ops_to_bytes`
   is concatenated encoder output (`mop.rs::ops_tests`) and every `encode_X` is
   `mop_X(..).word()` — so a green gate is **weak evidence about these
   conversions specifically**. What it *can* catch is an op dropped or
   reordered: M1, M3, M4, M5, M7.
2. **`mod incumbent` proves PRESERVATION, never correctness.** Only real
   `c2.dll` under wibo does the latter.
3. **`fnbyte-refused-parse` is ~70 % of the function population**, so no
   identity diff can see a defect in a shape the parser refuses.
4. **`hatch-red` is `REFUSED` at both ends**; per #1406 neither run establishes
   what a full run would.
5. **A required-zero byte delta is silent about everything that is not a byte**
   (#3336) — demonstrated twice here, by §5.1 and §3.2.
6. **A latent output is invisible to every instrument this project has.** §3.2's
   write set is computed, returned, documented and unreachable. Nothing in
   `gate.sh`, the sweep, the cross, the debug lane or the 878-TU scan can fail
   on it, and the only reason this lane knows is that a registered mutation came
   back green three times and was chased rather than re-worded.
7. **AND THE ONE THIS LANE LEARNED THE HARD WAY: a guard can be correct about
   its own question and still not be the guard you wrote it to be.** §6's first
   digest answered *"did the set of modified paths change?"* and was written to
   answer *"did the corpus change?"*. Those differ by exactly one case, and it
   is the case that voided another lane's pair the same day.
