## 1. What it admits, and what it refuses

`27 <TYPE>` is the **byte-offset add**. It pops a byte offset that the
preceding `33` pushed as an ordinary literal, adds it to the address under it,
and **re-types** the result. A member designator is one `27` per step (`&t->s.b`
is two), and c2 lowers the whole run as a single `addi rD,rBase,<sum>` — or an
`addis`+`addi` pair when the sum leaves the 16-bit immediate.

**It admits**, in `parse_expr_classed` and nowhere else that was not already
admitting it:

* a run of `27` steps of any length, summed, whose every step's TYPE is in
  `designator::is_ptr_any` — the **literal whitelist**
  `designator::walk_offset_adds` already enforces at this exact byte for the
  four leaf consumers;
* the result as a **`ValueClass::Ptr4`** on `parse_expr`'s class stack, which
  keeps `cstack_ok` true across the construct;
* consequently, the whole expression grammar downstream — the width-4
  reinterpret (`2C`), integer arithmetic over the converted value, and the
  straight-line selector's existing `addi` fold.

**It refuses**, each under its own census key and each with a fixture:

| refused | key | why |
|---|---|---|
| `27` whose TYPE is not a modelled pointer | **`expr-off-add-ptee`** (new) | one fact one locator: a `27` the *address leaf* would refuse is refused here too |
| a malformed TYPE at the `27` | `expr-off-add-type` | unchanged |
| `02`/`03`/`04` over a pointer | `expr-ptr-arith` | c2 **scales** those by the pointee width; `27` carries the scaling already. This is the whole reason the two have different opcodes |
| `28`, the subscript offset add | `expr-op-0x28` | `parse_expr` has no arm for it; it is **not** assumed to behave like its neighbour |
| a computed address in a call with **≥ 2 arguments** | `call-arg-computed` | board **#149**, and §4 is why |

## 1.1 The three parts of the slice, and which one did not exist

`ROADMAP_SLICING_2026-08-21.md` §5 defines a Phase-1 row as *"one value-type
variant + its type resolution + one general lowering"*. Measured against the
tree, those three had three different starting points, and **the doc's ordering
note is half right**:

> *"C1 is a promotion, not a construction — `designator.rs` already resolves the
> offset and width for four consumers. Largest row, cheapest work; take it
> first."*

| part | what was there | what C1 did |
|---|---|---|
| **the general lowering** | **all of it.** `[Load, Lit(k), Add]` per step, folded by `codegen::fold` into one `addi` | **nothing.** No new `crates/c2-core` file, no edit to an existing one. Confirmed by the byte judge, not by reading: `(int)&t->s.b` is `38630008 4e800020` |
| **the type resolution** | `designator.rs`'s whitelist, for the four *leaf* consumers — **not** at the expression position, which took whatever `read_type` returned | pointed the expression arm at the same predicate |
| **the value-type variant** | **wrong**, and stated as a fact in a comment | replaced. See below |

So "a promotion" is right about the lowering and the whitelist. It is wrong
about the mechanism: **the promotion is not of `designator.rs` into
`parse_expr`. It is of an env-gated sink that was already a complete acceptance
rule.**

`parse_expr`'s `0x27` arm existed at base, behind `C2RS_SINK_OFF_ADD_ARG=expr`
(board **#143**). Board **#661** had already named what it was — *"NOT a
measurement-only sink; a real widening behind an environment variable"*,
because it ends `ops.push(IlOp::Add)` with no poison arm. Board **#364** found
the same thing from the other side and scored its own prediction a MISS for it.
What the sink lacked was the two things above **and** a grade.

### 1.2 The value model was wrong, and the correction is the measurable half

The sink cleared `cstack_ok` at the `27`, with this comment:

> *"The byte-offset add's second operand is IMPLICIT — it is the TYPE, not a
> stack value — so the postfix discipline the class stack models does not hold
> across this token."*

**That is false.** The offset is pushed by the preceding `33` as an ordinary
literal; `27` pops two and pushes one, exactly like `02`. The sink's own
grammar comment, eight lines up, said so (`B9 t · 33 <int> 0 · 27 · …`).

It is not a tidiness point. Clearing the model forced the end-of-walk pointer
guard onto the coarse whole-expression fallback, which cannot see a `2C` that
moved the value out of the pointer class *before* an arithmetic operator.
MEASURED on `work/w-c1/probes/p1.cpp`, one env var apart on the base binary:

```text
  int f(T* t, int i) { return (int)&t->s.b + i; }        expr-ptr-arith:mid
  int f(T* t)        { return (int)&t->s.c - (int)&t->s.a; }  expr-ptr-arith:mid
```

Both are `Port=Match` at this tree. The sink papered over its own defect with a
*third* whole-expression flag, `scaled_arith`, wired into a special-case branch
at the top of the `ptr_arith` decision. C1 **retired that flag**: the fact it
carried — *`27` is unscaled, `02` is scaled* — now lives in the value model,
where `ptr_arith_exact` states it exactly.

### 1.3 The decision surface

`off_add_sink_enabled()` → **`off_add_admitted()`**, reading **`C2RS_OFF_ADD`**,
**ON by default**. Per `docs/rungs/README.md`'s decision-surface clause
(`ROADMAP_SLICING` §6 rule 7) the default is the only configuration anything is
graded at, and `=off` restores the pre-C1 parser **exactly**:

```text
  C2RS_OFF_ADD unset   fixtures/cpp/wc1_offadd.cpp -> 22/22 in class
  C2RS_OFF_ADD=off     fixtures/cpp/wc1_offadd.cpp -> 0/22, all 22 expr-op-0x27
  base binary          fixtures/cpp/wc1_offadd.cpp -> 0/22, all 22 expr-op-0x27
```

That third line is why the parameter is worth keeping: the lane's counterfactual
is re-runnable on any later tree without a checkout, instead of being a number
in this file. `C2RS_SINK_OFF_ADD_ARG` is **not** renamed or removed — it still
drives `shapes::calls::off_add_arg_sink`, the call-argument sink (§4).

## 4. STOP-AND-REPORT: board #149, the call-argument off-add — **not shipped**

The wave-7 fence (decision 9) lets this lane create new `crates/c2-core` files
and forbids editing existing ones, and asks for the exact edit it would have
made. Here it is.

**What it would take.** `SlotArg` (declared in `crates/c2-il/src/func/mod.rs`,
plus the `pub(crate)` twin in `func/body/mod.rs`) gains a variant for a computed
address:

```rust
    /// A formal plus a constant byte offset — `&t->s.k` as a call argument.
    ComputedAddr { param: usize, off: i32 },
```

and every `match` over `SlotArg` in **`crates/c2-core/src/codegen/calls.rs`**
(sites at 722, 1112–1140, 1300, 1418, 1676, 1792–1796, 1827–1828) and
**`codegen/cond_tail.rs`** gains an arm. That is a `c2-il` declaration whose
consumers are all in files this lane may not touch — **the fence is hit by
construction, not by choice.** The port stays honestly unable to represent the
shape, and `the_computed_address_schedule_is_not_established_and_has_no_slot_variant`
stops compiling the moment the variant is added, which is the tripwire
§9.19.5 left for exactly this.

**And the edit is NOT the work.** The variant is an afternoon; **its position in
the permutation walk is the row**, and that rule was searched over three grids
under a pre-registered protocol and **REFUTED**: the fitted rule is right on
**656 / 754 (87.0 %)** — one call in eight mis-emitted, silently, on a shape the
878-TU differential is blind to (§9.17.7 measured that blindness directly: the
`ceiling` sink emitted `mr` where c2 emits `addi` and the workload still read
6 match / 0 mismatch / disagreement 0).

**What C1 DID ship out of #149's population, and why it is safe.** The
**one-argument** call. §9.13.1's ALARM is that the `n ≤ 1` case is where
address-last and address-second agree and a wrong ordering rule ships green —
so the class is fenced at the point where *there is no ordering question at
all*: one argument, one register, no other move to order against.

Measured, and the fence is the tree's own, not one this lane added:

```text
  a1(&t->s.b)                 ok  int-tail-call     addi r3,r3,8  ; b a1
  a1(&t->s.b) from r4         ok  int-tail-call     addi r3,r4,8  ; b a1
  a1(&t->x)                   ok  int-tail-call                     b a1
  a1(&b->tail)  (wide)        ok  int-tail-call     addis;addi    ; b a1
  a2 (&t->s.b, k)             GAP call-arg-computed:eof
  a2b(k, &t->s.b)             GAP call-arg-computed:eof
  a3 (k, m, &t->s.b)          GAP call-arg-computed:eof
  a3b(&t->s.b, k, m)          GAP call-arg-computed:eof
  a3c(k, &t->s.b, m)          GAP call-arg-computed:eof
  a4 (&t->s.b, &n->z, k, 3)   GAP call-arg-computed:eof
```

All six negatives are in `wc1_offadd_neg.cpp` §C. **A green verdict on any of
them is a mis-emit, not a win.**

**Read before probe** (§6 rule 6): the next move on #149 is not a fourth grid.
The rule lives in c2's own argument-permutation walk, and
`whitebox/READ_PLAN_2026-08-21.md` is the index for pricing that read. This lane
did not price it — it is a characterization lane's work, not a slice's.

**Zero `crates/c2-core` lines.** The fence was never binding on what shipped.

### 8.2 Why it was that cheap — three reasons, and only one of them generalises

1. **The acceptance rule already existed**, complete, behind an env var, with a
   measured counterfactual attached (#143/#150). C1's real content was a type
   gate, a value-model fix and *a grade*. **This does not generalise**: the ten
   constructs of §3 do not each have a shipped sink. Grep says the sink family
   is four variables (`docs/IL_DECODE_REACH.md` §12) and only this one was ever
   a widening.
2. **The general lowering was free** because `[Lit, Add]` was already in the
   `IlOp` vocabulary and `codegen::fold` already folded runs of it. **This may
   generalise to some rows and certainly not to C4** — §5's own inverse-trap
   note says lowering a `double`, a pointer, a 64-bit pair *"is far more work
   than its decode"*, and C1 is the one row where the decode's product was
   already an op the lowering emits.
3. **The prior measurement existed and was good.** #150 predicted the
   conversion and the successor to within 0.2 %. **This generalises only where
   a sink was run**, which is where (1) applies.

### 8.3 What C2–C10 should be priced at, on this evidence

**Not 2–4 weeks, and not one session either.** The honest read:

* **C1 is the floor of the range, not a sample from it.** The slicing doc said
  so — *"largest row, cheapest work"* — and picked it first for that reason.
  Quoting C1's cost as the per-slice cost would be `CEILING` §6.1 item F's
  error (a figure against an unmeasured denominator).
* **The lowering is what varies, and C1 measured none of it.** C1's lowering
  cost was zero because its construct lowers to an op the port already emits.
  **C2 (intrinsic), C3 (bind), C4 (load-type)** each lower to something the
  port does not; C4 is fenced by §5's own note.
* **The conversion-per-slice number is now measured once and it is small.**
  +8 emitted functions, +12 bodies, **0 TUs**, against ~390,000 renamed bodies.
  If the other nine behave like this — and the residue table says C1 was the
  *largest* — then Phase 1 as a whole moves `match` by roughly nothing, and
  `ROADMAP_SLICING` §1's *"no slice pays in `match` until many have landed"* is
  confirmed rather than assumed. **Coverage is still the hard one.**
* **The evidence, not the code, is the unit of cost.** Three scan pairs, two
  full gates and an armed suite dominated this lane's wall clock by roughly
  10:1 over writing the change. That ratio is a property of the *protocol*, so
  it transfers to C2–C10 unchanged — a slice whose code is 5× C1's is not 5×
  the lane.
* **The recommended next slice is not C2.** It is whichever construct has a
  shipped counterfactual, because that is the reason C1 was cheap.
  `docs/IL_DECODE_REACH.md` §12 now lists exactly four, and after C1's
  retirement three remain — `C2RS_SINK_REL` (#420, the compare family = **C7**),
  `C2RS_SINK_BRANCH` (#440) and `C2RS_SINK_CHAIN` (#660). **C7 is the only
  Phase-1 construct with a shipped sink**, so it is the one row whose price is
  known before it starts. Both of those sinks are **poisoned**, though, which
  means their counterfactual measures a *decode* and not an *acceptance* — so
  C7 is C1-shaped in its measurement and not in its cost.
