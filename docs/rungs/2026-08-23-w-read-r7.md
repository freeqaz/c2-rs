## The three results

**1. The structural model SURVIVED the tap.** The region-finder rule reproduces
the observed region partition on **1,461 of 1,461** graded pairs over 60
fixtures — 100.00 %, at every region length 1–14. The edge-latency mechanism
reproduces **10 of 10** of `P_DAG.md` §5's published latencies from the raw
image bytes. Positive control (the `stage counts` invariant) and negative
control (`/Od` fires zero scheduler sites) both green.

*Qualification, published rather than buried:* only **three of the region
rule's seven exits** ever fired, so 1,461/1,461 grades three clauses, not the
rule. P3.1 is scored **PARTIAL**, not HIT, because the prereg demanded two
populations and this lane landed one.

**2. The ORDER model was never confronted, and that is the finding.** Not
because the model failed and not because the tap failed: **c2's scheduler does
not reorder anything on this corpus.** The final schedule — run 4, the one that
fixes emitted instruction order — changes the order on **3 of 357 functions
(0.84 %)**. Two independent instruments agree (region-walk differencing and the
tap's own function-walk verdicts). The prereg registered in advance (§6.3,
decline criterion 4) that a trivially small reordered subset means P4 is
reported **UNGRADED with the fraction published** and no agreement rate quoted.
A simulator returning its input scores 98.9 % / 99.2 % here; that number
measures the corpus.

This is `/QXSTALLS` in the shape §3 of the prereg predicted: reordering is
nearly a function of body length (0.00 % at every function length ≤ 7, which is
355 of 456 pairs) and the corpus is dominated by short bodies. **The larger
result is that this repo's fixture corpus cannot validate a scheduler model in
either direction**, which also re-prices R7's own premise — the read plan's
*"F0 re-priced 8 → 4 raw"* assumed a confrontation that is not available on
this corpus at any price.

**3. The 13,104-configuration search COULD NOT HAVE SUCCEEDED**, and one reason
**binds on the residual exactly.** Four independently sufficient structural
reasons, none of them in `schedule.rs`'s own one-line assertion. The binding
one: every producer→store edge in a store run addresses matrix cell `(1,8)` —
verified to be **the only cell of all 121** whose value is not a latency but a
runtime branch, giving **5** to the address operand and **2** to the data
operand. The search ranged over *one scalar latency in 1..6*; the residual
needed two, simultaneously, on edges out of the same producer. The R4 shape,
reached by a different mechanism.

## The instrument that lied, and what fixed it

P6.2 was registered as an instrument-lies check because `P_DAG.md` never states
the latency matrix's cell width and a wrong guess yields a plausible matrix.
Run as designed it scored 0/9, 0/9 and **1/9** at widths 1, 2 and 4 — **it
rejected the correct width.** Width 4 is right; the check failed because its
premise was wrong in a way no probe could expose: the cells are **tags**, not
latencies. The fix was not a better probe, it was reading `FUN_10c1c1d4`. The
clearest instance this lane produced of read-before-probe.
