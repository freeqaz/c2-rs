## §1 — What "closing" means, stated before the read

The refusal in `WB_R8IDIOM_FINDINGS.md` §6 names three unread things. This
lane closes iff it can publish, each `[R]`:

1. **A name** — a string in the image, or an unambiguous role-name derived
   from a table c2 itself indexes by opcode.
2. **The operands** — arity, and what each slot holds.
3. **The contract** — what a pass is required to do when it sees one, stated
   as the conjunction of the predicates that actually test for it.

**Partial is an acceptable and expected outcome.** If (1) does not settle,
(2) and (3) may still settle, and the honest publication is (2)+(3) with (1)
still refused. **A refusal that names what is missing beats a name that fits.**

## §2 — Predictions about the NAME

**P2.1 — there is a name table in the image that covers `0x2e4`.**
Predicted **YES**. Reasoning I am committing to in advance: the opcode field
is *shared* between machine opcodes (`0x001`–`0x294`) and tuple opcodes
(`0x2af`, `0x2c6`, `0x2d4`, `0x2e4`, `0x317`), and a backend with an ICE
reporter and a `/Bd` narration path almost certainly names both. **This is
deliberately the TIDY prediction** — see §6.

**P2.2 — the mnemonic table `0x10b1b260` itself extends past `0x295`** and its
row `0x2e4` holds a valid `char*`. Predicted **YES**, ~55 %. `w-r8idiom`'s
claim B says *"the mnemonic table ends at `0x295`"*, but `ref/P_ENCODE.md`
§2.1's `_last = 0x295` bound is stated about the **base-word / encode-form**
tables, and inheriting it to the mnemonic table is an inference nobody
measured. **If P2.2 hits, `w-r8idiom` claim B is partly wrong and I say so.**

**P2.3 — the name will contain neither "`b`" nor "`nop`" as a whole word.**
Predicted **YES** (~60 %): a marker minted by `ehexcept.c`, `fg.c`, `inline.c`
and `p2symtab.c` and expanded to an inert word is unlikely to be named after
either its IL shape or its final encoding.

**P2.4 — the name is EH-flavoured.** Predicted **NO** (~65 % it is *not*).
`fg.c`, `inline.c` and `p2symtab.c` all mint or test it and none of the three
is an EH file, so a name mentioning `eh`/`catch`/`throw` would contradict the
mint set. Registered because the seductive story is exactly the EH one.

**P2.5 — my registered failure mode for §2.** A scan for "arrays of pointers
into a string blob" **will find several arrays that are not name tables**, and
the temptation will be to read `table[0x2e4]` off the first one that looks
dense. **Mitigation, registered before running:** any candidate table must
reproduce **known** rows as a control — `0x290 → "emit"`, `0x276 → "nop"`,
`0x21 → "bc"`, `0x22 → "bca"` — and I must **watch the control fail** on a
deliberately wrong table base before quoting any row. A table that cannot fail
its control is measuring itself (`w-r8idiom` defect 1: four for four is the
tell).

## §4 — Predictions about the OPERANDS and the CONTRACT

**P4.1 — of `w-r8idiom`'s eight `mov ecx,0x2e4` rows, at most three are
mints.** Predicted count: **2 or 3**. (Stated as a number so it can be graded.)

**P4.2 — a `0x2e4` tuple carries a branch target.** Predicted **YES** (~60 %):
something in slot `+0x34` or the operand list resolves to a label/symbol. The
alternative I am registering against is that it carries **nothing** and is a
pure marker.

**P4.3 — the final-expansion arm ignores the tuple's operands entirely.**
Predicted **YES**, high confidence (~90 %). `w-r8idiom` printed the whole arm
and it touches no field of the incoming tuple. Registered because the
*consequence* is the interesting part: whatever `0x2e4` carries is consumed
**before** expansion, so the contract lives in its consumers, not its expander.

**YES** (~55 %): both `0x10b3c2cc` and `0x10b9f04e` test `+0x34` in the same
breath as the opcode. Predict `+0x34` is a *target/handler pointer* that is
non-null exactly on the `{0x2e4, 0x21, 0x22}` class.

**P4.5 — the contract will NOT be expressible in one sentence.** Predicted
**YES** (~60 %). Registered as my anti-tidy hedge in the one place I think mess
is real: "what a pass must do with a `0x2e4`" is likely different in the
scheduler, the merger and the loop recogniser.
