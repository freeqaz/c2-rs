## 1. What was asked, and what the brief got wrong

R5 was dispatched as *"the **189-arm** IL-record→codegen dispatch"*, priced
**15–25 days** — the largest read this project has funded — with the
instruction to verify the coordinator's addresses first because *"every
coordinator-supplied address list this project has issued has needed
correction by the lane that used it."*

It needed correction. **There are 62 arms, not 189.**

`189 = 0xBD − 0x01 + 1` is the size of the *opcode* domain. It was read off
`labels/W-IL.tsv:36`'s *"table 0x10bc4152, ops 0x01..0xBD"* as if the table
were opcode-indexed, and it propagated into five documents
(`READ_PLAN` §3/§4, `C2_MAP.md:1012`, `STEP5_PRICING:139`,
`WHITEBOX_LEVERAGE:89`, `ARCHITECTURE_PROPOSAL:968`). The switch is MSVC's
two-level form: a 189-entry **byte** table at `0x10bc424a` mapping `op−1` to
an index in `0..61`, then a 62-entry **DWORD** table at `0x10bc4152`.

Nobody had parsed it — `ref/ADDR.tsv:755` records `0x10bc4152` as `data`,
size 4, `unknown`.

**Consequence for scope: the brief expected a partial read and told the lane
to "land the largest evidence-complete increment and be precise about the
boundary". The population was 62, so the lane read all of it — 62 of 62 arms
and 189 of 189 opcodes.** The honest boundary is not in the arms; it is one
level down (§4).

## 2. The result the read was funded for

`READ_PLAN` §4 asked for the select-vs-decode split and said *"it has never
been located."*

**It is located, and it is a number: `0x294`.**

Every immediate in `[0x100, 0x400]` across all 62 arms was collected
mechanically — 26 distinct values, of which **exactly one is ≤ `0x294`**, and
that one (`0x200`, with `0x400`) appears only as a flag bitmask in an `or`.
Every node opcode the dispatch mints is ≥ `0x2af`. `P_ENCODE.md` §2.1 fixes
the machine opcode space at `0x001..0x294`. The ranges do not touch, and
there is a 26-value gap between them.

The constants are confirmed to *be* opcodes by a round trip inside the read:
arm 20 mints `0x2af`, and arms 14 and 56 test for it at `node+4` — the field
`P_ENCODE.md` §9.2 calls *"opcode-or-address-mode"* on a machine tuple. **One
field, one numbering, two disjoint ranges.**

So **there are three stages where the project's framing has two**: the
dispatch decodes `.ex` into an IR tree in the `≥ 0x295` space; something
lowers `≥ 0x295` → `≤ 0x294`; the encoder emits words. That *explains*, rather
than merely notes, why `wb-select`'s addresses are a disjoint set from
`0x10bc2xxx`.

Board **#3359** is refined in both directions rather than confirmed: its
observational half is upheld **and now explained** (no tap can see the seam
because the intermediate never reaches an obj), its structural half —
*"there is no intermediate"* — is wrong, and its pessimistic conclusion
survives on entirely different grounds (76 callees and six pieces of
cross-token state, not entanglement with selection).

## 3. The prereg, and the misses

**11 HIT · 5 MISS · 1 SPLIT · 4 UNGRADED.** The prereg was the first commit on
the branch, `52fa9d7bd`, and provably precedes the commit that taught the
tooling to parse the table.

Three misses worth carrying forward:

- **P1.2** registered a distinct-arm bracket of **[100, 170]**; the answer is
  **62**. I applied R2's 111→79 lesson but carried its *ratio* across —
  "ranking instruments measure themselves", instance six, this time turned on
  my own prediction rather than on a work-ranking.
- **P2.3** registered the pessimistic reading of #3359 and the binary
  disagreed. This is the most useful miss in the lane.
- **P4.1** predicted arm 9 tests the `0x4000` bit the reader sets for `0x27`.
  **Nothing in all 5,080 bytes reads that bit** — the constant occurs exactly
  once in the body and writes a *function* flag. The reader's `0x27` case and
  this dispatch are not one mechanism at two addresses, which is why
  `0x10bbfebb` is now named as the highest-value unread function this read
  exposes.

Four predictions are UNGRADED and both reasons are reported rather than
excused. **P5.1**'s three sampling strata became unnecessary once the
population turned out to be 62 — a full read is strictly stronger than any
sampling plan, and `--sample` remains in the instrument, unused.
**P6.1/6.2/6.3 were VOIDED**: all three predict counts of a *machine* opcode
per IL opcode, and the read refuted that premise. The registered probe design
silently assumed the two-stage model the read then disproved.

## 4. The boundary of the read, stated honestly

| population | read | denominator |
|---|--:|--:|
| distinct arms | **62** | 62 (100 %) |
| opcodes dispatched | **189** | 189 (100 %) |
| callees named, depth 1 | 76 | 76 |
| **callee bodies read** | **0** | **76** |

**The read is complete at the level it claims and empty one level down.** 61
arms route into 76 distinct direct callees over 174 call sites; **19 of 61
arms are DEFER**, their semantics entirely below the depth-1 bound. The four
largest callees are 2,763 / 2,282 / 1,174 / 1,128 bytes.

**What the unread remainder contains:** not arms — there are none left — but
those 76 bodies, which on this evidence is where the IR tree is actually
constructed, and is a strictly larger read than this one was.

**What no control in this lane can catch**, led by the one that is structural
rather than a tooling gap: this seam's output is an in-memory tree in a
private opcode range and **appears in no artifact**. `READ_PLAN` §3's *"the
tap cannot see this seam"* is a fact about the compiler. Every per-arm row in
`P_ILRECORD.md` §3 therefore stays `[R]`; the probe confirms the *range*
claim, not the arm readings.

## 5. The method result

The **first** confirmation probe appeared to refute the lane's central claim:
the mnemonic table `0x10b1b260` returns `blectr`, `bltlr`, `twle`, `twlgt` at
four of the minted opcodes. Those are the stride-16 extended-mnemonic table
read through a stride-12 walk — **exactly the trap `P_ENCODE.md` §2.1
documents by name**, with the same signature it records.

The replacement probe takes its predicate from that same section, which read
R2 marked `[O]`: `machine_opcode(N) ⇔ form_table[N] ≤ 113`.

```
CONTROL    machine space 0x001..0x294 : 660/660 = 100.0% pass
TEST       opcodes FUN_10bc2d7a mints :   0/25  =   0.0% pass
BACKGROUND indices 0x295..0x400       :   4/364 =   1.1% pass
```

A lane that quoted the first result would have published a false refutation
of its own central claim. `P_ENCODE.md` §2.1's value is now measured: it is
the difference between #3416 and its opposite.
