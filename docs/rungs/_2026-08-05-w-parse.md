## 3. #564 — the axis IS the base symbol, and **the control is the finding**

`docs/ORDER.md` §5 names the axis as the number of base symbols: eight
single-symbol cells of `xboxheap`'s statement shape emit the **rank-0**
producer first; `xboxheap`, with two, emits the **count-1** producer first.
Eight controls against one, on one declared axis.

**It differs on four axes and only one was declared.** `w-order2`'s generator
builds every producer of a cell from ONE kind (its tier 5 crosses the kind and
never mixes two inside a cell), uses three distinct formals as fillers where
`xboxheap` uses `this` twice, and never binds a reference. So I crossed all
four on `xboxheap`'s own word — 36 cells, `work/w-parse/grid.py` tier X:

```
one symbol   Pr11 S0 Pr10 S1 S3 S2 S4 S5      rank order, store order 0 1 3 2 4 5
two symbols  Pr10 S0 Pr11 S1 S2 S3 S4 S5      first-consumer, store order = SOURCE
```

**identical for all six producer-kind combinations (`LL AL AA AR LA LR`) and all
three filler mixtures (`FFF`, `FTT`, `TTT`) at each level.** The two-symbol row
is `xboxheap`'s emitted body instruction for instruction.

> ### **Prereg R2 is REFUTED and R3 is REFUTED.** I registered that the real axis would turn out to be the producer KIND mixture and that the symbol alone would change nothing. Both halves are wrong, and the incumbent — `ORDER.md`'s symbol axis — survives contact with a 2×2×3 it had never been shown. I registered R2 as "the one I most expect to be wrong, because `w-pair`'s H4/H5 died claiming exactly this class of axis"; that is what happened.

### 3.1 The control nobody had run: **it is the BIND, not the offset**

`ORDER.md`'s eight controls store to `p->mK` and `xboxheap` stores to
`l.mNext` where `E& l = mListHead`. Those are different *offsets* as well as
different symbols. `work/w-parse/grid2.py` separates them: every cell is
generated twice, once as `E& l = p->e; l.eK = v;` and once as
`p->e.eK = v;` — **the same destination bytes, the same base register `r3`,
the same displacement, one IL symbol apart.**

```
m_011_010_d   p->e.e1 = v      Pr11 Pr10 S1@r11 S0@r10 S2@r11    REORDERED
m_011_010_r   E& l; l.e1 = v   Pr10 Pr11 S0@r10 S1@r11 S2@r11    SOURCE order
```

> ### The reference **bind** is the axis. A sub-object addressed directly is one symbol and schedules like one; the same sub-object bound to a reference is a second symbol and pins the order across it. Board **#580**.

**566 `ref`/`direct` pairs, 100 of which emit different bytes** — the other 466
are cells where the schedule had no reordering to give up, so the axis is
invisible in them and a grid without the discriminating shapes would have
concluded the bind is free. That is `docs/STORE_SCHEDULE.md` §3's `D5` cell —
*"a bound reference `B& l = h->lh` is its own symbol"* — reproduced on 100
cells instead of one, and it is the reason `ORDER.md` §5's "two symbols"
reading is right for the wrong stated control.

## 4. What the multi-symbol regime IS — measured, and **NOT closed**

`work/w-parse/grid2.py` builds 5,562 cells: every 2-producer word of length
3–5 crossed with every non-trivial symbol mask, with and without unproduced
fillers, and with the second symbol as a bound reference **and** as a second
pointer formal. `work/w-parse/model.py` scores four rules on them, so the
number below is a comparison and not a score.

### 4.1 The STORE order — `SYMORDER`, and it reduces to `ORDER` exactly

> **SYMORDER (store order).** Rank the run's distinct producers globally by
> (use count desc, first-use asc). A store's rank `j` is its producer's
> position among **its own symbol group's** producers in that global order.
> A store with rank `j` may not occupy position `< u + j`; **two stores
> through different symbols may not be reordered past each other**; if nothing
> is allowed, source order wins.

| population (all-constant cells) | IGNORE (`ORDER`) | PAIRWISE | SOURCE | **SYMORDER** |
|---|---:|---:|---:|---:|
| fit, full sequence | 63.0 % | 93.7 % | 85.7 % | **94.1 %** |
| fit, multi-symbol only | 48.9 % | 91.4 % | 80.2 % | **91.9 %** |

**Control: on `w-order2`'s own 809 single-symbol cells SYMORDER's store order is
ORDER's, 809 of 809.** It is a generalisation, not a replacement.

**It is not closed.** The residual is structured — it concentrates on cells
whose leading store is *produced*, where the group floors are one too strong —
and 92 % is not a rule. **Nothing is shipped from it.**

### 4.2 The PRODUCER order under two symbols — **both candidates REFUTED**

This is the half `#564` actually asks about, and it is the one I could not
close. Over all-constant cells with ≥ 2 producers:

| | rank order (`ORDER`'s) | first-consumer in the final store order (`w-alloc`'s) |
|---|---:|---:|
| single-symbol | **857 / 857 (100 %)** | 822 / 857 (95.9 %) |
| **multi-symbol** | 4459 / 5053 (88.2 %) | 4860 / 5053 (96.2 %) |

> ### Neither formulation is the rule. `ORDER`'s rank order is exact on one symbol and wrong on 594 multi-symbol cells; `w-alloc`'s first-consumer order is wrong on 35 single-symbol cells (three-producer words such as `t2_000122`, where the count-1 producer is consumed before the count-2 one). **`order.rs`'s refusal of a multi-symbol run is correct as it stands and I did not touch it.** Board **#582**.

### 4.3 A premise of three landed docs is REFUTED: the producer KIND is *not* irrelevant

`docs/STORE_SCHEDULE.md` §2 states, as a measured negative, that *"the
producer's kind is completely irrelevant to the permutation"*, and
`w-order2`'s tier 5 was built to confirm it. It confirms it only for cells
whose producers all share one kind.

y_fvvv_F_LA_s0   { m0=f0; m1=1; m2=&t1; m3=&t1; }      addi r11,r3,76 · stw r4 · li r10,1 · stw r11,8 · stw r11,0Ch · stw r10,4

Same statement structure, same registers, same producer slots — **different

producer is a constant and the higher-ranked one is register-derived. `AL`,
`AA` and `AR` differ from `LL` on **0 of 94**. Board **#581**. It does **not**
touch `xboxheap`,

## 5. The `mr rN,r3` slot — from **n = 1** to a rule at **716 / 716** (prereg R4, HALF)

`docs/STORE_SCHEDULE.md` §5 records `xboxheap`'s live-range save of `this`
across the trailing call as *"one instance. Not a rule."* `work/w-parse/grid3.py`
is its grid: 716 member functions `M* f(...) { <store run>; h(f0); return this; }`,
crossing the produced word, the fillers and their identity, the symbol
partition and the producer count. **Every one carries the `mr`; 0 cells carry
an unclaimed token.**

**The substitution is checked, not assumed.** `work/w-parse/probe1.cpp`
compiles a real constructor beside the member function: the two bodies are
byte-identical, all twenty instructions, `mr` slot included. Using member
functions is only what lets each cell carry its own name through the listing.

> ### **THE RULE.** Let `P` be the number of distinct value producers and `u` the length of the **leading run of unproduced stores in the FINAL store order**, capped at 2. `mr rN,r3` is emitted immediately before store slot
> ### `m = P + u − 1`, and `m = 1` when `P = 0`.
> **716 of 716.** `xboxheap`: `P = 2`, `u = 2`, `m = 3` — after `mSize`, `mFreeHead` and `mCount`, which is where c2 puts it. Board **#583**.

Three earlier statements of the same quantity, all refuted by this grid:
`m = P + u − 1` with `u = min(2, #unproduced)` scores **520 / 716**; with `u` =
the unproduced stores among the first two slots, **658 / 716**; only the
leading-*run* reading reaches 716.

**R4 is a HALF.** I registered *"it lands immediately after the last store slot
the unproduced head occupies"* — that is `m = u`, which is 2 for `xboxheap` and
the answer is 3. The registered *shape* is right (it is a function of the
schedule and not of the source statement index) and the registered floor of 12
cells is met 60× over; the point estimate is wrong.

### 5.1 The same constant, found twice, in a place `ORDER` had it wrong

The `u` this rule needs — the **leading run** of unproduced stores in the final
order — is also the `u` `ORDER`'s **layout** clause needs. `ORDER.md` §1 says
*"the first `u = min(2, #unproduced)` producers go one apiece before store
slots `0 … u-1`"*. On `ORDER`'s own grid the two readings coincide, because its
floors put the unproduced stores in the head; on a multi-symbol run they do
not, and `min(2, #unproduced)` puts a producer before a slot that holds a
*produced* store. Switching the layout to the leading run moved SYMORDER from
84.6 % to 94.1 % and changed **nothing** on the 809 single-symbol cells. Board
**#584** — a correction to `ORDER.md`'s wording that is a no-op on everything
`ORDER` was measured against.

## 8. Three premises of my own brief, checked and REFUTED

1. **"The `.pdata` flag word is a shipped constant `40 00 14 04`."** It is
   **computed**: `crates/c2-core/src/coff/pdata.rs:71`'s `pdata_record` builds
   `UNWIND_THIRTY_TWO_BIT | (func_len/4) << 8 | prolog_len/4`. `w-tu3`'s row
   (board #506) and `BOARD.md`'s copy of it were true when written and are
   stale now. `xboxheap`'s real word decodes as `FuncLen 20 words · PrologLen
   4 words · bit 30`, and the port would compute exactly that.
2. **"`xboxheap` is blocked on three parse facts, and nothing else."** §7. The
   two lanes that "confirmed" it confirmed something narrower and true — that a
   *schedule*, an *allocation* or an *order* cannot unblock a *parse* — which
   does not imply the converse.
3. **`ORDER.md` §5's eight controls differ from `xboxheap` on one axis.** They
   differ on four (§3). The conclusion survives; the control did not, until §3.1
   built the one that isolates it.
