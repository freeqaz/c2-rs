### 3.1 GRID F3 — the six axes, and the ONE that is a regime boundary

| axis | levels | verdict |
|---|---|---|
| **A** store count before the call | 0, 1, 3, 6 | **free.** 1/3/6 all transfer; 0 is a different production (`expr-call-in-expr-recv-load-then-plumbing-0x3A`, not `expr-op-0x27`) |
| **B** store base | one base; two bases | **free at one base.** The two-base cell (`f3_b2`) emits and is left refused, matching the parser's existing multi-symbol gate |
| **C** the call's **argument setup** | none; writes `r4`; writes `r3` | **THE BOUNDARY — §3.2** |
| **D** callee kind | member on `this`; free fn; member on another object | **determined by C.** Free and other-object both put a non-`this` value in slot 0, so both force C = writes-`r3` |
| **E** receiver slot 0 | `this`; a formal | same — E and C are one axis, not two |
| **F** return-value use | ctor `return this`; void; `return <call>`; discarded int | **only the ctor is framed — §3.3** |

### 3.2 The boundary is **the argument setup writing `r3`**, and it is syntactic

Board #870 states the boundary as *"a trailing call that takes an ARGUMENT
breaks the run."* Measured here, that is one level too coarse, and the
refinement is what puts `xboxheap` on the safe side:

```text
  f3_a3_c0_dthis_fctor      Alloc(initSize)   member on `this`, args already placed
      stw 5,16(3) ; mr 31,3 ; stw 3,0(3) ; stw 3,4(3) ; bl ; mr 3,31
      ONE base (r3) throughout, no setup, `mr 31,3` additive     <- #866

  f3_a3_c1b_dthis_fctor     Alloc(size)       setup is `mr 4,5` — writes r4
      stw 5,16(3) ; mr 4,5 ; stw 3,0(3) ; mr 31,3 ; stw 3,4(3) ; bl ; mr 3,31
      ONE base (r3) throughout. The run STILL TRANSFERS.

  f3_a3_c1_dfree_fctor      g1(initSize)      setup is `mr 3,4` — writes r3
      mr 31,3 ; stw 5,16(3) ; mr 3,4 ; stw 31,0(31) ; stw 31,4(31) ; bl ; mr 3,31
      base SWITCHES r3 -> r31 mid-run, setup INTERLEAVED             <- #870
```

`c1b` is the cell that separates them, and it was in the grid because axis C was
enumerated by *what the setup writes* rather than by *how many arguments the call
has*. **The gate a framed seam owes is therefore `the call's argument setup is
empty, or writes no register the run reads`** — a syntactic predicate the reader
can compute from the actual list alone, so census and gate cannot disagree.

`xboxheap`'s `AllocatePageBlock(initSize)` is a member call on `this`: slot 0 is
`this` (already r3), slot 1 is `initSize` (already r4). **Empty setup.**

### 3.3 `x6` is on the WRONG SIDE of it — the handover's first gift, refuted

`x6` and `f3_a3_c1_dfree_fctor` are the same configuration: a store run, then a
**free** function taking `initSize`. Its callee cannot receive `initSize` in r4,
so c2 emits `mr 3,4`, which destroys `this` in r3 — and then the object must
already be in `r31`, the base of every following store must be `r31`, and the
`mr 31,3` moves to run index 0.

Board #1106 prices `x6` at **2** and calls it *"`xboxheap`'s ctor minus the
member address and one store, carrying the same frame, the same open-coded
`std r31`/`ld r31`, the same `.pdata` and the same `bl`."* Every one of those
four is true and **none of them is the axis**. It is `xboxheap`'s ctor minus the
member address, one store, **and the callee's receiver** — and the receiver is
the thing that decides the regime. This is `w-front2` §5.1's own lesson, one
lane later and on its own handover: *obj shape and price are uncorrelated at this
end of the frontier.*

**Axis F fires the same way.** Only the constructor form is framed at all:

```text
  f3_a3_c0_dthis_fvoid        frame words 0   -> TAIL CALL `b ?Alloc`
  f3_a3_c0_dthis_fretcall     frame words 0   -> TAIL CALL
  f3_a3_c0_dthis_fdiscardint  frame words 0   -> TAIL CALL
  f3_a3_c0_dthis_fctor        frame words 9   -> FRAMED
```

That is board #869 (*"a framed store run needs two calls, or one value live
across one call"*) reproduced in this family: the ctor's implicit `return this`
is the one value live across the one call, and without it there is nothing to
preserve and c2 tail-calls behind the run. Three of the four cells that *look*
like the target are not the target.

## 4. The two refusals `w-front2` did not price

### 4.1 `codegen::alloc`'s mixed-kind refusal is LIVE ON THIS BODY

`xboxheap`'s run has **two producers of different kinds**: the interior address
`addi r11,r3,8` at **2** uses and the literal `li r10,0` at **1**.
[`alloc::allocate`] refuses every mixed-kind run (board #836: over 81 mixed
cells clause 1 alone is wrong on 29, clause 2 alone on 35, the refusal wrong on
0). `w-seam` measured the narrow lift that would open exactly this cell and
**refused that too** (board #868): at the `addi-interior` spelling it is 12/12,
at `slwi` it is **0/12**, and `ProducerKind` cannot tell them apart.

`w-front2` §2 lists `xboxheap`'s CODEGEN price as **1** — #844's composition
seam — and does not mention #868, although `alloc.rs`'s own module doc ends:

> *"A lane that widens the parser to admit an interior address as a store value
> makes the mixed run reachable and inherits every paragraph above."*

This lane is that lane, and it inherits it. **There is a way through and it is
named rather than taken**: the reader's F2 widening admits *only* `IlOp::AddrOf`,
which is the `addi-interior` spelling and nothing else — a `slwi` value is a
*computed* value `parse_store_stmt` already refuses on its own terms. So the
spelling gate that #868 could not express in `ProducerKind` **falls out of the
reader's own vocabulary**. That is a real route and it is one refusal, not zero:
`ProducerKind` still has to gain the distinction and `allocate` still has to be
lifted, gated on strict use-count advantage, and re-gated.

`codegen::order::tests::xboxheap_allocation_is_still_refused_and_the_answer_it_owes_is_recorded`
asserts both halves — the refusal is live, and the registers the real obj demands
(`addi → r11`, `li → r10`) sit beside it, so a lifting lane inherits a target and
not merely permission.

### 4.2 The REFERENCE BIND is load-bearing, and the two spellings emit different bodies

`codegen::schedule`'s own `xboxheap_constructor_is_derived_not_fitted` reproduces
the real TU — but only by giving the two `&mListHead` stores a **second base
symbol**, justified in its comment as *"through the bound reference's own
symbol"* (board #839). Nothing established whether that was load-bearing.
`w-front2`'s ladder varies the bind (`x3` bound, `x5` direct) but only on a run
with **one** producer, where one symbol and two give the same answer — so the
ladder could not see it. `w-seam` §3.4 holds the binding **fixed on purpose**,
and says so.

A declared post-hoc holdout (`work/w-heap/grid_addendum/h1_xboxheap_direct/`,
named as post-hoc in its own header per this lane's prereg F-4) removes the bind
at the full width:

### 8.1 The near-miss worth recording

This lane wrote `check("..0.11", "P0 S0 P1 S1 S2 S3 S4 S5")` — `xboxheap`'s
emitted order against a **one-symbol** model — and it **failed**, returning
`P1 S0 P0 S1 S3 S2 S4 S5`. For about a minute that read as *"the shipped
schedule does not reproduce the frontier's cheapest TU"*, which would have been
this page's headline and would have been **wrong**: `schedule.rs` already carries
the same body correctly under a two-symbol model, and the string the "failure"
produced turned out to be the exact body of the **direct spelling** (§4.2), which
had never been compiled. The failing assertion was not a refutation, it was the
other cell.

Two standing rules caught it, in this order: *grep the crate for an existing
model over the same fact before adding one* (the brief's own instruction, aimed
at readers, and it fired on a **test**), and *when two instruments disagree, go
get an obj*. Both new tests exist because that near-miss was chased instead of
published.
