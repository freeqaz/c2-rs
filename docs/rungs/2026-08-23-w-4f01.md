## 1. What it admits, and what it refuses

`4F 01 <payload>` is the `.ex` **source-line record**. Its payload is a **VI32**
varint (`c2.dll` `0x10c1f9e9`): one byte when the value is `< 0x80`, otherwise
the escape byte `0x80` followed by four little-endian bytes. So:

| source line | record |
|---|---|
| `< 128` | **3 bytes** |
| `>= 128` | **7 bytes** |

Four sites in this tree read a fixed three. They read VI32 now.

**Refused, deliberately, and asserted by a test so it is not later mistaken for
a bug**: a lead byte in `0x81..=0xFF` is a *negative* one-byte VI32 in the real
reader; the adopted reader **refuses** it rather than sign-extending. A source
line is never negative, so it is unreachable from c1xx-produced IL. This is the
fail-closed idiom already used by `func::readers::read_varint` and
`func::ehscope::opt_line`, and the narrowing was **registered in the prereg
before the code was written**, not discovered afterwards and called a feature.

These are legitimate because `4F 02 20 00` is exactly a **4-byte** record
(`P_SUB4F.md` §4: sub `0x02`, format `73`, VARU payload), so the `4F 01`
following it is a **separate** record carrying its own VI32.

**The module-end failure mode is the sharper one and deserves naming: it did not
mis-read the record, it REFUSED it.** The decoder looked for the trailing `4D`
at a fixed `p+7`; with a wide line the `4D` is four bytes further along, the
check failed, and `try_ex_token` returned `None` — so the entire module-end
marker fell into an opaque run. A silent structural loss, not a wrong value, and
invisible to every round-trip control for the reason §4 gives.

The three variants now carry `{ line: i32, wide: bool }` — **the idiom
`ExToken::Lit` already used in that same file** for the identical `0x80`-plus-four
escape. `wide` is carried rather than re-derived so a narrowly-representable
value that c2 chose to encode wide re-encodes to the bytes it was parsed from.

### The sweep

A thorough sweep of `crates/` (including `#[cfg(test)]`), `scripts/`, and the

## 3. Red before green — twice, both from real captured bytes

**A fix that was never seen red proves nothing**, so both halves were run
against the unmodified tree first.

### 3.1 Decode — `22 passed; 3 failed` → `25 passed; 0 failed`

The three tests assert **only consumed width and token sequence, never the
payload type**. That is deliberate and it is what makes them a red rather than
a compile error: `matches!(t, ExToken::Stmt { .. })` is a legal pattern against
a tuple variant too, so the same test file runs on both trees.

```
assertion `left == right` failed: a source line >= 128 escapes to `0x80` + 4, so the record is SEVEN bytes
  left: 3
 right: 7
assertion `left == right` failed: 4 (the `4F 02` record) + 7 (the wide `4F 01`)
  left: 7
 right: 11
line 258: decoded a phantom Add out of the line payload — [Stmt(128), Add, Ss]
```

**The third line is the finding, not the first two.** `0x02`, `0x03` and `0x04`
are `Add`, `Sub` and `Mul` in that very decoder, so a three-byte read of a
seven-byte record leaves the line number's own low byte exactly where an opcode
is expected. Lines 258/259/260 synthesize `Add`/`Sub`/`Mul` respectively.

Two details worth keeping: `Stmt(128)` is the constant `0x80` that **every** wide
line collapsed to — precisely what R9's re-grading of its own captures predicted
when it scored 2/10 — and the bytes in all three tests are a **real capture** of
a five-line function under `#line 258`, hex-dumped at this lane's tip, not a
construction.

## 4. The control that CANNOT go red, and why that is the sharpest thing here

**Registered in the prereg before the run**, and it held: `ir0-roundtrip-broken`
reads **0 on both base and tip, over 870 of 870 bundles** — and it would read 0
**however wrong the reader was**. The four mis-skipped payload bytes coalesce
into a `Span::Opaque` run that re-encodes byte-identically, so the container
round-trip is lossless *on the defect itself*.

`STATUS.md` trap 0 says a green control is a statement about the **population**
it ran over. This is stronger: this control is green over the **shape**, so no
amount of corpus widening would ever have turned it red. The scan's own comment
calls `ir0-roundtrip-broken` *"a defect count with a known answer of 0"* — true,
and it is a defect count for a **different** class of defect than the one that
was live.

**And the defect had teeth on a live instrument path.**
`crates/c2-harness/src/search/moves.rs` picks its mutation sites with
`matches!(t, ExToken::Add | ExToken::Sub | ExToken::Mul)`. The permuter —
named in `CLAUDE.md` as one of goal (1)'s two consumers — was being handed
**mutation targets manufactured out of source-line payload bytes**.

### The candidate that was discarded, because it could not fail

The obvious body — six one-line `int f(int,int){return a+b;}` over lines
122..132 — is `Port=Match` and its capture **does** carry wide markers (3 narrow
+ 4 wide). It also stays **just as green with the width rule deliberately
re-broken**, because for that class the port never reaches the varint line
reader at all.

**A fixture that carries the shape is not the same as a fixture that fences it**,
and the only way to tell them apart is to break the rule and look. It was
replaced rather than kept — keeping it would have recorded an unreachability as
coverage, which is `#1148`'s failure mode.

### What the byte judge can and cannot see here — measured

**The source line does not reach the obj at the fixture profile.** Compiled from
an *identical* path, the three objs differ in 11-12 bytes and **every one lies
inside the harness's own embedded `…\out.obj` scratch path**. (The first
measurement of this compared objs from *differently named* files and looked like
a real difference; it was re-run with identical basenames before being believed.)

So these fixtures fence the width through **refusal-vs-emit**, not through
differing bytes, and three green `Port=Match` lines are **not** the proof — §3.2's
control is. The fixture headers say this too, so a later reader cannot quote the
green without the caveat.

## 9. Found and not taken

Ranked, sized, and left for whoever wants them.

1. **The `0x81..=0xFF` negative-VI32 arm is refused everywhere, in four places
   independently.** Cheap to unify into one reader; worth nothing today (a
   source line is never negative) and it would need a producer that emits one
   before it could be graded. **Do not "fix" it without such a producer** — it
   would be an ungradeable widening of a fail-closed boundary.
2. **`4F 01`'s payload is a LINE, and three doc comments said "index".** Fixed
   in `codec.rs`. **`IL_STMT_GRAMMAR.md:236-240` was not audited by this lane**
   and may carry the same wording.
3. **The other twelve payload-bearing sub-opcodes are still transcriptions.**
   `P_SUB4F.md` §4 gives widths for all 64; this lane adopted **one row**.
   `0x1f` is also VI32 and the port treats `4F 1F` as a bare 2-byte marker —
   `P_SUB4F.md` calls that *"not contradicted"*, which is not the same as
   confirmed, and `4F 1F` is the **function-start splitter the whole census
   rests on**. That is the highest-value unread row in the table.
4. **`ir0-roundtrip-broken` cannot detect a decoder that mis-measures a record.**
   A `Span`-level control that asserts *opaque runs do not grow* across a change
   would have caught this class. Sized: unknown; the shape is a per-TU opaque-byte
   census, which the scan already has the data for.
5. **No fixture exercises a `4F 01` payload between 128 and 255**, where the
   escape is present but the value still fits a byte. The twin set jumps 127 → 128
   → 100000. One more cell would close it; it is one `#line`.
