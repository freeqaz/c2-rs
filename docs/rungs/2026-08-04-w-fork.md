## 0. What this lane does not do

It moves **TU match by zero** and could not have moved it. It retires **neither**

## 1. Result, up front

Corpus: **1,000 real captured IL bundles** drawn from `work/capture-cache`
(`.ex` p50 3,358 B, max 9,636 B — the generated-sweep population), replayed at
their own captured argv. Sequential, one request in flight, `WIBO_FS_CACHE=1`,
`ulimit -c 0`, warm page cache. **Both arms run the same wibo binary and the same
guest stub**; the only difference is whether `$WIBO_FORK_SOCKET` is set. Three
interleaved rounds, load average 22–23 on a 32-thread 7950X with other lanes
live. Medians of three:

| arm | wall ms/obj | CPU ms/obj |
|---|---:|---:|
| spawn-per-obj (today's `Toolchain::replay` shape) | 7.772 | 7.230 |
| **fork server** | **2.859** | **2.623** |
| **speedup** | **2.72×** | **2.76×** |

Corpus: **60 real dc3 TUs** (`.ex` 108 KB – 2.8 MB, p50 2.0 MB —
`src/lazer/game/LiveInput.cpp`, `src/lazer/meta_ham/BlacklightPanel.cpp`, …),
three interleaved rounds at load 37–39:

| arm | wall ms/obj | CPU ms/obj |
|---|---:|---:|
| spawn-per-obj | 158.1 | 154.4 |
| fork server | 156.5 | 152.1 |
| **speedup** | **1.01×** | **1.01×** |

**The second table is the finding.** The fork server removes a *fixed* cost. On a
TU where c2 does 152 ms of work, a 6.8 ms fixed cost is 4 % and removing it is
worth nothing.

### Where the 7.23 ms goes (CPU, 1,000 reps each, same conditions)

| stage | CPU ms | cumulative share |
|---|---:|---:|
| `wibo --version` — bare loader floor | 2.24 | 31 % |
| + `LoadLibraryA(c2.dll)` and its DLL init (`c2load.exe`) | 6.80 | **94 %** |
| + the compile itself (spawn arm, small TU) | 7.23 | 100 % |
| fork + child address-space teardown + IPC (`WIBO_FORK_NOOP_CHILD=1`) | 0.803 | — |
| fork arm, total | 2.623 | — |

So the fixed cost really is **94 %** of a small-TU replay, the fork server really
does remove it, and it pays **0.80 ms** to do so. A hypothetical zero-overhead
in-process reuse would reach 7.23 / 1.82 = 3.97×; the serialised fork server
reaches 2.76×.

### One correction to `docs/PRIOR_ART.md` §1.3, in the unfavourable direction

That section prices the load path at 5.8 ms as "`LoadLibrary(c2.dll)` **and its 6
dependent DLLs**". **strace of a replay shows wibo opens exactly one file for
this: `c2.dll`.** `msobjXX`, `mspdbXX`, `msdisXXX`, `pgodb100`, `msvcr100` and
`msvcp100` are satisfied by wibo's *built-in* stub modules and are never read
from disk. And §1.3/§4's estimate of **"~10–20×, at 100 % coverage"** is not
reachable: the compile's own share was never measured there, and with it measured
at 1.8 ms of 7.2 ms, **Amdahl caps any fork server at 3.97× on this population
even if fork were free** — before the large-TU population drags the weighted
figure to 1.44×. That estimate should be corrected in `PRIOR_ART.md` §1.3, §4 row
1 regardless of what happens to this lane.

## 2. The killer probe, and it came back clean

**Question:** does `c2.dll` capture per-TU state — cwd, `TMP`/`TEMP`,
`MSC_CMD_FLAGS`, `MSC_IDE_FLAGS`, `_CL_`, `INCLUDE`/`LIB`/`LIBPATH` — at
`LoadLibrary`/`DllMain` time? If it does, forking *after* `LoadLibrary` cannot
vary that state per compilation and the fork point has to move earlier, which is
where the entire win lives.

`work/w-fork/c2probe.c` + `probe.sh`. Four modes, **identical c2 argv and
identical `-Fo` path in every one** (the path string is embedded in `.debug$S`,
so it must not vary), differing only in *when* the state was established:

| mode | before `LoadLibrary` | after `LoadLibrary` | role |
|---|---|---|---|
| `early` | real | — | baseline |
| `late` | **decoy** | real | **fork-server semantics** |
| `never` | decoy | — | power control |
| `reverse` | real | **decoy** | power control |

Result over **100 cases**, obj compared with `TimeDateStamp` zeroed:

```
cases with a usable early+late pair : 100   (early or late produced no obj: 0)
  early == late   (fork-after-LoadLibrary is state-safe) : 100 / 100   [differ: 0]
POWER CONTROLS — the probe must be able to see a difference:
  never  : produced an obj 0, aborted 100, byte-equal to early 0
  reverse: produced an obj 0, aborted 100, byte-equal to early 0
```

**The controls are the load-bearing half.** `early == late` on its own would be
consistent with the probe simply having no power over these variables. Both
controls abort **100/100** with

```
fatal error C1007: unrecognized flag '-DECOY-' in 'p2'
```

so c2 does read this state, it is read at **invoke** time, and `late` — the fork
server's exact ordering — is byte-identical to `early`. **Verdict: nothing that
matters is baked at DLL init. The fork point after `LoadLibrary` is safe.**

### Which variable, and an incidental finding worth a board row

Isolated one variable at a time: **`MSC_CMD_FLAGS` is the only one of the five
that c2 reads.** `MSC_IDE_FLAGS`, `_CL_`, `TMP` and `INCLUDE` all produce a
normal obj when poisoned.

**`crates/c2-reference`'s replay does not control `MSC_CMD_FLAGS`** — it is
inherited from whatever environment the harness was launched in. A developer or
CI runner with that variable set would silently change what the *oracle* emits,
or abort it with C1007. The capture-cache key does not include it either. This is
not a live defect (it is unset on this box) but it is an unguarded input to the
sole judge, and it is one `.env()` call to close. Reported, not fixed — this lane
owns no `crates/`.

## 3. What was built, and where

Prototype in a **worktree of `/home/free/code/milohax/wibo`**, branch
`w-fork/forkserver`, based off `main` at **`4a9dd6f`**. `main` was not touched —
lane w-wibo is resyncing it concurrently. Nothing was pushed.

| commit | what |
|---|---|
| `8b27cea` | `kernel32: add a WiboForkServe fork-server hook (prototype)` |
| `3c242f7` | `forkserver: report rusage on shutdown, add an explicit shutdown request and a no-op-child probe` |

`WiboForkServe(LPSTR buf, DWORD n)` — a wibo extension, not a Win32 API. A guest
stub does its expensive one-time setup, then calls it. The **parent never
returns**: it listens on `$WIBO_FORK_SOCKET` and forks per request. The call
returns **in the child only**, having `chdir`'d to the request's working
directory and written that request's argv into `buf` as NUL-separated strings.
Returns 0 when `$WIBO_FORK_SOCKET` is unset, so one binary serves both arms of
the benchmark and stock behaviour is preserved.

Bounded on purpose, because a fork server that leaks children is its own OOM
risk: the parent `waitpid`s each child **before** accepting the next request
(so at most one child exists), stops after `$WIBO_FORK_MAX_REQUESTS`
(default 100,000), and exits after `$WIBO_FORK_IDLE_SECS` (default 120) with no
connection. It writes a `$WIBO_FORK_SOCKET.ready` sentinel so the client waits on
a positive signal with a deadline instead of racing `connect()`.

Lane scratch, all in `work/w-fork/`:

| file | what |
|---|---|
| `c2probe.c`, `probe.sh` | §2's four-mode per-TU-state probe |
| `c2forkd.c` | guest stub: `LoadLibrary(c2.dll)` → `WiboForkServe` → `InvokeCompilerPass` → `ExitProcess`. Falls back to `c2host`'s exact behaviour when the socket is unset |
| `c2load.c` | loads `c2.dll` and exits — isolates spawn + PE load + DLL init |
| `driver.c` | one host-native A/B client (`floor` / `spawn` / `fork`) so both arms pay the same driver overhead |
| `mkcorpus.py` | extracts capture-cache entries into standalone cases, re-pointing `-il`/`-Fo`. Never mutates the cache |
| `ab.sh`, `forkbench.sh`, `baseline.sh` | the interleaved A/B |
| `compare.py` | the byte-identity gate |
| `cachesizes.py` | §5's population sample |
| `PREREG.md` | §7 |

**Not production quality and not integrated.** One request in flight, no
concurrency, no recovery from a child that hangs (the client's timeout is the
only bound), the wire format has no versioning, and `WiboForkServe` sits in
`kernel32` where a real version would want its own module. It exists to price the
idea.

**One portability bug the benchmark found**, worth recording because it is a trap
for anyone writing a wibo guest stub: **stock wibo answers `GetProcAddress` for
an unknown `kernel32` name with a trampoline that aborts the process when
called**, not with `NULL`. So `if (GetProcAddress(...))` is not a feature test —
it is a core dump. `c2forkd` gates on `GetEnvironmentVariableA("WIBO_FORK_SOCKET")`
instead.

## 4. Byte identity — 10,580 obj comparisons, 0 differing

A faster oracle that emits different bytes is not an oracle. Every comparison
zeroes the COFF `TimeDateStamp` (file offset 4..8) as the project does, and
compares **two objs written to the identical `-Fo` path** — c2 bakes that path
into `.debug$S`, so comparing across paths would manufacture a false mismatch.
`compare.py` prints the number of pairs it actually compared and **exits non-zero
if that number is 0**; `driver` exits non-zero in every mode if it produced no
objs. A fork server that silently produced nothing would otherwise look
infinitely fast — that failure mode was actually hit twice during this lane (an
`argv[0]` bug and the `WIBO_FORK_NOOP_CHILD` run) and the harness called both
failures, not speed.

| comparison | pairs | differing |
|---|---:|---:|
| fork server vs spawn-per-obj — 300-case corpus | 300 | **0** |
| fork server vs spawn-per-obj — 1,000-case corpus × 5 rounds | 5,000 | **0** |
| fork server vs spawn-per-obj — 1,000-case corpus × 3 rounds (clean run) | 3,000 | **0** |
| fork server vs spawn-per-obj — 60 real dc3 TUs × 3 rounds | 180 | **0** |
| fork server (patched wibo) vs spawn under **stock** wibo `4a9dd6f` | 1,000 | **0** |
| spawn under patched wibo vs spawn under stock wibo — *the change is inert* | 1,000 | **0** |
| probe `early` vs `late` (§2) | 100 | **0** |
| **total** | **10,580** | **0** |

The fifth and sixth rows matter independently of speed: they establish that the
wibo patch changes nothing about what the oracle emits, through the fork path and
through the ordinary path.

## 5. The honest denominator — how much of our real work is cold

The brief's own strongest counterargument was that `work/capture-cache` already
amortises this for repeat workloads, so a fork server would buy nothing. **On the
cold/warm axis that counterargument does not survive contact with the cache.** On
the *size* axis, something worse than it happens.

### 5.1 Cold is not the small case — it is nearly all of it

`find work/capture-cache -maxdepth 1 -mindepth 1 -type d`, bucketed by mtime,
2026-08-04 21:55 local:

| entries created | count |
|---|---:|
| total in the cache | 623,174 |
| on/after 2026-07-20 | 623,174 |
| on/after 2026-08-01 | 603,481 |
| **on/after 2026-08-04 (today)** | **587,033 — 94.2 %** |
| on/after 2026-08-04 20:00 | 311,368 |
| **in the hour 21:00–22:00, while this lane ran** | **63,545** |

The cache is not amortising a stable workload; it is being **filled**, at tens of
thousands of new cold entries per hour, by the concurrent lanes. And its key
includes `c2.dll`'s contents, **the wibo version string**, and the workload tree's
git identity — so a wibo bump (including adopting this one) invalidates
**every** entry once, and any tracked edit to the workload tree does the same.
There is no steady state in which this cache is mostly warm.

### 5.2 But the size distribution is bimodal, and that is what kills it

20,000 entries sampled at stride 25 across 500,000 cache directories:

```
.ex bytes: min 2691  p10 2757  p50 2802  p90 4293  p99 1313588  max 2783298
  >=   10000 bytes:   1031  (5.16%)
  >=  100000 bytes:    971  (4.86%)
```

**94.8 % of entries are under 10 KB of IL and 4.86 % are over 100 KB, with
essentially nothing in between.** The small mode is the generated sweep /
`mode_cross` corpora; the large mode is real dc3 TUs.

Weighted by that population, using §1's two measured points:

| | spawn CPU | fork CPU |
|---|---:|---:|
| 95 % small | 0.95 × 7.230 = 6.87 | 0.95 × 2.623 = 2.49 |
| 5 % large | 0.05 × 154.4 = 7.72 | 0.05 × 152.1 = 7.61 |
| **total ms per average entry** | **14.59** | **10.10** |
| | | **1.44×** |

**Half of the CPU is in the 5 % of TUs the fork server cannot help.**

### 5.3 And the cache's population is *capture* work, which this prototype does not touch

`work/capture-cache` caches `Toolchain::capture_reference` — a whole `cl.exe` run
under wibo under strace. This prototype accelerates `Toolchain::replay`, driving
`c2.dll` standalone on an existing bundle. The two overlap only partially: a
`c2rs diff` does one capture (cached) **and** one uncached replay per case (board
**#282**), and the K3-edit / IL-space-search path in
`crates/c2-harness/tests/edit_differential.rs` is pure `replay_within` on novel
bundles and is where the full 2.76× would land.

So §5.1's 587,033-entries-today number is real cold volume, but most of it is
capture volume, and **1.44× is an upper bound on what this prototype would do to
it, not a description of it.**

## 6. The follow-on this lane priced by accident, and it is the bigger one

`WiboForkServe` is generic — any guest stub can call it, and §2's probe result is
about `c2.dll`'s init, not about the hook. So the same mechanism can be pointed at
the front end. Measured on this box, 50 reps each, same conditions:

| | wall ms |
|---|---:|
| `wibo cl.exe /?` — spawn + `cl.exe` load, no front end | 8.8 |
| `wibo cl.exe /c /O1 /GS-` on an **empty** `.cpp` | **27.3** |
| same on a one-function `.cpp` (`fixtures/cpp/add3.cpp`) | 24.6 |

**The `cl.exe` pipeline's fixed cost is ~25 ms — 3.7× the 6.8 ms this lane
removed — and it is paid on every one of the 587,033 captures made today.** A
`c1xx`+`c2` fork-server stub (the pieces exist: `c1host/c1host.c` already drives
`c1xx.dll` standalone) is the lane worth commissioning. It is **not** free: the
front end almost certainly *does* read per-TU state, so §2's probe has to be
re-run against `c1xx.dll` first and may come back the other way, and the capture
path's `/Bd` echo + strace-`unlink` scrape would need rethinking. That is a lane,
not an afternoon.

## 7. Registered vs realized

`work/w-fork/PREREG.md`, written before the fork server existed.

| | registered | realized |
|---|---|---|
| per-obj wall, small TUs | 2.0–2.5 ms | **2.859 ms** |
| speedup, small TUs | 3.2×–3.9× | **2.72× wall / 2.76× CPU** |
| fork + IPC + waitpid overhead | 0.3–0.8 ms | **0.803 ms** — top of the band |
| compile proper | ~1.7 ms (by subtraction) | **1.82 ms** (by direct measurement) |
| `PRIOR_ART` §1.3's 10–20× | "not reachable, Amdahl caps it at 4.6×" | **cap is 3.97×; achieved 2.76×** |
| large-TU behaviour | not registered | **1.01× — this was the surprise** |
| population-weighted | not registered | **1.44×** |

**The prediction was slightly optimistic and the miss is entirely the fork
overhead**, which landed at the top of its registered band rather than the
middle. The compile estimate was right to 7 %. **The one thing this lane failed
to register in advance is the axis that decided it** — the dependence of the
speedup on TU size. §4 of the prereg registered that the cold *fraction* would be
computed and reported whatever it said; it did not anticipate that the *size*
distribution would matter more than the cold fraction.

### The registered decision rule, applied

| realized speedup | recommendation (registered) |
|---|---|
| ≥ 3× | ADOPT |
| **2×–3×** | **REPORT, do not adopt now** |
| < 2× | DECLINE |
| any unexplained byte mismatch | DECLINE regardless of speed |

**2.76× lands in the middle band.** No byte mismatch, over 10,580 comparisons.

## 8. Recommendation: DECLINE AS BUILT, keep the branch, re-target the mechanism

**Do not integrate this into `crates/c2-reference` now.** The reasons, in the
order that decides it:

1. **1.44× population-weighted**, because half the oracle's CPU is in the 5 % of
   TUs where the answer is 1.01×.
2. **2.76× on the favourable half is below this lane's own pre-registered 3×
   bar**, and that bar was set before any number was in hand.
3. Adopting it means the differential harness depends on a **forked wibo with a
   non-upstream `kernel32` export**, while lane w-wibo is actively resyncing that
   fork with upstream `1.2.0`. That is a real maintenance surface to buy 1.44×.
4. Adopting it **invalidates all 623,174 capture-cache entries once** (the key
   includes the wibo version string), which at the current fill rate is itself a
   large cold bill.

**Do keep the branch and the finding.** Three things are now established that
were not this morning, and each is reusable:

* **`c2.dll` bakes no per-TU state at DLL init** — the one risk `PRIOR_ART` §1.3
  flagged as unverified, closed with two power controls, 100/100.
* **A fork server under wibo is byte-exact** — 10,580 obj comparisons, 0
  differing, including 1,000 against *stock* wibo.
* **The mechanism is a 30-line `kernel32` hook** and it is written, committed and
  measured. Re-pointing it at `cl.exe`'s 25 ms fixed cost (§6) needs a new stub
  and a re-run of §2's probe against `c1xx.dll`, not new infrastructure.

### What would overrule this, and how to check it

* **If the workload shifts to IL-space search.** `edit_differential`-shaped work
  is pure `replay` on novel small bundles — exactly the 2.76× population, with
  none of the 5 % large tail. If that loop becomes the project's main consumer of
  c2 (it is the thesis's actual target per `docs/EDIT_MODEL_MVP.md`), the
  population weight in §5.2 no longer applies and the number to quote is 2.76×,
  not 1.44×. **Check:** count `replay`/`replay_within` calls per unit of real
  work, split by `.ex` size, and re-weight §5.2.
* **If someone wants the fork server concurrent.** This prototype serialises. Its
  *CPU* per obj would barely change (the 0.80 ms is per-request work, not
  contention), so concurrency raises throughput but not the ratio — the spawn arm
  parallelises too, at 86 % of linear to 8 threads per
  `docs/perf/perf_scale.csv`. **Do not expect concurrency to move 2.76×.**
* **If §6's `cl.exe` probe comes back clean.** Then the same hook is worth 25 ms
  on the dominant workload rather than 6.8 ms on a minority of it, and the
  maintenance surface in point 3 above gets amortised over a much larger win.
  That inverts the recommendation — but it is a different lane's measurement,
  and this lane declines to claim it in advance.

### Reported, not done (this lane owns no `crates/`)

* `crates/c2-reference`'s replay and capture do not pin **`MSC_CMD_FLAGS`**, and
  the capture-cache key does not include it. It is an unguarded environment input
  to the sole judge (§2).
* `docs/PRIOR_ART.md` §1.3 and §4 row 1 should be corrected: the "6 dependent
  DLLs" are wibo built-ins and are never loaded from disk, and "~10–20×" is
  unreachable — Amdahl caps a c2 fork server at 3.97× on the small-TU population
  and 1.44× on the cache's actual mix (§1).

## 9. Reproducing it

```sh
# probe (needs the toolchain; ~1 min for 100 cases)
python3 work/w-fork/mkcorpus.py work/w-fork/probe-corpus 100
i686-w64-mingw32-gcc -static -static-libgcc -O2 -o work/w-fork/c2probe.exe work/w-fork/c2probe.c
sh work/w-fork/probe.sh

# build the fork-server wibo (worktree, branch w-fork/forkserver off 4a9dd6f)
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release -DWIBO_ENABLE_LTO=OFF \
      -DWIBO_ENABLE_FIXTURE_TESTS=OFF && make -C build/release -j6

# the A/B (both arms, byte compare, interleaved)
gcc -O2 -o work/w-fork/driver work/w-fork/driver.c
i686-w64-mingw32-gcc -static -static-libgcc -O2 -o work/w-fork/c2forkd.exe work/w-fork/c2forkd.c
python3 work/w-fork/mkcorpus.py work/w-fork/main-corpus 1000 --skip 40000
ulimit -c 0 && sh work/w-fork/ab.sh work/w-fork/main-corpus 3

# the population denominator
python3 work/w-fork/cachesizes.py 20000 --stride 25
```

`work/w-fork/1033` must be a symlink to the toolchain's `1033` message dir, and
`ulimit -c 0` matters: a stub that trips wibo's missing-import trampoline dumps
core once per case.

**Every number in this doc was measured with other lanes running.** Wall clock
drifted by up to 3× between identical rounds (round 3 of the first 5-round run
read 19.2 ms/obj for a spawn arm whose CPU was 8.8 ms); **CPU did not** — which
is why every headline is quoted as a median of interleaved rounds with the CPU
figure beside it, and why the fork server was taught to report `getrusage` on
shutdown.
