## 3. What the conversion actually needed

`Primes.cpp`'s obj, from `scripts/gt_dump.py`:

```text
   1 .drectve  2 .debug$S  3 .XBLD$W  4 .XBLD$W
   5 .text  raw=64  rel=6  chars=0x60401020
   6 .data  raw=248 rel=0  chars=0xc0401040

   0000  3d400000  lis  r10,0        REFHI -> ?primes@… (+PAIR)
   0008  392a0000  addi r9,r10,0     REFLO -> ?primes@… (+PAIR)
   000c  814a0000  lwz  r10,0(r10)   REFLO -> ?primes@… (+PAIR)

  11/12 .text  13 ?NextHashPrime@@YAHH@Z
  14/15 .data  16 ?primes@?1??NextHashPrime@@YAHH@Z@4PAHA  sec=6 STATIC
```

### 3.1 `resolve_data_def` is a SECOND resolver, not a widened first

`Bindings::resolve_data`'s whole population is linkage `02`, and its doc says why
in three clauses. `resolve_data_def`'s population is exactly the two linkages
that one refuses. They are not the same question at two strengths — one asks
*"may the port reference this address without emitting a section?"*, the other
*"does this TU define an object here, and what is in it?"* — and the second
carries the bytes because the failure mode when a section's contents and its
size come from different places is board **#232**'s.

It lives on `Bindings` so the **census and the gate ask one question**. That
required `.in` to become a **constructor argument** of `Bindings` rather than
something a caller attaches: a defaulted-empty stream on one of the two is
precisely how the census comes to count a function in class that
`IlBundle::functions` refuses. `census/gate disagreement on EMITTED fns` reads
**0** at the tip.

### 3.2 The class has ZERO free immediate fields, and that is the sharp fact

`ptr_walk_loop` has two (`K0`, `K`); `if_call_join` has two. This one has
**none** — sixteen words, every register and every displacement fixed. So the
fence does all the work: a body that would need a different word must be refused
by the **reader**, never bent to fit. GRID B's `p0`/`p1`/`p2` differ in every
function name, every array name, every array value and (for `p1`) the array's
size, and their `.text` is **byte-identical**. That is the claim as a
measurement.

### 3.3 `codegen::frontier_bytes` got its caller

That file's header says of itself: *"it converts no TU, moves no numerator and
appears in no accept path."* `codegen::static_scan_loop` is the same sixteen
words, built the same way, reached by `select_function` — and
`frontier_bytes`' own tests assert **this** builder against `C2_TEXT`, the
sixty-four bytes transcribed from real `c2`, so the measurement and the emitter
cannot drift.

## 4. GRID B — the fence, six negatives and six clauses

`work/w-data/GRID.md`, frozen at `37b0ff6d` before the first `cl.exe` on it;

## 5. GRID C — the writer's first draft was WRONG, and its own refusal is what caught it (#1702)

`emit_comdat_obj` shipped placing every defined object's section **after** every
code group, and refusing more than one object because every rule in it had been
read off **one** obj. Then the positive fixture turned out to be exactly that
refusal — three cells in one file is three defined objects — and `c2rs gap` read
`codegen-gap … outside the measured class`.

**At n = 1 "grouped" and "interleaved" are the same obj.** The refusal is the
only thing that made the difference visible before a file was written.

Both rivals were frozen in `work/w-data/GRID.md` before the cell compiled. The
three-function cell says **INTERLEAVED**, in the section table *and* in the
symbol table:

```text
   5 .text(p0)  6 .data(p0)  7 .text(p1)  8 .data(p1)  9 .text(p2) 10 .data(p2)

  11/12 .text 13 ?p0 14/15 .data 16 ?a
  17/18 .text 19 ?p1 20/21 .data 22 ?b
  23/24 .text 25 ?p2 26/27 .data 28 ?table
```

**The symbol COUNT is 29 under both readings**, which is why the cell had to be
read by *order*. A lane that checked `nsym` and moved on would have banked the
wrong rule.

**R2 was not a straw man.** This same writer already interleaves `.pdata` after
its own `.text`, and `emit_obj`'s own comment records `.rdata`/`.pdata`
interleaving in `.text` order over 240 objs. What argued for R1 is that a COMDAT
`.data` is `SELECT_ANY` and not `ASSOCIATIVE` — a real difference, and not the
one that decides placement.

## 6. THE HANDOVER IS WRONG ABOUT WHICH SEAM (#1705)

The brief, from w-cfg2 §4: *"`undname`, `osfinfo` and `vswprnc` each need **two**
data symbols per body … the same seam one door further in. A lane that opens it
opens four rows at once."*

**Re-surveyed at this tip against their own objs, and it does not hold. Not one
of the three has a `.data` section at all.**

```text
  undname.cpp   6 sections: shell(4) .text(140) .pdata(8)
  osfinfo.cpp   6 sections: shell(4) .text(152) .pdata(8)
  vswprnc.cpp   6 sections: shell(4) .text(156) .pdata(8)
```

Their data symbols are **undefined externals in section 0** —
`?pairNode_vtable@@3PAXA`, `?gHeapManager@@3V_HeapManager@@A` (undname),
`__pioinfo`, `_nhandle` (osfinfo) — which is **`data_sym`/WR1's population,
linkage `02`**, the exact set `resolve_data_def` refuses and `resolve_data`
already admits. Nothing this lane built touches them.

What those three actually need is **WR1's `data_sym` widened from an
`Option<String>` to a list**, plus a framed body class: all three are framed
(`.pdata`, a `$M`/`$M`/`$T` triple), and `vswprnc`'s four undefined externals are
**all `Type` 0x0020 FUNCTION** — it needs no data symbol at all, only the
REFHI/REFLO against a code symbol w-cfg2 correctly named.

**So "opens four rows at once" is one row, not four.** The handover's *ranking*
was right — `Primes.cpp` really is the cheapest frontier TU — and its
*generalization* named a seam the neighbours are not on. Board **#666**'s shape
from a fourth side: a correct inventory and a wrong statement about what it
generalizes to.
