## 1. The result

> ### **THE REPLICATION IS EXACT, DOWN TO THE BYTES.** Two sessions were dispatched on w-callprice's R2 without either knowing of the other. Both re-derived the population, both wrote a member value-tail reader from scratch, both ran it over 878 TUs. The newly-differing sets, compared per `(TU, emit_name)` against the same base scan: **444 and 444, the identical set, symmetric difference 0** — and for **all 444** the two readers' emitted `.text` words are **byte-identical**. Census `712,238` / `39,644`, `fnbyte-exact` `36,228` unmoved, `fnbyte-differs` `2,111 → 2,555`: every published digit of §10.28 reproduces. **Board #2088.**

> ### **AND THE TWO SESSIONS REACHED OPPOSITE SHIPPING DECISIONS ON THOSE IDENTICAL NUMBERS.** §10.28 shipped the class and published the finding in its own merge headline. This lane **reverted** it, on the ground that the emitted census — the metric the goal is written in — would gain **444 claims the oracle grades wrong**, in the direction four lanes have spent the week reversing (`w-empty` −1,373, `w-fix` −143, `w-splice` −723, `w-seed` −223: **−2,462** against **+444**). Both readings are on the board; **the class stays shipped** and this row is the caution, not a revert order. **Board #2089.**

> ### **THE MECHANISM IS FOUR LINES AND TWO WORDS, AND IT HAS NOTHING TO DO WITH FLOATING POINT.** §10.28 explains the 434 through `Timer` — 31 reference words against 13, *"with `Ms()`'s `lfd`/`fcfid` among the words c2 has and the port does not"*. Reduced: for `struct T{ void s(){} int m(){return 7;} int both(){ s(); return m(); } }`, c2 emits **`38600007 4e800020`** — `li r3,7 ; blr`, a **two-word leaf** — where the port emits the same 13-word framed sequence. No FP anywhere. The class is a call sequence c2 does not emit as a call sequence. **Board #2090.**

> ### **AND THE SAME DEFECT IS ALREADY LIVE IN A CLASS THAT SHIPPED LONG AGO.** In that same four-line probe, `?m3_call@@YAHPAUT@@@Z` is **`int-tail-call`, in class at BASE**, and wrong for exactly the same reason: the port emits `48000000` (`b ?both`) where c2 emits `38600007 4e800020`. So the 2,111 `fnbyte-differs` at base **is** this population, and §10.28's rung is a new *instance* of a standing property of every call-bearing class the port has — not a peculiarity of the value tail. **Board #2091.**

> ### **WHY THE INHERITED PRICE MISSED IT: THE REPRODUCTION DIFFERED FROM THE CONSTRUCT IN ONE FIELD, AND IT IS *WHETHER THE CALLEE HAS A BODY*.** w-callprice §7-R2 hand-checked R2 on `float wcp_value_tail(O *o){ o->Poll(); return o->Level(); }` and read `bl Poll · bl Level` off c2's own `/FAsc` listing. **That listing is correct.** `Poll` and `Level` are declared and never defined in it, so c2 *cannot* inline them — and the construct it stands for is a header inline whose callees are header inlines. Both lanes' fixtures have the same property, which is why both are byte-exact and both workloads are 0 for 444. **Board #2092.**

> ### **THE LABEL LEAD §10.28 DID NOT MEASURE IS 0, AT BOTH MODES, WITH A KNOWN-ANSWER CONTROL.** The commission required it measured against the obj by w-json's counterfactual method rather than read off `LABEL_COUNTER.md`. Seven cells, two modes: the value tail — free or member, int or FP — charges **exactly** what w-mcall's statement sequence charges (+5 at `/O1`, +4 at `/Ox`), so `SeqTail::label_lead` is **0** and nothing was guessed; floating point costs **+1 at both modes**, which is `plan_labels`' existing per-TU `_fltused` slot. The FP-leaf control reads **+4 = 1 + 1 + 2**, `LABEL_COUNTER.md` §1's own table reproduced rather than quoted. **Board #2093.**

> ### **AND THREE MUST-FAIL MUTATIONS SAY THE THREE FENCES ARE LOAD-BEARING, WHICH §10.28 ASSERTS AND DOES NOT SHOW.** Dropping `CallValueFp` from `touches_floating_point` → **`Port=Mismatch @ offset 12`**, the COFF header's `NumberOfSymbols`. A `label_lead` of 1 → **`Port=Mismatch @ offset 2587`**, a label symbol, with the class still `13/13` in class. Admitting the `2C` result conversion → **`Port=Mismatch @ offset 8`** on a one-body TU where the fenced port says `NotImplemented`. **Board #2094.**

Both lanes' fixtures declare their callees and never define them, so c2 cannot
inline them and emits `bl · bl`. This lane's `wfltret_value.cpp` — thirteen

inherited price was hand-checked on**, which is §1's fifth headline and
**#1148's "one line of C++ nobody had written" at the level of linkage rather
than source**. The listing seam cannot catch it, because the listing is of the
reproduction.

## 5. The label lead — MEASURED, at both modes

w-json's counterfactual form: two TUs differing in exactly one function body,
the **same** framed `int z9(int a){ return gz(a)+7; }` second in every one, its
`$M`/`$M`/`$T` triple the readout. Real `c2.dll` under wibo.
`work/w-fltret2/gen_lab.py` + `label.sh`; raw output in `label_o1.txt` /
`label_ox.txt`.

| the first function's body | `/O1` lead | `/Ox` lead | `_fltused` |
|---|--:|--:|---|
| `leaf-none` (control) | — | — | no |
| free **int** value tail (in class at base) | +5 | +4 | no |
| free **FP** value tail | **+6** | **+5** | **yes** |
| member **int** value tail | +5 | +4 | no |
| member **FP** value tail | **+6** | **+5** | **yes** |
| member statement sequence (w-mcall's class) | +5 | +4 | no |
| an FP leaf with a pooled constant | +4 | +4 | yes |

1. **The value tail charges exactly what w-mcall's statement sequence charges**,
   at both modes and on both receiver forms — so `SeqTail::label_lead` is **0**
   and decline **D5** (*"no `Some(k)` is guessed"*) never had to fire.
2. **FP costs +1, and it is the TU's `_fltused` slot**, already charged once per
   TU by `plan_labels` off `Function::is_float`.
3. **+1 at BOTH modes.** Unlike w-bdnz's counted loop this charge is not
   mode-dependent, so a `Some(k)` would have been well-defined — and it is still
   0, because the charge is the TU's and not the class's.
4. **The known-answer control holds**: the FP leaf reads **+4 = 1 (leaf) + 1
   (`_fltused`) + 2 (a newly pooled FP constant)**, which is
   `LABEL_COUNTER.md` §1's table reproduced by this instrument rather than
   quoted by it.

## 9. What this lane deliberately did NOT do

* **It did not revert master.** The class is landed with its finding published in
  its own merge headline; that was an informed call and this rung is the second
  reading, not an override. #2089 is a caution row, not a decline of a shipped
  thing.
* **It did not build a same-TU-callee fence to rescue its own copy.** The
  distinguishing fact is whether c2 will *inline*, which is
  `INLINE_PREDICATE.md` §2's rule — **0.9716 on a 9,993-callee hold-out with a
  2.84 % residual**, deliberately unshipped by `w-splice` because *"3 % of a
  guess is a wrong emit"*. A same-TU proxy would be sound and would convert
  **0** here, since 444 of 444 are same-TU.
* **It did not re-price `chained-then-type-real-whole` (105 / 4).** Its dominant
  construct is `float DataArray::Float(int i){ return Node(i).Float(this); }`
  (`src/system/obj/Data.h:435`, 86 + 17 emitted in as many TUs) — a header inline
  whose callee is a header inline, the same shape, and never graded.
* **It did not touch `seq_call_arg_slots`.** #2026's designator ambiguity is
  intact and the blanket `SymAddr` refusal is kept.
* **It did not re-run the sweep or the cross at this tip.** No `crates/`,
  `fixtures/` or `scripts/` line differs from master.

### 9.1 P5's miss is the methodological finding

P5 was registered at 0.55 as *"`Timer::SplitMs` is not two calls and a return …
because every hand-read construct on this board has had one more fact in it than
the reading recorded"*. The source **is** two calls and a return. The extra fact
was one level down: **what c2 emits for it**. A hand-read of the source cannot
find it, and neither can a hand-read of the IL — only the obj can, and only when
the cell has the construct's own linkage.

### 9.2 P8 hit its number and the number was worthless

P8 predicted ≥ 400 converted and the answer is 444; it is the lane's most useless
correct prediction. **A conversion count is not a result unless it is crossed
with the oracle**, which is why P11 was registered beside it and why P11's
failure is the outcome. Any future PREREG on this board should register the pair
or neither — and #2095 is that instruction with a number attached.
