# W37 — the store RUN, and the free return that ends it (+36,684)

    Tag:       W37
    Slug:      store-run
    Date:      2026-07-31
    Fixtures:  w37_store_run.cpp w37_store_run_neg.cpp
    Census:    602,703 → 639,387 (24.47 % → 25.96 %), +36,684
    Record:    this document

The brief's target was **`expr-op-0x32`, +78,983**, the second-largest item on
W35's counterfactual map of where `expr-op-0x27` goes. Two things about that row
turned out to be true at once, and only the second was expected.

**It is a LIMIT, not a construct** — the store leaf's own "and the body ends
here", exactly the shape W35 found one file away. And **81 % of it is the TAIL,
not the statement list**: the largest single sub-population is a body with
*one* store whose only problem is what follows it.

## The framing correction, made before the estimate

`expr-op-0x32` measures **1,814** today, not 78,983. The 78,983 is a
*counterfactual successor*: where those functions land after W35's counterfactual
A (admit the whole indirect-load operand production inside `parse_expr`), a build
that was reverted and never shipped. Taken literally the row is one lift deep
behind a gate nobody has lifted.

**That does not make the population unreachable, and this is the load-bearing
claim of the rung.** `expr-op-0x32` is a `parse_expr` fall-through key, but the
store production does not go through `parse_expr` at all: `try_parse_store_leaf`
is a whole-body recognizer tried from `parse_segment_shape`'s `B9 | 33` arm,
*ahead* of the expression parse, and it already owns the designator, W35's shared
offset-add walk, the widths and the FP split. A body whose destination has an
offset add and which the store leaf refuses blocks at the `27` today and at the
`32` under the lift — the same body, two attributions, `GAPS.md` §6's unstable
attribution. Widening the **store production** reaches it in either world, and
the realized +36,684 came out of `expr-op-0x27` (−34,420) and
`expr-intrinsic-base-member-addr` (−2,264) with the `0x27` parse gate untouched.

So the sizing instrument was not a lift; it was a **store-production
first-blocker histogram**, which did not exist. Building one is the whole method
of this rung and it is reproducible (§8).

## What it admits

```text
  ( <scopes / line markers> <store statement> )+
  <return plumbing, void>
    | <B9 params[0] <T> [2C <T'> 00] 41 <T'>> <return plumbing>
    | <return head> <return this> <fn tail>
```

where `<store statement>` is **exactly** the statement
[`try_parse_store_leaf`] has admitted since W25 — same designator, same offset
run, same widths, same FP split, same argument-register bounds — extracted into
one `parse_store_stmt` that both recognizers call. A fourth copy of the statement
would have been `GAPS.md` §6's "one fact, one locator" one layer out from the
designator it already applies to.

**The lowering is one store per statement, in source order.** No scheduling, no
reordering, no coalescing. MEASURED before any of it was written
(`work/w37/probe/p1.cpp`, `p2.cpp`, `p4.cpp`, `p6.cpp`, at `/O1` and `/Ox`, which
agree instruction for instruction):

```text
  void s2 (S*,int u,int v)  { a=u; b=v; }        90830000 90a30004
  void s2r(S*,int u,int v)  { b=v; a=u; }        90a30004 90830000   SOURCE order
  void s2s(S*,int v)        { a=v; b=v; }        90830000 90830004   one formal twice
  void s2t(S* t,S* s,…)     { t->a=u; s->b=v; }  90a30000 90c40004   two base registers
  void W3 (S*,char,short,long long)              9883001c b0a3001e f8c30020
  void Fp2(S*,float f,double d)                  d0230010 d8430018   the other file
  void F7 (S*,int×7)                             seven `stw`s, r4…r10
  T& set2(int u,int v){ a=u; b=v; return *this;} 90830000 90a30004   the tail is FREE
```

### The tail is 81 % of the row, and it is a recognizer with one caller

Measured on the 878-TU workload by counterfactual, decomposed by run length and
tail:

| | needs the STATEMENT LIST | needs only the TAIL | total |
|---|---:|---:|---:|
| tail = void | 10,280 | — | 10,280 |
| tail = `return this` / constructor | 21,573 | 20,665 | 42,238 |
| tail = `return <first formal>` | 0 | 496 | 496 |
| ceiling (counterfactual A) | 31,853 | 22,580 | **54,433** |

**22,580 bodies are a SINGLE store**, already exactly the shape
`try_parse_store_leaf` accepts, refused only because of what came after the
`4B`. `eat_ctor_this_epilogue` — the recognizer for that — has existed since W19
and had **exactly one consumer**, the empty-constructor arm. This is the
coverage-costing form of §6's rule from the *other* side: not a private copy that
is narrower than its siblings, but a **shared** locator that only one caller ever
asks. Both are invisible to every gate here, because refusing more emits nothing.

The tail has three spellings and two of them are the same fact:

* `return *this;` / `return s;` — an ordinary value return, `B9 <tok> <T> 41 <T>`
  ahead of the `3A`;
* a **constructor's** implicit result — the same `B9 … 41 …` but *after* the
  `29`, which is `eat_ctor_this_epilogue`. 42,238 of the 54,433, i.e. the
  dominant shape here is an inline constructor storing its members;
* void.

**It costs nothing, and only at formal position 0.** MEASURED, four neighbours in
one TU (`work/w37/probe/p6.cpp`):

```text
  S*  r_first (S* s,int u,int v) { s->a=u; s->b=v; return s; }  90830000 90a30004        blr
  int r_first_i(int u,S* s,int v){ s->a=v;         return u; }  90a40000                 blr
  S*  r_second(int k,S* s,int u) { s->a=u;         return s; }  90a40000 7c832378  mr r3,r4
  int r_formal(S* s,int u,int v) { s->a=u;s->b=v;  return u; }  mr r11,r3 ; … ; mr r3,r4
```

The fourth is worse than a register move: the result register displaces the base,
so c2 saves it into r11 and **re-bases the later stores**. The gate is therefore
on the formal's *position*, which is the same fact
`chain::straight_line_out_of_class_ctx` states for a bare `return <formal>` in
the integer class.

## Refused, with the measured cost of each refusal

| refusal | why | cost on the 878-TU workload |
|---|---|---|
| a **literal** value in a run of more than one | c2 hoists the `li`s out of the sequence, allocates them r11/r10/r9 **descending**, CSEs equal ones, interleaves them with the stores past three, and **reorders the stores**: `{ s->a=1; s->b=u; }` is `li r11,1 ; stw r4,4(r3) ; stw r11,0(r3)`, the two statements emitted in the opposite order to the source | **11,391**, measured by lifting the gate and rescanning |
| a run of **three or more mixing the two register files** | c2 schedules: `{ i=u; j=v; x=w; }` comes back `stfs ; stw ; stw` with the FP store hoisted past both, and `{ a=u; x=v; y=w; }` comes back `stfs ; stw ; stfd`, so it is not "FP first" either. Correct in **all 42** ordered mixed pairs at length 2 and wrong in **16 of the 24** mixed triples | **618** |
| a **`volatile` stored value** | a memory object: c2 homes the parameter in the frame and reloads it. **A live mis-emit, see below** | **0** |
| two statements writing **overlapping bytes of one base** | c2 eliminates the dead store — `{ s->a=u; s->a=w; }` is a *single* `stw r5,0(r3)` | **0** |
| a returned value that is **not the first formal** | one `mr` at best, a re-based run at worst (table above) | **0** |
| the value is an indirect load, computed, a call result, a compound assign `0x19`, or narrowed by a `2C` | each is a scratch-register round trip or a read-modify-write, and each is the single store's own pre-existing refusal | not re-measured; inherited |

`w37_store_run_neg.cpp` carries one case per row and censuses **0/13**.

**The literal gate was checked in the under-claiming direction**, which is the
direction nothing here tests. Lifting it in the parser alone gains 11,391 census
functions **and produces a census/gate over-claim of exactly 11,391** — the
port's own `store_leaf_text` still refuses every one, because it restates the
rule. So the parser gate is not conservatism layered on codegen; it is the same
rule stated where census and `PortC2` cannot disagree, which is what keeps
disagreement at 0.

## Two live wrong-bytes emits, both found by the new generated axis

Neither was found by a fixture, a lane, the scan or review.

**#15 — a `volatile` stored VALUE, live on mainline since W25.**
`void f(Q* s, volatile int v){ s->a = v; }` is a single `store-leaf`, in class,
and the port emitted `stw r4,0(r3) ; blr`. c2 emits

```text
  stw  r4,28(r1)     ; home the volatile parameter
  lwz  r11,28(r1)    ; reload it
  stw  r11,0(r3)
  blr
```

— a whole frame slot; the body is not a leaf at all. `Port=Mismatch @ 8`, the
COFF `PointerToSymbolTable`, on two lines of C++. This is
`readers::is_volatile_tag` at a **third** position: §6 instance #13 put the gate
on the base LOAD, W35 measured that the same bit at the `27`/`30` designator
positions is free, and **nobody asked about the value**. The tell needed no
compiling: a predicate with three positions and gates at one of them. Cost of the
repair: **0 functions** — recorded separately from the widening on purpose.

**#16 — the empty prefix.** Generalizing `store_leaf_text` from an *exact*
three-op match to a *loop* added a case the exact match did not have: the **empty**
`ops` slice, which every shape whose data lives in another field
(`IlFunction::compare`) presents. Those walked past the loop and came out as a
bare `blr`. Caught by the one fixture that puts a compare leaf in the same TU as a
store — `w29_fp_contract.cpp`, `Port=Mismatch @ 8` — while `w25_store_leaf.cpp`,
which has no compare, was green over it. The generalizable form: **turning an
exact match into a prefix match adds the empty case, and the empty case is never
the one the rung is about.**

## Estimate vs outcome

The estimate was written to `work/w37/ESTIMATE.md` **before** the sizing scan,
with the pre-filter named.

**What the bucket had already been filtered by.** To reach the store recognizer
at all a body must have bound `.sy`, passed `formals_are_one_register_each`,
opened on `B9`/`33` (so it is *not* the `26` dispatch W36's row went to), and
been declined by the compare, float, indirect-load, ptr-identity, address and
empty-destructor leaves **and by the store leaf itself**. So "the base pointer's
type might not be modeled" was already applied — `is_ptr4_kind` admits
`86/96/A6/B6 × 43/44`. What was not filtered is everything from the value onwards
and everything after the `4B`, which is where the whole row turned out to live.

| | estimate | outcome | bias |
|---|---|---|---|
| counterfactual A (parse ceiling: a sequence of store statements, no codegen) | **+25,000**, range 8,000–60,000, biased **HIGH** | **+54,433** | **wrong direction** — LOW by 2.18×, inside the range |
| the shippable rung | **+12,000**, range 4,000–30,000, biased **HIGH** | **+36,684** | **wrong direction** — LOW by 3.06×, **outside the stated range** |

**Fifth consecutive miss, second consecutive one that is both in the wrong
direction and outside its own range** (W36 was 2.99× low). The cause is not the
one W36 named — no sibling rate was borrowed here, and the refusal to borrow one
is written into the estimate. It is simpler and worse: **the estimate enumerated
six candidate sub-shapes and the winner was not among them.** The list opened
with "a body that is more than one statement" and never considered the *tail* at
all, which is 81 % of the row. Both W35 and W37 have now missed the same way —
W35's estimate named the call-argument sub-shape (worth ≤ 7) and missed the
private single-add limit (worth 5,161).

The generalizable correction is narrower than "enumerate harder". In both cases
the winner was **a body the port's own recognizer already matched, refused by
something outside the construct the row is named for** — a limit *inside* the
recognizer for W35, and the *epilogue after* it for W37. So: before enumerating
sub-shapes of a row, take the recognizer that already covers the obvious one and
list what it refuses **on both sides of the construct** — its internal limits and
its terminators. That list is short, it is readable from the source, and twice
now it has contained the answer.

**The row-to-counterfactual gap is 1.45×** (78,983 → 54,433), against 67×, 67.8×
and 13.4×. That is not a better prediction; it is a different kind of row. The
earlier three are *first-blocker* rows, whose size measures how early a token
appears. 78,983 is a counterfactual successor — by construction the set of bodies
whose destination expression **fully parsed** — so almost everything that would
have thinned a first-blocker row was already spent. **A counterfactual successor
is a much tighter bound than a blocker row, and the 67× prior must not be applied
to one.**

## Found and not taken

Ranked, with the frame axis applied. Every figure below is from
`work/dc3-workload/scan-w37-final.jsonl`.

1. **The FP/GPR mixed-run scheduling rule — 618, and it is the riskiest thing
   this rung leaves.** Refused rather than fitted, on the evidence of 24 triples.
   It is small, but the *reason* it is refused is that c2 has a scheduler here
   and this port has no model of one; the same scheduler is what makes the
   literal case (11,391) unreachable, so the two are one question and it is worth
   **12,009** together. `GAPS.md` §6 instance #10 is the warning against fitting
   it from the six data points to hand.
2. **The literal-in-a-run rule — 11,391**, `calls-0`. The largest single item
   this rung refuses and the cheapest next thing in this family, *if* the
   scheduling rule can be characterized. The enumeration that would settle it is
   the same shape as instance #10's cycle grid: run length × (literal position)^k
   × equal-vs-distinct literals, over both files.
3. **The store run's own residue is unmeasured on one axis.** The counterfactual
   ceiling (54,433) minus the widening (37,302) minus the literal rule (11,391)
   leaves **5,740** which is the *statement's* own gates — value width class,
   type-restates-value, displacement bound, argument-register position, FP
   register resolution — and I did not decompose it. It is inherited from W25 and
   none of it is new here, but nobody has sized which of those five is carrying
   it.
4. **`expr-op-0x27` is still 421,587**, and 116,118 of that is `calls-2plus`, so
   a quarter of the residual row needs a frame before it needs anything else.
   `expr-intrinsic-base-member-addr` is 113,981 with 35,006 `calls-2plus`.
5. **The `0x19` compound assign.** `IL_STORE_LEAF.md` §6 recorded "a setter that
   writes a member *and then* sets a dirty flag with an `0x19` compound-assign
   op" as *the* dominant wild neighbour of the single store, and ranked it second
   overall. This rung took 36,684 out of the same two rows **without touching
   `0x19` at all**, so that ranking was measuring a real shape and over-weighting
   it. It remains unmeasured and is now a cleaner question than it was, because
   everything around it has been drained.
6. **A store whose value is an indirect load** (`a = r.a;`, the body of every
   hand-written copy constructor and assignment operator) is `lwz r11,k(rB) ;
   stw r11,j(rA)` — two instructions, one scratch register, no frame. The store
   production refuses it and this rung did **not** size it, because the probe
   that would have (a designator followed by a `30`) is indistinguishable from an
   ordinary member *load* in expression position and the first instrument built
   here conflated 165,258 functions on exactly that. Sizing it needs an
   instrument anchored on the `32`, which §8 now has.
