> ### 1. The #500 byte-fraction ranking is **byte-identical** to the table `w-tu3` published — **all four columns, all 18 rows** — across **seven merges**, including `w-wire`'s **+716 byte-exact functions**. Not one of those 716 was in a frontier TU.

> ### 3. Crossing that with `w-tu1`'s own obj-shape screen gives a 2×2 whose **buildable cell is EMPTY**. `xboxmem` was in that cell and is **the only TU that ever was**.

**The search for a better selector was never the binding problem.** Ten
selectors were refuted over blocker keys; this lane's finding is that on the
current frontier there is **nothing for a selector to find**, because no TU is
simultaneously expressible by the emitter and clean enough in obj shape to be
worth a lane. That is a statement about the *port*, not about the ranking.

## 3. The screen — board #720

`c2_core::codegen::Selected` has seven variants: `Plain`, `Tail`, `Float`,
`Framed`, `Seq`, `CondPair`. Between them they encode **straight-line** bodies
and **one two-arm conditional**. **No variant encodes a backward branch**, so no
loop of any kind has a representation, and none encodes a multi-way conditional.

The three existing rankings cannot see this. #269 counted independent refusals,
#465 counted already-emitted functions, #500 counted already-emitted bytes — all
three are *quantities of progress* computed from `select_function`, and none can
distinguish

* *"refused because one expression token is unmodelled"* — **a rung**, from
* *"refused because it is a LOOP"* — **a new CFG class**.

The screen reads `fn_cflow`'s `<class>|<key>` crosses (the rows that name a
**blocked** body; the bare class rows count every function and summing those
would over-count) and asks whether every blocked function's class is in
`PORT_CFG_CLASSES`.

### 3.1 `Sort.cpp` is the cell that makes the point

`src/system/math/Sort.cpp` is **one function** (`HashString`), **80 bytes**,
**zero relocations**, **no `.pdata`**, **no `$M`/`$T`**, no `.data`/`.rdata`.
By every obj-shape criterion `w-tu1` used it is the cleanest TU on the frontier,
and it is **one function from converting**. It cannot be built: those 80 bytes
are a rotated `while` loop. **#500 ranks it ahead of both TUs that can be
built**, and the unit test asserts that inversion rather than asserting about it.

### 3.2 `Unclassified` is a third verdict, not a `false`

A body the census bailed on before the control-flow step (`cf-expr-…`)
contributes to `fn_blockers` but to no `class|key` row. Counting only the
classified rows would let such a TU read *reachable* on the strength of the
functions it *could* classify — absence read as success. So the classified count
is compared against `fn_blockers`' total and any shortfall is its own verdict.

**`Pool.cpp` is the live instance and it is exactly the trap**: two `cflow-if-1`
functions — both inside the port's classes — and a constructor tagged
`cf-expr-0x05`, whose obj is

    cmpwi cr6,r10,1 ; bf 25,+28 ; addi r10,r10,-1 ; mtctr r10
    add r10,r11,r5 ; stw r10,0(r5) ; mr r5,r10 ; 4200fff4 bdnz -12

a CTR loop, plus a `divw` and the two-instruction `twi` divide-guard pair. A
screen that trusted the classified rows would have called `Pool` reachable and
sent a lane at it.

### 3.3 The control, #721

`xboxmem.cpp` — the one TU ever converted from per-function codegen breadth — is
`cflow-if-1` × 3 + `cflow-straight` × 1, **exactly and only the two shapes
`Selected` encodes**. `PORT_CFG_CLASSES` is a **hand-maintained mirror of a
`c2-core` enum** with nothing in the type system tying them together, so the
control's real job is catching the list going stale when a variant is added. An
**absent** control prints as absent, never as a pass.

## 4. The 2×2, and the empty cell — board #722

`w-tu1` §2 says plainly what actually chose `xboxmem`: *"I dumped the reference
obj of every cheap frontier candidate before committing."* The criteria were no
`.pdata`, no `.rdata`/`.data`, no `$M`/`$T`, no REFHI/REFLO, no frame. That
screen is the **procedure** behind the one conversion; #500 is a *retrodiction*
built afterwards. Crossing them:

| | **obj-clean** | **obj-dirty** |
|---|---|---|
| **CFG-reachable** | **0 TUs** | 2 — `Main`, `xboxheap` (#622) |
| **CFG-blocked** | 3 — `Sort`, `Pool`, `IPP_basicmath` | 13 |

**Control: `xboxmem` is (reachable, clean).** It is the only TU that ever was.

> ### The two screens that each retrodict the one conversion select **disjoint sets** on the live frontier, and their intersection is **empty**. #500's head (`mmio`, 16.8 %) is priced 17 and declined twice; the obj-shape screen's set (`Sort`, `Pool`, `IPP`) is at **0.0 %** on #500 and every member is CFG-blocked.

This is why the ten refuted selectors were refuted. A selector is a choice
function over a set; the set of buildable frontier TUs is **empty**, so no
selector over blocker keys, mass, purity, depth, union coverage or byte fraction
could have named one. **Mass pointed the wrong way, purity pointed the wrong
way, and so did the unit** — because the question they all answer is *how much
is left*, and the binding question is *can it be written at all*.

## 5. Step 2 — what I did NOT do, and the price

**I did not commit to a TU.** The instruction was to build whatever the ranking
names. It names `mmio`, which the brief simultaneously lists as known-declined
at price 17, twice. That is not a tie to break — it is the ranking failing to
name anything actionable, which §4 shows was inevitable.

**I re-priced the two candidates the obj screen names, and both come out at 10**
(prereg **P5 HIT**, registered ≥ 8; the reprice table is now cross-checked five
times and dearer every time: 10, 15, 17, 17, 10):

`Sort.cpp` — 1 function, 80 B, 0 relocations:
a loop `Selected` variant · the `assign-store-type-8643` parse blocker ·
`lbz`/`lbzu` (update form) · `mulli` · the `divw`+`mullw`+`sub` modulo ·
the 5-instruction `twi` divide-guard idiom with its exact `TO` fields ·
**`mr.` + `bt`/`bf` on `cr0` — a second CR-field regime** · the rotated
pre-tested loop shape · the interleaved schedule (the guard is woven *between*
the modulo instructions — #644's "a producer is not one contiguous
instruction") · ALLOC across a loop-carried body.

`IPP_basicmath_xbox.cpp` — 4 functions, 184 B, 0 relocations:
a CTR-loop variant · `expr-cmp-eq` · `bclr` conditional return ·
`mtctr`/`bdnz` · `lfs`/`lfsx`/`stfs`/`stfsu` · `fadds`/`fmuls` · the
pointer-difference `sub` base · **three distinct loop idioms across the four
functions** · a float formal in `f1` · loop-body ALLOC/SCHED. All four must be
byte-exact for the TU to convert.

**The mechanism that stopped me is the first item in both lists, and it is the
same one: there is no loop.** Not "no loop for this shape" — `Selected` has no
backward branch at all, `docs/CFG_SHAPE.md` §3.7 characterizes loops at the byte
level and **nothing implements them**, and the census cannot even assign a CFG
class to `Pool`'s ctor. That is a foundational CFG class plus a second CR-field
regime plus an interleaved schedule, in one lane, with four functions that must
all land — and I judged that a lane that started it and did not finish it would
ship a half-built CFG class, which is worse than an honest zero.

**I did not spend the one-shot gate.** Nothing here is a fitted model; the screen
is a partition over data the census already writes, and its one assumption
(`PORT_CFG_CLASSES`) has a known-answer control.

## 7. The instrument trap, third instance — board #723

**`llvm-readobj` cannot read these objs at all.** Machine `0x01f2`
(PowerPC-BE): *"The file was not recognized as a valid object file"*, on all 18.
My first survey piped its output through `grep -c` and printed a clean,
plausible, **entirely fabricated** table — 18 rows of `sections=0 pdata=0
relocs=0 $M/$T=0`. `llvm-objdump` fails the same way; `llvm-mc --disassemble`
**silently drops a stdout line for every word it cannot decode**, which shifted
the offset/mnemonic pairing for the whole of `Main.cpp` until the reader was
changed to one word per invocation.

Same shape as w-dclass §4.6, w-tu1 §3.1 and w-vmx's 28.7 %. **The only thing
that caught it was that every row was zero** — a uniform result looked wrong.
The replacement (`work/w-tu4/coffdump.py`, reloc constants taken from
`c2-obj/src/reloc.rs`) was then cross-validated against a number the harness
already computes: its `.text` totals match `bytefrac-denominator` on **18 of
18**. *A tool is not trustworthy because it produced output; it is trustworthy
because a number it produced was already known.*

## 8. The alarm, and what could still be wrong

`fnbyte-differs` is **0** before and **0** after, and it cannot have moved: this
lane ships an instrument, changes no `c2-core`, and touches no accept/refuse
path. FBM, `fnbyte-exact`, `fnbyte-partial` and TU match are identical across
the before/after scans (§ header).

**What shape would break this?** The screen's one claim is `PORT_CFG_CLASSES`,
and the honest limit is that **the census's CFG class is not the emitted CFG**.
`docs/CFG_SHAPE.md` §0.1 measures c2 folding `cflow-if-1` bodies to branchless
arithmetic or to `bclr` — so a census class is a statement about the **IL**, and
a TU could in principle be tagged `cflow-if-n` and emit no branch at all, which
would make this screen **too pessimistic**. It cannot make it too optimistic:
a `cflow-loop` body cannot emit without a backward branch. **The screen is a
floor on buildability, and #722's empty cell is therefore a floor too** — the
buildable set is empty *at least*. Whether some `cflow-if-n` TU folds branchless
is the measurement that would move it, and it is §9's first item.

## 9. Found and not taken

1. **Does any frontier `cflow-if-n` TU emit branchless?** §8's one way this
   screen is loose. `CFG_SHAPE.md` §3.5 has the fold table; nobody has crossed
   it with the frontier.
2. **`Pool.cpp`'s `Alloc` and `Free`** are 7 and 6 instructions, `cflow-if-1`,
   zero relocations, and both fold to `beqlr cr6` — genuinely cheap, and worth
   **0 TUs**, because the ctor is a CTR loop. Take them for FBM, never for match.
3. **`IPP_basicmath_xbox.cpp` is the most regular cell on the frontier** — 4
   functions, ONE blocker key (`expr-cmp-eq`), ONE CFG class, zero relocations,
   no frame, no `$M`/`$T`. If a loop class is ever built, this is the TU to
   build it against, and §5 has the ten mechanisms priced.
4. **The `.text` of `Main.cpp` is not a COMDAT** — a plain `.text` holding two
   framed bodies with 8 bytes of leading zero padding. It is one of the two
   CFG-reachable TUs and its obj shape is why it was not taken.
5. **`docs/CFG_SHAPE.md` §3.7 is a complete byte-level loop specification with
   no implementation.** The rotated `while`, the CTR loop, the `cr0`-vs-`cr6`
   two-valued rule and the `BO=16, BI=0` encoding are all already measured. The
   next lane at this does not need to characterize anything — it needs to build.
