## What it admits, and what it refuses

**The rule:** the graded-tree identity is computed over **every file on disk
under `GRADED_DIRS` that git is not explicitly ignoring.**

It is a *subtraction from the filesystem walk*, not a replacement of it by a git
listing, and every property below follows from that one choice:

| case | before | after | why |
|---|---|---|---|
| a tracked file's content changes | hashed | hashed | `git ls-files --others` cannot name a tracked file |
| an untracked, **unignored** file appears | hashed | **hashed** | the interlock is not weakened — this is the peer-session case `w-gatefix` built it for |
| a **gitignored** byproduct appears | hashed → **VOID RUN** | not hashed | the repo has already declared it generated |
| a byproduct nobody gitignored appears | hashed → void | hashed → **still void** | deliberate. The fix for that is one line of `.gitignore`, not a line here |
| there is no git to ask | hashed | hashed | degrades to the pre-#3048 function exactly |
| the exclusion would remove **every** file | n/a | hashed, unfiltered | the safety valve, §3.3 — the identity must never go *unavailable* because of the ignore rules |

**What it refuses to cover, stated here rather than discovered later:**

1. **A writer that modifies a TRACKED file and restores it** before the second
   hash. No content hash can see that, before or after this lane.
   `work/w-hatch/hatch_red.py` does exactly this by design, which is why it
   carries its own interlock (#2969) rather than relying on this one.
2. **An undeclared byproduct.** It still voids the run. That is not a gap being
   tolerated; it is the fail-open direction chosen on purpose, because the
   alternative (a positively-enumerated graded set) fails silently and this one
   fails loudly.
3. **A grading INPUT that someone gitignores under a graded directory** would
   leave the identity without anything noticing. Nothing does today — measured,
   §2 — and the *count of excluded files is printed at both ends of every run*
   so that the day it stops being true is a number that moved rather than a
   silence. That is #1002's rule (a denominator is not published until it has
   been printed on both sides of a change) applied to this subtraction.

### Why this and not `PYTHONDONTWRITEBYTECODE=1`

Both #2979 and #3048 name `PYTHONDONTWRITEBYTECODE=1` (or excluding
`__pycache__` from `GRADED_DIRS`) as the fix. Neither is taken. The three
reasons, in the order they matter:

1. **It changes what the gate RUNS in order to make a statement about what the
   gate MEASURES.** The subject moves so the instrument can be quiet. Everything
   else in `gate.sh` goes the other way — `graded_tree_hash` itself exists
   because #2907 preferred to *measure* the tree rather than assume it.
2. **It would have MASKED this incident.** With `-B` exported on 2026-08-10 the
   interlock goes quiet, `w-main2` never files #2979, `w-mmio3` never loses two
   runs to it, and nobody learns that **a gate row writes into the tree it
   grades**. The value of the last three days on this item is entirely in the
   fact that the interlock stayed loud.
3. **It is specific to one writer**, so the second writer is a second incident.
   `scripts/` already contains a *second* python module with a bytecode cache
   (`gt_dump.py`), and the trigger is not even "python" — it is "a byproduct
   lands in a graded directory". A rule keyed on `.gitignore` is keyed on the
   thing the repo already maintains for exactly this distinction.

And excluding `__pycache__` by name is the enumeration this project has paid for
repeatedly (traps 0 and 5): it is right until the day something else appears,
and on that day it is silently, confidently wrong about which tree was graded.

### 3.2 …and the mutant found an arm that was GREEN FOR THE WRONG REASON

Board **#3059**. The first run of mutant 2 reddened **four** arms, not one:
`hash-covers-crates`, `hash-covers-fixtures` and `hash-covers-scripts` went with
it. Instrumenting the mutant to dump its exclusion list gave the answer:

```
DBG-IGN crates/*
DBG-IGN fixtures/*
DBG-IGN scripts/*
```

— untracked files whose names are **literally `*`**. The arms read

```sh
printf '\n// touched\n' >> "$_ti_dir/a1/$_ti_d/"*
```

and **POSIX `sh` does not perform pathname expansion on a redirection target**
(it is optional, and only in interactive shells). So each arm was *creating a
new untracked file called `*`*, never touching the tracked `crates/probe.rs`.

The arm prints *"editing crates/ moves the identity"*. It was in fact grading
*"creating an untracked file moves the identity"* — a true statement about a
different property, and one that would have stayed green through a change that
stopped hashing tracked content altogether. It is named per directory now
(`crates/probe.rs`, `fixtures/f.cpp`, `scripts/s.sh`) and grades the sentence it
prints; with the repair, each mutant reddens exactly the one arm it should.

**This is the lane's best find and it was free.** A mutation written to test the
*new* code failed the *old* code for a reason nobody had looked for, which is
the argument for writing a rival-design mutant rather than only a
disable-the-fix mutant.

### 3.3 The safety valve, and the first version of its arm asserted nothing

A probe pointed `graded_tree_hash` at a scratch directory and it returned `:0`
— **IDENTITY UNAVAILABLE**. The root sat inside an *ignored path of an
enclosing repository*: `git -C <root> rev-parse` resolves to the outer repo, so
`git ls-files -o -i` reports every file under the root as ignored, and the
exclusion swallows the whole tree. That is a silence, in the one instrument
built to break silences.

The valve is fail-open like the rest: **if the exclusion would remove every
file, do not exclude** — hash the raw walk and let the identity be the
pre-#3048 one. It cannot fire at this gate's own call site (a repository root
has its own `.git` and the nearest one wins) and it fired on the *first* scratch
root a probe pointed at, which is the argument for it rather than against it.

**The first B3 was vacuous and is recorded because that is the finding.** It
built a synthetic repo whose `.gitignore` was a single `*` and asserted the
identity survived. It passed — **and it passed with the valve removed**, because
`git ls-files --others` never names a *tracked* file, so a `*` inside a repo of
its own excludes nothing at all. Only running the mutant exposed it. The shipped
B3 uses the construction that actually found the defect: an outer repo ignoring
`sub/`, with the graded root at `sub` and no `.git` of its own. With the valve
removed it reads `:0 / :0`.

Two arms in this lane were written, looked green, and were asserting something
other than what they printed — B3's first version and #3059's three. **Both were
caught only by running a mutant, and neither would have been caught by reading
the code.**

## §5. HOW MANY LANDED GATE CLAIMS ARE AFFECTED — with the method, not an assumption

**The question is about evidence quality, not about the port.** A void run is
*ungraded*, not *wrong*: it withdraws the attribution of a verdict to a tree. It
produces no counter-example and cannot turn `mismatch 0` into a mismatch.

### 5.1 The method

1. The graded-tree identity did not exist before `c6d6602e` (`w-gatefix`,
   2026-08-10 05:16). Before that, the `.pyc` was still written on every first
   run, but **no run made a claim about which tree it graded**, so there is no
   such claim to invalidate. Those runs' actual claims — lane counts, graded
   counts, `mismatch 0` — are untouched (see 5.3).
2. After `c6d6602e`, enumerate every merge into `master` up to `31a83377`
   (`git log --merges c6d6602e..31a83377`): **six**.
3. For each, read the landed rung for the gate transcript and both hashes. A
   void run **exits 1** and prints `THE TREE MOVED UNDER THIS RUN`, so a run
   quoted with two equal hashes is decidably sound; a run quoted with one hash
   or none is **undecidable from the repo** and is reported as such rather than
   assumed either way.

### 5.2 The result — all six decidable, none invalidated

| merge | rung | reported `graded tree` | verdict |
|---|---|---|---|
| `adfc2a78` w-gatefix | §11 | `8df4daab3052` (709) at **both** ends | **SOUND** — and warm: #2979 records that this lane's own transcripts were taken in a tree that already had a `__pycache__`, so the row could not fire there |
| `de16f6cc` w-main2 | §9 | `1c4314da6555` (804), identical | **SOUND** — and it is the lane that FILED the bug (#2979) after its own first run went `628102b17f0d (712) → ac876e62dfb7 (713)`; the shipping run used `python3 -m compileall -q scripts` as a workaround |
| `6f3ba44c` w-mmio3 | §9.1 | `851c61dce7ff` (810), identical | **SOUND** — and it says plainly that its **first two runs** were void, `52237379d357 (718) → 4c7dadb3326e (719)`, one file, named |
| `83e23ab6` w-wordwrap2 | §11.1/§11.2 | `c9e8965b05fb` (723), identical | **SOUND** — its §11.1 is explicitly labelled VOID, `89697685c12d (722) → c9e8965b05fb (723)` |

**Zero landed gate claims are invalidated.** Five of the six merges made a gate
claim; all five are decidably sound; **four of the five explicitly record having
hit the void and re-run**. There was no undecidable bucket, which is the outcome
the PREREG gave 0.75 to the opposite of.

**What it cost instead was runs, not correctness**: at minimum six full gate
runs (w-main2 1, w-mmio3 2, w-wordwrap2 1, w-keygen 1, this lane 1) at ~9 min
each were spent on it, plus w-main2's and w-mmio3's diagnosis time, plus this
lane. The interlock was doing its job the whole time; what was missing was
anyone with the seam to fix it, because every lane that hit it correctly refused
to edit the instrument its own claim rested on.

### 5.3 The part that generalises less than it looks

The reason no claim is invalidated is **not** that a void run is harmless. It is
that in this instance the two hashed trees differed by exactly one file, that
file is a gitignored CPython cache, and **no grading step reads it** — CPython
reads a cache on the *next* import, not the one that wrote it, and it is derived
from `sweep_gen.py`, which did not change. So the two trees were
grading-equivalent and the identity was distinguishing a difference that made
none. That is the specific fact this lane's file-list diff establishes, and it
is exactly the fact the new rule generalises: the identity should not be moved
by things the repo has already declared to be derived.

**It is not a licence to read past a future `THE TREE MOVED`.** Anyone who sees
that line must still do what §1.1 did — diff the file list and name what moved —
because the next one may be a peer session writing into `crates/`.

## Found and not taken

1. **`gt_dump.cpython-314.pyc` has no identified writer.** It is in the main
   repo's `scripts/__pycache__` and did **not** appear during this lane's gate
   window, so something other than a gate row imports `scripts/gt_dump.py`.
   Harmless under the new rule; still an unowned writer into a graded directory,
   and the second instance of the class. Board **#3061**.
2. **The identity does not cover `work/`.** `w-gatefix` §12 item 3 already says
   so and it is unchanged here: the ladder-red and hatch-red rows' subjects live
   under `work/`, and a change to them moves no identity. Widening
   `GRADED_DIRS` to include `work/` is *cheap now* and was not cheap before —
   `work/` is gitignored wholesale, so the new rule would exclude all of it, and
   the widening therefore needs a `.gitignore` change (force-added files under
   `work/` are tracked and would be hashed) rather than a `graded_tree_hash`
   change. Not taken: it is a different lane's risk and this one's seam is the
   byproduct rule.
3. **`--selftest` cannot see the cold path.** Every arm here runs against a
   synthetic checkout that the arm itself creates, which is cold by
   construction — but the *gate's own* cold path (a real `setup_worktree.sh`
   worktree, a real 9-minute run) is not reachable from a test. It was done by
   hand in §1 and §4 and there is no standing instrument for it. A row that
   diffed the graded file list across every run and printed the names would be
   the standing version, and it is a strictly better failure message than
   *"find what wrote to crates fixtures scripts during the run"*. Not taken:
   it wants a temp file surviving between the two hash calls, which is a
   different shape from the two pure functions the file has now.
4. **`graded_tree_hash`'s optional second argument is not threaded into the
   exclusion.** The function takes `<root> [dirs]` and defaults `dirs` to
   `GRADED_DIRS`; `graded_ignored_list` always asks git about `GRADED_DIRS`.
   **No caller passes the second argument today** (checked: both production
   call sites and all sixteen arms use the one-argument form), and the failure
   direction if one ever did is **fail-open** — an ignored file inside the
   caller's directories but outside `GRADED_DIRS` would be hashed rather than
   skipped, so the run over-grades and can only void, never go quietly blind.
   Not taken **because the gate of record was already in flight over this
   tree**: a two-line tidy is not worth a second forty-minute pair on a
   saturated box, and shipping the tidy ungated would be exactly the thing this
   lane exists to stop. It is a one-line change (`-- $_gh_dirs`) plus its
   argument threaded through `graded_ignored_list`, for whoever next opens the
   file.
5. **Nothing was done about `hatch-red`'s `HATCH-STALE`** (#1389), which is
   pre-existing and repo-wide, and this lane's fix does not touch it. Both
   gate-of-record runs report `HATCH-RED REFUSED` for that reason, as the
   reproduction run at `31a83377` did.
