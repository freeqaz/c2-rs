**5 of 5 move again, one for one, to a single successor, and all five are still
`0/1`.** The chain is now three links long — `expr-op-0x27` →
`assign-store-type-8643` → `expr-op-0x32` — and every link converts zero.

**So #1335's inference does not hold, though its measurement does.** Five cells
sharing a successor is not the strong form of "they are one predicate" if they
then *leave* that successor together, one for one, for the next one. What five
cells moving in lockstep through three keys demonstrates is a shared **path
through the parser**, which is exactly what #150's fall-through argument says a
census key records. The correct reading is the weaker one: the cells agree on
where the walk stops at every depth probed so far, and no depth yet reached
distinguishes "one predicate" from "one path". #1294 is neither strengthened nor
refuted by this; it is **untested by it**, which is a different thing from
supported.

**A methodological note this cost me and is worth leaving behind.** The first
run of these cells reported *no movement at all* under my sink, and the reason
was not the parser: `mk.py` resolves `ROOT` three directories up from its own
location, so invoking the main repo's copy from a worktree runs the **main
repo's** binary — which has no `C2RS_SINK_STORE_TYPE` and silently ignored it.
The cells were graded by a build that did not contain the change. It was caught

  exported the variable for a scan and then ran `cargo test` in the same session

* `the_default_arm_of_the_store_type_gate_is_the_shipped_eat_int_like` — the

  triples spanning both sides of the boundary (`int`, `unsigned`, `const int`

  **cursor** as well as the verdict. A regression here would silently re-price
  board #667's whole row and no gate could see it, because the sink emits
  nothing.
* `the_sink_arms_are_nested` — **`Int ⊆ Ptr4 ⊆ Any` on both the verdict and the
  cursor**, over 14 cases including the two malformed inputs a gate at a segment
  end really meets. This is the property that makes §4's headline readable and it
  is *not* obvious from the code: `eat_int_like` opens with an exact-triple
  whitelist (`INT_LIKE_TYPES`) **before** it consults `read_type`, so a triple on
  that list which `read_type` could not frame would be taken by the **default**
  arm and refused by the **widest** one. The recovery is the only number the arms
  produce and a narrower wide-arm can only push it **down** — so that failure
  would read as a *cleaner* decline, which is the direction nobody re-checks. All
  four `INT_LIKE_TYPES` entries are in the case list, so the hazard is covered
  exhaustively rather than by sampling. It holds.

**An unrecognized spelling resolves to the shipped gate, never to a silent
widening** — a typo'd sink that quietly measured something else is trap 5 with a
variable name on it.

**It is not a proposal and nothing here promotes it.** Board #661 is the standing
lesson that a sink can accept differently as well as measure, and this one has
the same hazard in a different place: the value whose store it folds away is a
pointer, and `dst_not_formal` — the gate that decides whether folding is legal —
admits an automatic local only on `.sy`'s evidence that it is a plain,
never-address-taken `int`. **`mismatch` is 0 in all five arms and is reported as
