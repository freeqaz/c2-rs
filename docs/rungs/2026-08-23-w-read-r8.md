## What it admits, and what it refuses

**Admits — the rule, in the form a port can implement.**

c2 has **no block-ordering pass and no block-order key**. Blocks are spans of a
single flat doubly-linked tuple list; the emit walk `FUN_10b338f5` @
`0x10b338f5` follows `tuple+0` and does nothing else. Emission order **is** list
order. So `M1` and `M2` were never rival rules about blocks — they are two
traversals inside the `switch` lowering, whose address nobody in this repo had
found (`WB_REGALLOC_FINDINGS.md:708`: *"an unread algorithm"*).

* **jump table** and **CTR ladder** walk the case list, which `reader.c` builds
  by **append** in source order and **never sorts** → arms in **SOURCE** order.
* **decision tree** walks a **value-ordered** structure → arms in recursive
  pivot order over the **VALUES**, with source order playing no part:
  `emit(V) = n < 8 ? reverse(V) : emit(V[:p]) ++ [V[p]] ++ emit(V[p+1:])`,
  `p = n/2`. The `8` is **read** at `0x10bd1388`, not fitted.
* Default arm: tree → **first**; ladder and table → **last**.

**Refuses, by name.**

* **No closure claim.** R3's closure argument was applied to the five splice
  primitives and **fails**: direction is a runtime parameter passed by pointer
  at **707** sites, 75 functions loading both. No sole author of block order is
  claimed, and none can be on that argument.
* **Does not separate a block MOVE from a leaf MATERIALIZATION.** Every arm in
  the grid is a two-word `return CONST`. The read says the switch module splices
  the body in unchanged and its expanders insert only compare/branch tuples —
  which favours materialization — but this grid cannot decide it.
  `FUN_10b35c78` @ `0x10b35c78` is the named, unread candidate.
* **The corpus is randomized, not the dc3 workload.** 240 seed-deterministic
  cells with case count, value set, density and **source order** randomized
  independently — **239 HIT / 1 MISS**. The trade is deliberate: the workload
  has real switches but no ground truth about their case *values* without
  parsing dc3 sources, and the rule is stated over values. A workload scan
  would still add the real distribution of shapes.
* **The cluster partition is named, not modelled.** The single corpus miss is a
  **hybrid** — c2 partitioned 19 clustered values and gave the dense low cluster
  a jump table and the outliers a decision tree. The rule holds per cluster; the
  partition constant (max-gap `3` at `[0x10b24184]`, loaded `0x10bd1844`) was
  already read and explains the miss without being fitted to it.
* **No new `if`/loop cells**, no `/O2`, no POGO, no `/Os` — so the size-mode
  threshold record at `0x10b2417c` is read but unexercised.

## Estimate vs outcome

Priced **5–10 days, explicitly uncertain**, as the riskiest row in the plan.
**Realized: well inside it — the decline criterion (30 bodies / 3 days) was
cleared inside ~15 function bodies, and the pre-authorized decline was not
needed.**

**The armed-suite row cost more wall clock than the read did.** Three peer
lanes ran their own suites concurrently and the box sat at load 67–77; the
first attempt was killed mid-run at exit 144 with no completion marker, and was
relaunched detached. **Reported because the failure mode is the one
`rungs/README.md` cares about: a killed suite leaves 887/0 in the log and looks
like a pass if you only read the counts.** The marker is what distinguishes
them, which is why the invocation appends one.

The bias is worth naming because it inverts the row's own premise. R8 was priced
as expensive *because it had no address*. It had no address because **the three
addresses it was given were translation-unit anchors**, copied forward from
`rungs/2026-08-19-c2map3.md`'s *"Found and not taken"* — a section whose own
words are *"the next read is named, not taken"*. All three are dead leads, and
two are mis-described in `READ_PLAN` §3 and in the dispatch brief.

**The decisive lead was one line nobody had used**: `ref/P_DAG.md:113`,
*"`0x10be626c` re-links the tuple list (`tuple+0` next, `+0x10` prev)"*. That
named the data structure, which turned "find the ordering pass" into "find the
list" — and the list has exactly one consumer. **Sixth consecutive lane on
which read-before-probe paid**, and here in the strong form: the grid was
designed *after* the read, and the read is what told the grid which control to
carry.

## What went red, and why that is the evidence

**The corpus found what the grid could not, exactly as the prereg said it
would.** 239 of 240 randomized cells obey the rule; the one that does not is a
**hybrid** lowering — a jump table for a dense cluster plus a decision tree for
the outliers — a shape that appears nowhere in this repo's record. It is
explained by a partition constant already read from the image, not by a
parameter added to fit it.

A **one-level** pivot model fitted three main-grid cells exactly. Frozen as a
predictor over six fresh holdout cells and committed **before** compiling, it
scored **4 HIT / 2 MISS** — missing at n = 16 and n = 20, i.e. exactly where a
group large enough to split *again* first appears. The corrected rule is
recursive and scores **22 HIT / 0 MISS**.

A model that had only ever met n ≤ 14 would have shipped looking correct. This
is the anti-fitting clause of the prereg doing its job on this lane's own work.

**Two classifier bugs, neither of which produced a failing run.** Keying the
lowering-shape test on `mtctr` called a **CTR ladder** a jump table; the repair
matched `bdzf` but not plain `bdz`, mis-filing `sw_scram08`. Both produced
clean, plausible tables. Both were caught only by reading the emitted words.
**Sixth entry in this repo's "ranking instruments measure themselves" pattern,
and the first where the instrument is a classifier rather than a ranking.**

## Corrections landed on the record

Eight, all amended **beside**, never over. The load-bearing one:

**Every published statement of `M2` in this repo says "reverse *SOURCE*
order"** — board **#1906**, `WB_LOOP_FINDINGS.md:449`,
`WB_REGALLOC_FINDINGS.md:541`, `ref/P_DAG.md:259`, `CFG_SHAPE.md:1757`. **It is
descending case VALUE.** Nobody could have known: every prior block-order cell
in the repo writes its cases in ascending source order, where the two are the
*same sequence*, so no prior cell is capable of separating them. This lane's
`scram` family writes the same values in a non-ascending source order and the
objs choose value — and `sw_spscram12` ≡ `sw_sparse12` confirms it independently.

The rest are tabulated in `WB_BLOCKORDER_FINDINGS.md` §2.
