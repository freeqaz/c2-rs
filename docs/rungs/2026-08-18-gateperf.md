## 2. THE PROFILE — where the wall clock actually goes

Taken as **one run**, decomposed by the gate's own per-leg timers, on the base
commit `071d2d47`, in a worktree created by `scripts/setup_worktree.sh` — i.e.
**the first gate run of a fresh lane**, which is the normal case here and turns
out to be a different animal from the second. `scripts/gate.sh --jobs 4
--require-graded`, load average 5 → 17.

| leg | wall | share |
|---|---:|---:|
| 18 mode lanes | 23 s | 1.3 % |
| generated sweep (19,556 cases) | 303 s | 17.3 % |
| **mode cross (90,812 cells), COLD** | **1,261 s** | **71.9 %** |
| debug lane (18 × 386) | 160 s | 9.1 % |
| overhead (builds, hashes, reap, hatch/ladder rows) | ~8 s | 0.5 % |
| **TOTAL** | **1,755 s** (29 min 15 s) | |

and the run consumed **382 % CPU of an available 3200 %**. On a 32-core box, a
`--jobs 4` gate leaves 28 cores idle for half an hour.

**The same gate, second run in the same worktree** (§6) reads **246 s**. The
difference is one number: the cross leg, **1,261 s cold → 38 s warm**, 33×.
So there are two profiles, not one, and quoting either alone is wrong:

* **run 1 in a worktree** is dominated by the cold cross (72 %);
* **run 2 onwards** was dominated by the sweep (**303 s of ~450**), which had no
  cache at all.

The dispatch handed down a quiet-box decomposition of 5 / 300 / 45 / 85 = 446 s.
**Its sweep and debug figures reproduce; its cross figure is a WARM number and
does not apply to a lane's first run.** That is board **#3265**.

## 3. Inside the dominant leg — per case, per operation

### 3.1 The anatomy

`scripts/expr_sweep.sh` spawns one `c2rs diff` per case. Timed serially, warm,
load 12–16, on case 9,000 of 19,556 (three consecutive runs: 58 / 56 / 57 ms;
the first touch is 313 ms and is discarded as page-cache fill):

| operation | ms | share | how it was measured |
|---|---:|---:|---|
| capture — `strace` → wibo → `cl.exe` → `c1xx.dll` → `c2.dll` | **43** | **75 %** | a timing wrapper on `C2RS_WIBO`, so the figure is taken *inside* the traced process |
| replay — wibo → `c2host.exe` → `c2.dll` | 6 | 11 % | the same wrapper |
| everything else — `c2rs` startup, scratch dir, `PortC2`, the obj compare, I/O | 8 | 14 % | the residue |
| **total** | **57** | | `date +%s%N` around the process |

19,556 × 57 ms = **1,115 s of serial work**, which at 4 jobs is ~279 s and the
gate measured 303 s. The arithmetic closes.

### 3.2 The spawn count — counted, and it is NOT the lever

The dispatch's second hypothesis was that process spawn dominates, on `w-fork`'s
measurement that ~94 % of c2's per-invocation cost is spawn + PE load. **It is
confirmed and it is mis-actionable, and separating those two is the finding.**

Counted with a wrapper script substituted for `C2RS_WIBO` that appends its argv
to a file and `exec`s the real wibo:

```
wibo invocations per case, UNCACHED   2   cl.exe (the capture) · c2host.exe (the replay)
wibo invocations per case, CACHE HIT  2   wibo --version (the cache context) · c2host.exe
```

Per case the gate creates about **six** processes — the `sh` subshell fork, then
`exec` of `c2rs`, `tail`, `strace` and two wibos — so the sweep leg is
**~117,000 process creations**. The cached path is about **five**:
**one spawn in six removed, 75 % of the cost removed.**

And the process that was assumed expensive is not:

```
c2rs nosuchcmd     0 ms avg over 20      # locates nothing, parses, exits
c2rs provenance    0 ms avg over 10      # locates the toolchain
/bin/true          0 ms avg over 20      # the control
```

**`c2rs` process startup is under 1 ms.** So the fork-server / batch-subcommand
design — the thing the dispatch expected to be the answer, and which
`STRATEGY_REVIEW` §4 calls "the lane worth commissioning" — is worth **under
2 %** of this leg. The expensive spawn is `cl.exe` under wibo mapping
`c1xx.dll` (1.71 MB) and `c2.dll` (1.35 MB) of PE, *inside* one of the six, and
the lever is not spawning fewer processes: **it is not doing that work twice.**
Board **#3262**; prereg **P11** registered this at p = 0.70 and hit.

### 3.3 The capture cache's actual role — the deliverable question, answered

The dispatch asked whether the cache benefits the sweep or the cross. Measured:

| row | drives | consults `work/capture-cache`? | cold | warm |
|---|---|---|---:|---:|
| 18 mode lanes | `c2rs gap` | **yes**, since 2026-08-04 | 23 s | 4 s |
| generated sweep | `c2rs diff` | **NO — and its sibling's header said so** | 303 s | 303 s |
| mode cross | `c2rs gap` | **yes** | 1,261 s | 38 s |
| debug lane | `c2rs gap` | **yes** | 160 s | 76 s |

`scripts/mode_cross.sh`'s own header carries the sentence, written 2026-08-04
and true until today: *"`expr_sweep.sh` cannot take this path: it drives `c2rs
diff`, which does not consult the cache at all."* **19,556 identical `cl.exe`
invocations per gate run, on every gate run, for two weeks.** That is the
cache-shaped hole the dispatch predicted, and it was documented rather than
hidden.

**Two things had to change together and only one of them is the cache.** The key
includes the source path (it is baked verbatim into `.gl` and `.debug$S`), and
the sweep regenerated its corpus into a **per-run** directory —
`/tmp/c2rs-gate-$$/sweep` under the gate — so every key would have been new on
every run. The case directory is stable now and lives outside the run's outdir,
exactly as `mode_cross.sh` has done it since the day it was written, with a lock
and a private-cold fallback on contention.

### 3.4 What is graded does not move — and one check was ADDED

This is the part that had to be right, so it is stated as four separate claims:

1. **The port is never cached.** `port.compile_to` runs on every call against a
   fresh `PortC2`. A caching bug cannot hide a wrong emit by skipping the port.
2. **The replay is never cached.** Every case still runs standalone `c2.dll`
   under wibo, and this is visible rather than asserted — the wibo argv log for
   a **cache HIT** reads
   `c2host.exe c2.dll c2.dll -il …_CL_faa7f0b8 -typedil … -Fo…\out.obj`.
   **P0.1 is executed per case, per run**, and it is a second, whole-obj
   validator of the cached bytes riding on top of the first.
3. **Only c2's own obj and IL bundle come off disk**, keyed over the source
   bytes, the source argument string, the flags, the cwd, the
   `cl.exe`/`c1xx.dll`/`c2.dll` contents, the wibo version and the cache root.
4. **The new dependency is named and instrumented, not implicit.** The row now
   depends on cache integrity — a dependency the mode cross and the 878-TU scan
   have both carried for two weeks. Every case's outcome word is counted and
   printed:

   ```
   cache: hit=19460 miss=96 validated=192 cache-bad=0 (of 19556 cases)
   ```

   `hit + miss` = `graded + ungraded` exactly: the 96 misses are precisely the
   96 cases `cl.exe` refuses to compile, which `capture_cache` deliberately
   never stores. `poisoned` and `foreign` are a **hard red** in both
   `expr_sweep.sh` and `gate.sh`'s `sweep_verdict`, with no baseline and no
   tolerance.

**And the row gained a check while getting faster.** `C2RS_SWEEP_VALIDATE`
(default: every 100th case) re-captures a strided sample of the run's own hits
through the real toolchain and byte-compares them against what the cache served
— **190 bypass-and-compare validations per gate run**. Nothing in this repo ran
`--validate-cache` on a schedule before; it existed and no standing instrument
used it. **It is free**: `validate=100` and `validate=0` both read 32 s.

The sampling is done in the shell and not in-process on purpose, and the reason
is a trap: `c2rs diff` performs exactly **one** capture per process, so an
in-process `--validate-cache N` tests `1 % N`, which is never 0 for `N > 1`. It
would have validated **nothing** while printing that it was validating.

## 4. The A/B — one session, one binary, identical counts

Sweep leg alone, 19,556 cases, load 20–26 throughout, runs back to back.
**Every run printed `checked=19556 mismatches=0 graded=19460 ungraded=96
unknown=0`** — that identity is what makes the timings a statement about speed
and not about coverage.

| `C2RS_SWEEP_JOBS` | uncached (`C2RS_SWEEP_NO_CACHE=1`) | cached, warm | ratio |
|---:|---:|---:|---:|
| 4 | **296 s** | **110 s** | **2.69×** |
| 16 | **98 s** | **32 s** | **3.06×** |
| 32 | — | 32 s | — |

* cold fill (the first cached run, 19,555 misses) at 16 jobs: **117 s** — i.e.
  a *worse* first run than uncached, by 19 s, which is the write cost and is
  paid once per worktree;
* the warm run repeated: **32 s** again, `hit=19460 miss=96 validated=190`;
* `validate=0`: **32 s**. The validator is inside the noise.

Combined with the concurrency default (§6), `--jobs 4` uncached → `--jobs 16`
cached is **296 s → 32 s, 9.25×**, on the leg that was the gate's largest.

## 6. The concurrency default — the change that costs nothing and was already made

`scripts/gate.sh` has read `jobs=16` since 2026-08-08, with a sixty-line
measured justification in its header from lane `w-throughput`. **The standing
lane instruction is `scripts/gate.sh --jobs 4 --require-graded`, which overrides
that default with the untuned constant the tuning replaced** — `jobs=4` stood in
the file from its creation commit `25def085` (2026-07-31) with a single
`git log -L` entry and no board row explaining it.

Measured at this lane's tip, warm, one session, `--require-graded`, identical
verdict blocks:

| | total | lanes | sweep | cross | debug |
|---|---:|---:|---:|---:|---:|
| `--jobs 4` | **246 s** | 4 s | 119 s | 38 s | 76 s |
| `--jobs 16` | **142 s** | 2 s | 29 s | 30 s | 74 s |

**1.73×, for a flag.** The gate now prints an advisory with that number when
`--jobs < 16`; it does **not** silently correct the value, because `--jobs` is
the caller's knob and a gate that ignores an explicit argument is worse than a
slow one. `docs/rungs/_TEMPLATE.md`'s gate row now reads
`--jobs 16 --require-graded`. **The remaining fix is to the dispatch template
and only the coordinator can make it.** Board **#3263**.

### 6.1 …and the ranking invalidated itself, which is the transferable part

Serving the sweep from the cache did not make the debug row slower. It made it
**the largest leg**: 160 s of 1,755 s (9 %) became **74 s of 142 s (52 %)**,
with the absolute cost falling. So the debug row was parallelised too — it ran
its 18 lanes one after another while `gate.sh`'s own lane leg has always run its
18 `$jobs` at a time.

| lanes at once | 1 | 4 | 16 |
|---|---:|---:|---:|
| wall clock | 83 s | 22 s | **10 s** |

and the 18 `DEBUG-LANE-RESULT` lines are **byte-identical at all three settings,
and byte-identical to the sequential code's own output from the gate run
immediately before the change** (`diff` of `dl-preseq.res` against `dl-16.res`,
empty). The counters are collected from **files** in registry order in the
parent shell — `fails=$((fails+1))` inside a backgrounded subshell is discarded,
which is the exact trap `gate.sh --selftest`'s own header warns about, and it
would have turned every failing lane into a silent pass. A lane with no result
file is a hard failure with a short-count reconciliation behind it.

`w-gatewire` §5 found its row's absolute cost stable within 11 % while its share
tripled from the box's **load**. Here the share went 9 % → 52 % from **another
row being fixed**. **A leg's share of a gate is a statement about the other
legs**, so a ranked optimisation list is invalidated by its own first item. The
answer is to re-profile between changes, which is what was done here.

## 7. A live `0` found on the way — `ARG_MAX`

Giving the sweep a stable case directory made its paths ~90 bytes instead of
~34, and the first run died:

```
scripts/expr_sweep.sh: line 226: /usr/bin/ls: Argument list too long
sweeping 0 of 0 generated cases
...
VACUOUS: 0 cases reached and NONE graded.
```

**It failed loudly, through the vacuity guard, which is the system working.**
Fixing it turned up the same defect **already live** in `scripts/mode_cross.sh`,
whose case directory has been inside a worktree since the file was written and
whose paths are ~100 bytes. Its `total_cases=$(ls "$cases"/*.cpp | wc -l)` has
been failing, and `wc -l` has been reading the empty output as the number 0.
**This lane's own base run at `071d2d47` prints it:**

```
sweeping 90812 of 90812 case-lane cells (cross of 0 cases x …)
```

Harmless — `total_cases` reaches no verdict — and that is exactly why it
survived. Both drivers now use `find -maxdepth 1`, and `mode_cross.sh` refuses
an empty case directory **positively** rather than carrying a 0 into a sentence.
Board **#3264**. The transferable rule: **a command substitution whose command
can fail must not feed an integer**, because `$(false | wc -l)` is `0` and `0`
is a legal count everywhere in this repo's shell.

## 8. The load-sensitive test — it is a shared temp path, and it presents as a port defect

Handed over mid-lane: peer `w-c2map2` saw `reloc_identity` fail **3 of 3 at load
~15**, on a **docs-only** branch whose `crates/` was byte-identical to base,
while its own `mode_cross` leg was running; it passed alone and a re-run was
green.

**It is not a timeout and it is not flakiness.** `work()` was
`c2rs-w-relo-{pid}` — one directory for the whole test binary — and all **three**
tests in the file call `grade()`, so `cargo test` ran three concurrent real
captures into it. `Toolchain::capture_reference_with`:

* sets `TMP` and `TEMP` to the work dir, so `cl.exe` writes its `_CL_*` IL
  bundle there — under a name hashed from the source path, **the same `s12.cpp`
  for all three**, so three compilers write the same five filenames at once;
* opens by deleting every `_CL_*` in the directory ("clear stale bundles so
  `find_bundle_base` cannot pick up a previous capture in a reused work dir") —
  one test deleting another's live bundle;
* compiles to a fixed `out.obj` that each of them `remove_file`s first.

Every thread compiles identical source at identical flags, so most interleavings
produce identical bytes and pass. **Reproduced and fixed, one session, one
binary:**

| | failures |
|---|---|
| before, load 6–9, no aggressor | **0 of 18** |
| before, uncached `expr_sweep.sh` at 48 jobs alongside (load 29–33) | **6 of 30** |
| **after**, the SAME aggressor (load 32–35) | **0 of 40** |

**The failure text is the finding.** The reds read `Unbound` on all three
symbols — a reference obj paired with somebody else's or a half-written IL
bundle — and the assertions then say *"RELOC-EQ indicts correct functions"* and
*"the fence stopped firing and the port is emitting a wrong relocation again"*.
A temp-path race wearing the words of a live wrong emit.

**Is it a class?** No, and this was checked rather than assumed: all **24** files
in the tree that build a temp dir from the pid were read. Eleven already key
scratch on `{tag}-{pid}-{counter}`; eleven use `{tag}-{pid}` with no tag reused
between tests (`census_gate` even gives each of its worker threads `root/w{n}`);
`fence_count.rs` has no tag and one test. **`reloc_identity.rs` was the only file
in the tree whose capture work directory is shared by more than one
concurrently-running test.** It is a bug, and the fix is this file adopting the
convention its eleven siblings already have. A test
`two_grade_calls_never_share_a_scratch_directory` pins the property **by name**,
because a count-shaped check is precisely what the old code passed. Board
**#3266**.

*Seam note, said loudly:* this edits `crates/c2-harness/tests/`, which the
dispatch assigned to peer `w-calleeguard`. That lane has merged (`b8ddb7aa`) and
the coordinator routed this item here.

## 9. `C2RS_REQUIRE_TOOLCHAIN` — armed, and the demand made a preflight

`w-calleeguard` landed `crates/c2-harness/tests/require_toolchain.rs`, which
fails when the variable is set and `Toolchain::locate()` is `None`. **Nothing
set it.** An armed-and-unused instrument is the same defect as an unarmed one,
one step further along.

**The boundary, stated once so it is not re-derived wrongly:**

> Skipping is **fine** when nobody claimed otherwise.
> Skipping is a **failure** when the run claimed to be graded.

So the demand rides on `--require-graded` / `C2RS_GATE_REQUIRE_GRADED=1` and
**not** on the default path: `CLAUDE.md`'s clean-degradation requirement and the
portable lane's entitlement to be empty are both untouched. `gate.sh` **exports**
the variable rather than setting it on one command, so every child of a graded
run inherits the caller's demand and the next instrument to honour it needs no
edit here.

It also **preflights**, with one `c2rs diff` against one fixture through the
run's already-pinned binary, greping for the same `SKIP: toolchain absent` line
the four rows already key on — one rule, one spelling. Demonstrated live, both
directions, on this tree:

```
toolchain hidden + --require-graded   EXIT 1 in 11 s
    GATE: FAIL (TOOLCHAIN ABSENT) — you asked for a graded run … and
    `Toolchain::locate()` returned nothing, so EVERY row below would have
    skipped and reported 0.
    … A fresh `git worktree add` has NO compilers/ …

toolchain hidden, no demand           EXIT 0 in 24 s
    GATE: SKIPPED — all 18 lanes, the sweep, the cross and the debug row
    skipped, NOTHING WAS GRADED.
    O1  SKIP  0/386 … <- toolchain absent      (all 18)
```

and the instrument itself verified in all three states — var + toolchain →
pass, var + no toolchain → **FAILED**, no var + no toolchain → pass.

**The wall-clock saving is 24 s → 11 s and is stated rather than sold.** It is
not why the preflight is here. It is here because the failure now appears at the
top of the log with its remediation attached instead of as an inference from
eighteen `0/386` rows.

**Where the variable actually bites is the suite row, and that row is
hand-typed.** `gate.sh` never runs `cargo test`, so exporting reaches nothing
today; `docs/rungs/_TEMPLATE.md`'s evidence table now reads
`C2RS_REQUIRE_TOOLCHAIN=1 cargo test --workspace --release --no-fail-fast`,
which is the one place every future rung copies from. **The standing dispatch
text should carry it too, and only the coordinator can make that edit.**

## 10. Proof the gate still goes RED

A gate that got faster and can no longer fail is the worst outcome available to
this lane, so nothing here is asserted.

| fault | how it was made | result |
|---|---|---|
| **a poisoned / refused cache entry** | four fabricated sweep logs driven through the **real** `sweep_verdict` + `decide` in `--selftest` | `GATE: FAIL — expr-sweep failed: CACHE POISONED/REFUSED on 1 case(s) — … this row's ORACLE side is untrustworthy on this run (C2RS_SWEEP_NO_CACHE=1 grades every case for real)` |
| **a COLD cache** (`hit=0`) | same route | `GATE: PASS` — slow and correct is not a failure |
| **an ABSENT cache line** | same route | `GATE: PASS` — `mode_cross.sh` prints none and must not redden; an absent count is not a zero |
| **an empty case directory** | `mode_cross.sh`'s new positive check | `FATAL: … holds no .cpp after regeneration` |
| **an `ARG_MAX` glob** | it happened, unplanned | `VACUOUS: 0 cases reached and NONE graded`, exit 1 (§7) |
| **an absent toolchain under `--require-graded`** | env override, live | exit 1 in 11 s (§9) |
| **the graded tree moving mid-run** | it happened, unplanned — this lane edited `crates/` while its own base run was in flight | `*** THE TREE MOVED UNDER THIS RUN …` exit 1, over a run whose four rows had all reported clean |
| **a lane producing no result** (debug row) | the new short-count reconciliation | `DEBUG-LANE-RESULT FAIL … rc=NO-RESULT` + `FAIL: N of 18 lanes reported a result` |

`gate.sh --selftest` is **170 cases, 0 failed** — the floor was raised 166 → 170
in the same commit, because a truncated selftest is the failure it exists to
catch.

The three cache cases are the ones to read together: a check that can tell
`clean` from `poisoned` but not from `cold` or `absent` would redden the mode
cross on every run, since that row is ruled by the same classifier and prints no
cache line at all.

## 11. The multi-lane case, and what is NOT taken

### 11.1 Three or four concurrent lanes — the recommendation

The evidence, all from this lane:

* a `--jobs 4` gate uses **283–382 % of 3200 % CPU**. Four of them is ~1,200 % —
  **still under 40 % of the box.** `--jobs 4` is not a contention limit; it is
  an untuned constant (§6).
* the **warm** sweep saturates at 16 jobs (32 s at both 16 and 32), so per-lane
  concurrency above 16 buys nothing even alone.
* the box's problem is not the gate's core count. It is that four lanes each
  did **19,556 uncached `cl.exe` invocations** per gate run — **78,000
  compilations of 19,556 distinct sources**. After this lane they do ~384
  between them (the 96 uncacheable cases × 4).
* and the concrete harm of contention was **not** slowness: it was
  `reloc_identity` reading as a port defect (§8), and that was a temp-path bug
  that load merely exposed.

**Recommendation, in order:**

1. **Stop specifying `--jobs 4`.** Use `gate.sh`'s own default. 1.73× for free,
   and the header explains why 16 and not 24 for exactly the multi-lane case.
2. **Do NOT add a global lock or a shared job budget.** Nothing measured here
   supports one: the box is not CPU-starved by gates, and a lock would serialise
   lanes that are now 7× cheaper each. If contention is still visible after (1)
   and (2), measure it before building a semaphore.
3. **Do not chase load-sensitive test failures as flakiness.** §8's mechanism
   was findable by reading, and the *only* honest reasons a test can be
   load-sensitive here are shared mutable paths and shared work directories.
   The tree has been swept for both; one instance existed and is fixed.
4. **The shared cache is a help, not a hazard, between lanes** — the entries are
   keyed on content and path, and one lane's entries are simply another's
   misses. What it is not is *shared*, because the case paths are per-worktree
   (§11.2 item 1).

### 11.2 Priced and NOT taken

**1. Worktree-independent case directories — coverage-preserving, ~19 min per
new lane, NOT taken.** Every lane creates a worktree, and a worktree's first
gate pays a cold cross (**1,261 s**) and now a cold sweep fill (**117 s at 16
jobs**) because the cache key contains the source path and both case directories
live under `$repo_root/work/`. Pointing them at `main_repo_root()` would make a
fresh worktree's first run warm. **Not taken** because both drivers `rm -f` and
regenerate that directory, so 3–4 concurrent lanes would contend on one mutable
corpus and the lock's private-cold fallback would fire under exactly the
condition that is normal here — trading a cost paid once per lane for one paid
on contention. It needs the regeneration made non-destructive (write-if-differs)
first. Board **#3265**.

**2. The per-process cache context — coverage-preserving, ~15 % of the warm
sweep leg, NOT taken.** `CaptureCache::new` runs `wibo --version` and FNV-hashes
`cl.exe` + `c1xx.dll` + `c2.dll` (**3.16 MB**) — once per `c2rs gap` scan, but
**once per case** for `c2rs diff`, i.e. 19,556 times. By subtraction it is ~4 ms
of the 17 ms warm case. Removing it means memoising a toolchain digest, which is
the one thing `capture_cache`'s module docs are most careful about ("the key is
a hash over *inputs*, never over mtimes"), so it wants its own lane and a stated
invalidation rule.

**3. The capture cache has no eviction and is enormous.**
`<main-repo>/work/capture-cache` holds on the order of **21.5 M entries** behind
a **1.37 GB directory inode**, at ~7 KB across 8 files each — order **150 GB**
and **170 M inodes**. It grows because the key includes the cache root, the
source path and the toolchain digests, and nothing ever removes a generation.
This lane adds ~19.5 k entries per worktree. **Not touched** — it is not in this
seam, it is a real operational item, and it interacts with **#3249**.

**4. `hatch-red` still reads `REFUSED HATCH-STALE` on every run of this lane**,
on both trees, exactly as `w-gatewire` §10 reported (board **#1389**/**#3219**).
Not caused here, not fixed here. Its duration remains unmeasured.

### 11.3 The COVERAGE-REDUCING candidates — priced, NOT implemented, for the user to rule on

None of these is adopted. They are written down because the honest answer to
"how much faster could it be" includes them, and because a lane that quietly
took one would be the catastrophe §1 names.

**R1. The sweep is largely redundant with the cross's `Ox` lane.** `c2rs diff`
hardcodes `/Ox /GS- /c`; `lanes.txt`'s `Ox` lane is `/Ox`, which `mode_lane.sh`
splices to `/Ox /GS- /c` — **the same profile over the same 19,556 generated
cases**. What the sweep uniquely adds is the **P0.1 replay check** per case. It
is not a *pure* duplicate — `mode_invariance.py` writes lowercase `z:\` source
arguments and `to_wibo_path` writes `Z:\`, so the two rows genuinely compile
different path strings and c2 bakes the path into the obj — but the *shapes*
graded overlap almost entirely. **Price: dropping the sweep's port verdict and
keeping only the replay would save ~0 s now that captures are cached, and would
lose the one row that found board #232.** Recommendation: **do not**.

**R2. Drop `--validate-cache` sampling.** Saves 0 s (measured, §4). **Do not.**

**R3. Sample the sweep or the cross with `--sweep-cases` / `--cross-cells`.**
The knobs exist and correctly forfeit the unqualified `PASS`. After this lane
the full sweep is 29 s and the full cross 30 s at `--jobs 16`; sampling buys
seconds and costs the enumeration's only property. **Do not.**

**R4. Skip the debug row on lanes that touch no `crates/`.** Would save 10 s
now. `w-gatewire` deliberately shipped that row with no opt-out ("an omittable
check is an omitted check"). **Do not.**

The real reading of R1–R4 is that **after §5 there is no coverage-reducing
change left that is worth anything.** The gate is 142 s at `--jobs 16`; the four
proposals above sum to well under 60 s and each costs a check.
