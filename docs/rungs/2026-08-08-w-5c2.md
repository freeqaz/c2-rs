## 2. WHICH OF THE FOUR THINGS IT IS — established by reading, before any scan

`PREREG.md` §1 registered this section's three findings **before the first
scan**, from the tree alone. All three re-derive.

### 2.1 (a) — a diagnostic classifier narrower than the tree's own reader

`mcall.rs`'s module header: *"It **accepts nothing**: every entry point returns
a `Block`, the gate is byte-for-byte unchanged, and only the census key
moves."* The `-then-op-0x5C` half of the key is minted in `mark_whole`
(*"Diagnostic only: the `Err` stays an `Err`"*) through `Fail::blocker` →
`FailKind::Value` → `Blocker::Op(b)`.

The gate underneath it is `eat_dtor_stmt_trailer`, which has **exactly one call
site** — `body_matches`, reached only from `mark_whole`. It reads

```rust
    5C  <eat_int_like TYPE>  <flag ∈ {0x11, 0x01}>
```

against a token `w-5c` anchored as `5C <TYPE> <varint>` on **335,716 sites, 0
desyncs, two independent anchors**, whose measured states include `02 03 04 41
43` and a 9,645-site escape. `control_flow.rs::operand()` has read it at the
anchored width since 2026-07-31 and `chain_skip_form` has had the row since
`w-5c`. So the classifier is narrower than the tree beside it, by two fields.

**This is not the phantom-rung shape and the difference matters.** The census
measure being narrower than the *emitter* manufactured 7,983 functions once
(#139, and the fix under-sized 1.69×). Here the emitter refused these bodies at
the `26` long before `mcall` ran — `mcall` exists precisely to name that
refusal. A narrow gate inside it cannot manufacture a blocked function. What it
manufactures is a **mis-ranked** one: a body filed as *"needs a `5C`
production"* when the `5C` is a red herring the matcher tripped over on its way
past the construct that actually blocks it.

### 2.2 (c) — the zero beside the row is a rendering

`docs/IL_CALL_IN_EXPR.md` §16.2 files the row as

| second blocker | functions | whole within 4 | note |
|---|---:|---:|---|
| `op-0x5C` | 890 | **0** | a destructor statement trailer whose flag is neither measured value |

That `0` is produced by `blocker_is_measured(Blocker::Op(b)) =
BARE_BINARY_OPS.contains(&b)`, and `0x5C` is not in that eleven-byte set. So
`mark_whole`'s greedy chain breaks at `adm.n == 0` with `need =
NEED_UNMEASURED` **before granting anything**, and the column is structurally
incapable of holding another value. `mcall.rs:1600` says so out loud: *"a pair
whose second half is `op-0x5C` … is reported as UNMEASURED at the pair level"*.

A zero an instrument cannot move is not a measurement of the row, which is why
a decline citing it would have been a decline citing nothing. §4 is the same
number taken again on an instrument that **can** move.

### 2.3 (d) — applies to the WIDTH question, and only to it

`w-5c`/#1428 measured a `chain_skip_form` width at zero on this family and
#1357 reported `op:5C` `TAIL_INERT` on `Main.cpp` at both ends. Both stand and
neither is re-litigated here: **a width in that table structurally cannot lift
this row**, because this row never consults that table. `git grep
eat_dtor_stmt_trailer docs/` returns **nothing** — the gate that does raise it
had never been named in a doc, let alone measured.

### 2.4 (b) — not a second production, and the test says so on a body

`the_trailer_flag_alone_turns_a_whole_body_into_the_op_0x5c_key` takes
`DTOR_MEMBER_OFF0`, which files as `expr-call-in-expr-recv-field-off0-**whole**`
— a body the matcher finishes — changes **one byte**, the trailer's flag, from
`11` to `02`, and the same body files as
`expr-call-in-expr-recv-field-off0-then-op-0x5C`. Nothing about the program
changed. There is no second production; there is one gate with a narrow field.

## 6.5 `w-ladders`' three cautions, applied to this rung's own numbers

Lane `w-ladders` landed at `25d4913e` while this rung was being written and
named three things that bear directly on it. All three are checked here rather
than acknowledged, and **one of them changes how a number above must be read.**

### 6.5.1 There is NO codegen column, so §4's zero is a READER-side zero — and it has to be

Board **#1464**: `ladder.py` has no codegen column at all — `fn_blockers` and
`emit_blockers` are **the same reader column at two populations**, and
`fn_gate_refusals` is documented as an invariant that must be empty.

**This rung must therefore not be quoted as saying the row is worthless to a
codegen lane.** What it says is narrower and it is exactly right for the row:
`mcall` **accepts nothing**, so every number here is about the *reader's* census
key by construction — there is nothing for a codegen column to see, and the
absence of one costs this measurement nothing. §4's "0 of 231 on the emitted
axis" is the same reader column restricted to emitted symbols and is corrected
to say so; it is **not** a second, independent axis, and the rung table above
should be read with the two rows as one.

### 6.5.2 The RENAME trap — checked, and this movement is NOT one

Board **#1465**: `chain_step_with` returns `Err(noform)` **before** moving the
cursor, so granting an unpinned opcode renames `expr-op-0xNN` to
`expr-chain-noform-0xNN` and buys **zero decode distance**. Six of sixteen
ladders end on exactly that.

**The 1,169 here are not that, and the evidence is in a test rather than in an
argument.** `eat_dtor_stmt_trailer_with` **consumes** the trailer, and
`the_trailer_sink_arms_are_nested` asserts the cursor lands on the `4B` that
closes the statement for every accepting arm over the whole 4 × 7 grid — real
decode distance, one statement's worth, at every site. Two corroborations from
the movement's own shape:

* **It is not 1:1.** A zero-distance rename sends one key to one key. This sends
  one key to **57**, and the largest destination is a *construct* (`chain-bind`,
  +949) rather than the next opcode along. `w-5c`'s own movement was 1 key → 14
  and was a clean identity too; the distinction between the two cases is
  distance, not identity.
* **The two EH trailers one and two tokens further on absorb 12 functions
  between them**, not 1,169. If the cursor had not moved, `0x5D`/`0x5E` is where
  essentially all of it would have gone — which is precisely what `w-5c` §5
  measured when its own floor moved by one statement (61.3 % to `5D`/`5E`).

So the movement is a **rename with distance**. It is still worth **zero**, and
§4 is why: distance is not completeness.

### 6.5.3 Which seventeen, and that `xboxheap.cpp` is in it

### 8.2 An instrument failure this lane hit, recorded because it is a live trap

`work/w-front3/hatch.py` resolves its `ROOT` as `dirname³(__file__)`. A worktree

`cargo build` reported *"Finished in 0.00s"* and the "hatched" binary's
`sha256sum` was **identical to the unhatched one**. A hatched ladder run on that
binary would have reproduced the unhatched table exactly and been published as
"the hatch moved nothing". **Always `sha256sum` the hatched binary against the
unhatched one before climbing.** Board **#1460**.

### 8.3 A commit message that shipped without its code, caught by `git show --stat`

**What caught it**: `git show --stat HEAD` after committing, and a positive
