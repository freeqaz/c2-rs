## 2. ITEM 1 — board #1388, and the mechanism is one missing `canonicalize`

### 2.1 The wrong verdict, reproduced on the base binary

Same binary, same entry, same flags, same cwd, one hit and zero misses either
way. Only the **spelling** of `--cache` differs:

```
$ ./work/w-cache/c2rs-base gap … --cache work/w-cache/cache
  capture cache: work/w-cache/cache
  [1/1] mismatch     src/xdk/nuispeech/xboxheap.cpp  (bytes diverge)
  match             0    0.0%
  mismatch          1  100.0%
  capture cache: 1 hit, 0 miss, 0 uncacheable  |  validator: 0 re-captured and
    agreed (0 of them only after zeroing the COFF TimeDateStamp), 0 POISONED
  mismatches:
        1 x bytes diverge
CORRECTNESS SIGNAL: 1 mismatching TU(s), 0 replay divergence(s), 0 poisoned cache entr(ies)
```

```
$ ./work/w-cache/c2rs-base gap … --cache $PWD/work/w-cache/cache
  capture cache: <REPO>/work/w-cache/cache
  [1/1] match        src/xdk/nuispeech/xboxheap.cpp
  match             1  100.0%
  mismatch          0    0.0%
  capture cache: 1 hit, 0 miss, 0 uncacheable  |  …
```

The **first** run at the relative spelling — the one that filled the entry —
reported `match`. That is the whole shape of the defect: **it cannot fire on a
miss.**

### 2.2 What is actually in the bytes

The cached obj is 1,213 B and contains exactly one `out.obj` string:

```
Z:\<REPO>\work\w-cache\cache\38ae869280b316944bde743b6c7b59be\out.obj
```

`CaptureCache::new` canonicalized the root **into the key** and stored the
caller's spelling in `self.root`. Those two disagree on exactly one path:

* On a **miss**, `capture_reference_with` calls `absolute()` on the directory it
  is handed, so `-Fo` and the returned `ref_obj_path` are absolute whatever the
  spelling. Both sides of the differential agree. Green, always.
* On a **hit**, `read_entry` served `self.root.join(key)/out.obj` verbatim. Under
  a relative `--cache` that is a relative path, and `to_wibo_path` passes a
  relative path through **unchanged, without even the `Z:` prefix**. The port
  bakes that short string as `S_OBJNAME` while the cached reference obj carries
  the long one. Two objs differing only in the path each records about itself.

And because the **key** already held the canonical root, both spellings addressed
**one entry** — which is why the wrong answer was stable and reproducible rather
than intermittent, and why `--validate-cache` (which re-captures *in place*)
could never have seen it.

### 2.3 The fix, and what it deliberately is not

Absolutise once, in `new()`, and use that one value for the key and for every
served path. The key line is byte-identical to what it produced before.

**`crates/c2-obj` is untouched.** The compare was never the problem and the
`TimeDateStamp` at offset 4..8 remains the only field the differential
neutralises. Making the compare lenient would have converted a false alarm into
a real blind spot, in the direction that matters.

Verified end to end: the tip binary at the **relative** spelling now reports
`match` on a hit, and the entry it hits is the one the **base** binary wrote.

### 2.4 The provenance guard, fired on purpose

The absolutisation alone leaves the served path *derived* rather than *checked*.
So each entry now records the absolute path it was captured at (`objpath` in
`meta.txt`), and one served from anywhere else is REFUSED — counted, named, and
re-captured. Rewriting one entry's `objpath`:

```
  capture cache: 0 hit, 1 miss, 0 uncacheable  |  validator: 0 re-captured and agreed …
  cache entries REFUSED on provenance: 1 (expected 0 — an entry whose recorded
    capture path is not where it is being served from is re-captured, never served)
    REFUSED src/xdk/nuispeech/xboxheap.cpp: entry records its capture at
    /some/other/cache/2093bcd668a7bfbe0a27195bb1a88a0c/out.obj but is being served
    from <REPO>/work/w-cache/cache2/2093bcd668a7bfbe0a27195bb1a88a0c/out.obj —
    the obj embeds its own -Fo path, so those are not the bytes c2 would emit here
```

`0 hit, 1 miss`, and the verdict stayed `match`. A stale or foreign entry is a
**miss plus a named refusal**, never a silent wrong verdict.

The count prints **even when it is 0**, because 0 is the expected reading and a
guard shown only when it fires cannot be told from one that is not wired up.

`objpath` is deliberately **not** key material: putting it there would bump every
key and cold-start every cache on this box to re-derive bytes that are already
correct.

### 2.5 Three tests, three mutations, three distinct reds

| mutation | test that went red | its message |
|---|---|---|
| undo the absolutisation | `a_relative_root_and_an_absolute_root_agree_on_key_and_on_served_path` | `two spellings of one cache directory must serve from one path` |
| drop the read-side check | `an_entry_recorded_at_another_path_is_refused_not_served` | `a foreign entry read as Miss — it must be REFUSED` |
| drop the written line | `a_written_entry_records_its_own_capture_path` | `write_entry did not record the capture path` |

Exactly **one** test failed under each, and no other test's expectation was
satisfied by any of them. The first mutation is the sharp one: it restores the
old `cache-root` canonicalization in the key, so the *key* half stayed green and
only the *served-path* half went red — which is the split the test was written
to make separately falsifiable.

## 3. ITEM 2 — board #1406, and the outcome that is neither PASS nor FAIL

### 3.1 What it grades

`work/w-hatch/hatch_red.py`, unchanged: 11 arms, 9 red and 2 green, 8 distinct
leading words, and 10 of 11 failing against the unrepaired `hatch.py` with the
key arm reading *"the foreign edit SURVIVED: NO — IT WAS EATEN"*. On this tree,
clean, it passes 11/11 and leaves `crates/` empty of diff.

### 3.2 Where it runs, and why there

**First, before `pin_harness`.** The arms write into `crates/` and restore in a
`finally`; `pin_harness` is the gate's one and only `cargo build`. Anything else
risks compiling a half-hatched tree. It needs no toolchain and takes seconds, so
a broken hatch is also on screen before twenty minutes of compiler:

```
hatch-red:       work/w-hatch/hatch_red.py  (no toolchain; fires hatch.py's refusals)
  PASS
building the harness (no-op if current)
```

### 3.3 REFUSED is not a fig leaf and it is not a failure either

Two of the four outcomes are properties of the **tree**, not of `hatch.py`:
`crates/` differing from `HEAD` (the arms would `git checkout --` over it — which
is #1380's incident re-enacted by the test written to prevent it), and a hatch
whose needles have drifted out of the tree so `apply` cannot build the arms a
tree at all (#1389's shape, and it is live). A lane mid-wave is routinely in the
first.

So `REFUSED` exits 0 — and **forfeits the unqualified headline**, exactly as
`SAMPLED` and `SKIPPED` do:

```
GATE: PASS (HATCH-RED REFUSED) — 2/2 lanes ran and every one of them graded a corpus,
…
  HATCH-RED REFUSED — DIRTY-TREE crates/ differs from HEAD and the arms would
  overwrite it: crates/c2-il/src/func/body/expr.rs
```

The interlock is `git diff HEAD -- crates/`, **not** the worktree-vs-index diff
`hatch_red.py` checks itself: a *staged* edit survives the arms' `git checkout
--` but can still move one of `hatch.py`'s needles, which would turn a peer's
ordinary work-in-progress into this row's red.

The 11 arms are **not** counted toward `--require-graded`. That demand is "this
run established something about the PORT", and 11 arms of a `work/` script say
nothing about the port; folding them in would let an all-skip run on a
toolchain-less box satisfy a demand it has to fail. A case pins it.

### 3.4 The two ordering traps, both hit while writing this

Both were predicted in the prereg as the place a bug would be, and both happened.

**Trap A — an early guard makes a later assertion unreachable.** A `SETUP
FAILED` arm *also* prints a `FAILED:` line. Read in the wrong order, a tree whose
hatch has drifted is indistinguishable from a `hatch.py` whose guards have
stopped working — the second is a real defect and the first is a Tuesday. The
case `hatchred-stale-hatch-is-not-a-broken-guard` drives exactly that log.

**Trap A again, one level up.** The first draft put the absent-tuple check in the
table region, above the completeness check — and it took `short-table`'s headline
away from the check that case exists for. Caught by the pre-existing selftest,
moved below, and `short-table` prints its own message again:

```
  ok    short-table   GATE: FAIL — the registry has 2 lanes and the table has 1 rows.
```

**Trap B — a shared prefix.** Every non-PASS detail leads with its own word —
`DIRTY-TREE`, `HATCH-STALE`, `TRUNCATED`, `VACUOUS`, `EXIT`, `ARMS-FAILED`,
`NO-LOG`, `UNRECOGNIZED`, `RESIDUE`, `MISSING`, `NO-GIT` — and a case asserts
the distinctness rather than hoping for it:

```
  ok    hatchred-every-refusal-leads-with-its-own-word 7 distinct leading words across 7 refusal shapes
```

### 3.5 Seven mutations, seven reds

| mutation | went red as |
|---|---|
| M1 read `ARMS-FAILED` before `HATCH-STALE` | `wanted REFUSED/HATCH-STALE, got FAIL/ARMS-FAILED` **and** `6 distinct leading words across 7 refusal shapes` |
| M2 drop the anti-vacuity arm | `hatchred-no-red-arms-is-vacuous  wanted FAIL/VACUOUS, got PASS/none` |
| M3 `REFUSED` stops forfeiting the headline | `GATE: PASS — …` + `a REFUSED hatch row never prints an unqualified PASS` |
| M4 drop the truncation arm | `hatchred-short-run-is-not-a-pass  wanted FAIL/TRUNCATED, got PASS/none` |
| M5 an absent tuple stops being a failure | `GATE: FAIL — hatch-red reported an unrecognized verdict ''.` |
| M6 fold the 11 arms into `--require-graded` | `require-graded-all-skip-fails  wanted FAIL, got PASS` (7 checks) |
| M7 a `FAIL` verdict stops failing the gate | `hatchred-fail-fails-the-gate` and `hatchred-residue-fails-the-gate` |

M1 is the one worth reading twice: it reddens **two** cases, and the second is
the trap-B distinctness arm noticing that two outcomes collapsed onto one word.
M5 is the one worth reading for the opposite reason — removing the check still
FAILs, via the catch-all arm, but with a *worse* message, and the case caught it
because it asserts on the message and not on the exit status.
