## 3. What C1-A ships, stated as a rule before it is written

1. **One value-type variant.** The `0x27` result is a **pointer** of the TYPE
   the opcode names. The shipped arm pushes `ValueClass::Ptr4` onto
   `parse_expr`'s class stack instead of clearing `cstack_ok`, so the
   `expr-ptr-arith` / `expr-ptr-bitwise` guards stay *exact* rather than
   falling back to the whole-expression flag.
2. **Its type resolution.** The `27 <TYPE>` is resolved through
   `designator.rs`'s existing pointer whitelist (`is_ptr_any`) — a literal
   `(tag, kind)` whitelist, refusing rather than assuming, exactly as that
   module's header requires. The sink's *"accept any TYPE"* is **not** shipped;
   an unmodeled tag refuses under its own census key.
3. **One general lowering.** `[.., Load(base), Lit(k), Add]` →
   `addi rD,rBase,k`, which `crates/c2-core/src/codegen/straightline.rs`
   already emits. **No new c2-core file and no edit to an existing one is
   predicted to be needed.**
4. **The lockstep obligation.** `expr.rs:2148-2152` records that widening
   `parse_expr` here obliges `mcall::eat_int_operands`'s `Vocab::CallArg` to
   widen in lockstep or `§9.14.6`'s correspondence guard goes red. Both are in
   `crates/c2-il`. If the guard goes red, that is a **finding to report**, not
   a thing to silence.
5. **Decision-surface clause** (`docs/rungs/README.md` kind 2): whatever
   arbitrary choice the arm makes is exposed as a named parameter whose
   **default reproduces c2 byte-exactly**, never a baked constant.
