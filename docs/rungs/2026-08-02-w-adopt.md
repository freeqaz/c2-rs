# W-ADOPT — the gate reads the `26` name separator

    Tag:       W-ADOPT
    Slug:      w-adopt
    Date:      2026-08-02
    Fixtures:  il_gl_sep26.cpp
    Census:    706,402 unchanged (28.69 %), +0 — a binding repair, not a widening
    Record:    this file; prereg `_2026-08-01-w-adopt-prereg.md`

## What it admits, and what it refuses

`.gl` introduces a record's name with `00` **or** `26` (`NAME_SEPARATORS`).
§9.20 taught the instrument-side scanner both and left the **gate** —
`gl_defined_names`, and therefore `Bindings::per_record` and
`IlBundle::functions` — reading `00` only, on the stated ground that widening
what a gate accepts is a differential decision rather than a reader repair.
This rung takes that decision.

Admitted: a record whose name is introduced by `26` now binds to **its own
name**. Refused, newly and positively: a bound run that **terminates** at `26`.

The second half is the part that is not bookkeeping. Terminating runs at `26` is
not optional — a run opened at the previous `00` would otherwise swallow the
separator and the name would still be lost — but it *shortens* a run that
previously ran past one, so a record's bound name can change with no record
moving. And every field this reader takes after a name is at a fixed
displacement from a **NUL** terminator: `linkage_needs_a_directive` reads the
linkage byte at `name_nul + 3`, measured across fourteen return types against
the TYPE field that follows a defined record's terminating NUL. A run that ends
at `26` ends because the *next* name began, so those three bytes belong to
another record. Reading them is reading a field that is not there, and the
answer decides whether the TU refuses for `__declspec(dllexport)`. Closed by
refusing rather than by reading — this was the one place the widening could have
produced wrong bytes instead of a refusal.

## What the incumbent was actually doing

Not mis-framing the name. **Never seeing it.** The reader opens a run only after
a `00`, so a `26`-introduced name is absent from the run list entirely, and the
record's "nearest preceding run" becomes the *previous record's* name — 70 bytes
back on the new fixture. `MAX_NAME_TO_OFFSET` is 32, so the record was
unnameable and the whole TU refused.

That refusal was right, and it came from the wrong place. The distance bound
caught what the scanner had lost, and it only holds while nothing else happens
to land inside 32 bytes of the offset field. On a TU where something does, the
same reader binds a body to another symbol's name — which is
`il_gl_record_order` and `il_extern_c_name` a third time, reached by a route
neither of those fixtures covers.

**E5 was the reason to expect a loss, and it was wrong.** The declared bias was
"pessimistic on the direction of the swap": widening what a gate sees widens
both what it can bind *and* what it must account for, and `IlBundle::functions`
refuses a TU for a single unaccounted `.gl` name. The predicted 30 lost TUs did
not appear — and the mechanism is worth stating, because it is the same
mechanism that makes this rung's payoff zero. Of the 6 matching TUs, **5 are
empty modules** that return at `segs.is_empty()` before `Bindings::per_record`
is ever called, so the accounting rule cannot reach them. Only `Spew.cpp` goes
through the binding path, and it still matches. The lane had one TU of exposure,
not 878.

**E7 and E16 were the same prediction from two sides, and both are unobserved.**
E16 said some run visible only under the `26` scanner would terminate on a
non-NUL byte, making the `name_nul + 3` linkage read wrong; E7 said that or the
shortening would re-point at least one binding. Across all 871 graded TUs,
**zero** bound names changed. So the terminator guard is, on this corpus, a
guard that never fires — it is retained because it is cheap and because the
shape it forbids is the only wrong-bytes route the widening opens, and it is
recorded here as **unfired, not as validated**. `a_record_name_terminated_by_26_refuses_rather_than_reading_past_it`
constructs the shape by hand precisely because the workload does not supply one.

## What it actually repaired

TU match did not move, and neither did any census. What moved is **which TUs the
gate can name at all** — measured directly over the 871 graded TUs' cached `.gl`
by running both readers:

| | |
|---|---|
| TUs the incumbent **refused to name** and the widened reader binds | **270 of 871** |
| `.gl` records named as a result | **8,583** |
| TUs where a bound name **changed** (both readers bound) | **0** |

Those 270 are all `vocab-gap` at both ends: their bodies still fail to decode, so
the class does not move and the scan cannot see the difference. That is not a
disappointment, it is the prereg's stated reason (E10, board #149) for requiring
a dedicated probe: **the 878-TU scan cannot grade this change**, because on 865
of 878 TUs the gate refuses before the emitter is consulted, and a repair to
*why* it refuses is invisible to a metric that only records *that* it refused.

The honest summary is a precondition, not a payoff: the name binding is no
longer the blocker on 270 TUs, and it was silently the blocker on all of them.

## The probe, and why the fixture alone is not evidence

`fixtures/cpp/il_gl_sep26.cpp` — a virtual destructor, so c2 synthesizes `??_GR`
and introduces its `.gl` name with `26`. Three `.ex` bodies, three framed
records, the middle one `26`-introduced at distance 17 (70 under the incumbent).

Its verdict is `NotImplemented` at base **and** at tip, with
`ReferenceReplay=ByteExact`. That is the required outcome — seeing three more
names must not turn a refusal into an emit — but it also means the fixture
**reads green under both readers**, and per #145 a probe that cannot go red is
not evidence. Stated plainly: the `.cpp` carries the source, the replay claim and
the fail-closed claim; it does **not** discriminate the change.

The discriminating artifact is
`gl::tests::the_gate_binds_a_26_introduced_record_to_its_own_name`, which
transcribes the fixture's two records byte for byte and asserts both halves —
the NUL-only reader refuses this shape, the widened one binds
`??_GR@@UAAPAXI@Z` to 2769. The incumbent is kept **executable** for that
purpose (`gl_defined_names_with(gl, sep26)`), rather than described in a comment:
"this used to refuse" is exactly the sort of claim that rots into folklore once
the code it describes is deleted.

Both mutations were run and both went red:

| mutation | result |
|---|---|
| gate reverted to `gl_defined_names_with(gl, false)` | `left: ([], [])` vs `right: ([(2644, "??1R@@UAA@XZ"), (2769, "??_GR@@UAAPAXI@Z")], [])` — FAILED |
| terminator guard deleted | binds `?w_add@@YAHH@Z` across a `26` — FAILED |

## Found and not taken

1. **The 878-TU scan cannot grade a binding repair, and nothing says so at the
   time of measurement.** This lane produced a report identical to base in every
   field while changing the bound names of 8,583 records on 270 TUs. The scan is
   not wrong — it grades objs — but "no field moved" was indistinguishable from
   "nothing happened" until the cached `.gl` was re-read by hand. A gate-side
   counter (TUs whose `gl_defined_names` returns non-empty) would have shown
   270 → and would have shown it for free. `gap.rs` was out of scope for this
   lane (`w-reach` is live in it); this is the first thing to add when it is not.

2. **`MAX_NAME_TO_OFFSET` is now load-bearing for a reason that no longer
   exists.** Under the widened scanner §9.20 measured the maximum name→offset
   distance at **27** across 676 records, and the bound is 32. It was catching
   the missing-name case as a side effect; that case is closed, so what the bound
   still protects against is unmeasured. Do not widen it (§9.20 says so
   explicitly) — but do not cite it as a working safety net either.

3. **The terminator guard is unfired.** Zero occurrences on 871 TUs. If a later
   corpus produces one it will show up as a refusal with no explanation attached;
   a counter on that branch would be worth more than the guard itself.

4. **Not taken, unchanged from the prereg**: the 32-byte bound (§9.20.9,
   +11 TUs), the varint framing (§9.20.8), and the `??_` synthesis
   re-measurement (#152, which ROADMAP §10.9 also flags as needing to be
   re-measured against 4,591 rather than 13,646).
