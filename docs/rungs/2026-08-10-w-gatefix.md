## 0. THE COMMISSION, AND WHAT IT TURNED OUT TO BE

> The brief: *"fix the gate's ability to grade the wrong tree and report it as
> the right one … `scripts/gate.sh`'s first lane runs `hatch_red.py`, which does
> an unconditional `git checkout -- crates/`."*

The brief is right about the outcome and it is one level short of the mechanism,
and the missing level is the whole lane. **`gate.sh` already had the interlock.**
It has had it since board #1406 — a wide one, over all of `crates/`, reading
`HEAD` rather than the index, with its own refusal word and a paragraph of
commentary explaining why a dirty tree must be `REFUSED` and not `FAIL`.

It never fired, because two lines above it the row did this:

```sh
_hr_exp=$(cd "$repo_root" && python3 "$_hr_py" --list 2>/dev/null | grep -c . || echo 0)
```

`--list` is documented on line 5 of `hatch_red.py` as *"names the arms, runs
nothing"*. It returns at the top of `main()`. And then the module's
`finally: restore()` — `git checkout -- crates/`, unconditional — fires anyway,
because it is attached to `sys.exit(main())` and not to anything that wrote.

So the sequence is:

1. the probe reverts `crates/`;
2. the interlock, two lines later, reads a clean tree and passes;
3. the arms run, `SETUP FAILED` on this tree (#1322/#1389, seven lanes old), and
   the row reports **`REFUSED HATCH-STALE`** — which is why #2907 saw a refusal
   that was not `DIRTY-TREE` and could not work out why;
4. `hatch_red.py`'s **own** `REFUSING to run on a dirty tree` guard, which is
   correct, is never reached — `--list` returns above it;
5. `pin_harness` computes its `-dirty` marker **after** all of that, so the one
   signal that could have said *"this is not the tree you handed me"* reads
   clean;
6. the gate builds, grades and reports `tree <HEAD>`.

**The lane that hardened that exact line was `w-hatchroot`**, which added the
`cd "$repo_root"` to it for board #1460 — because `hatch_red.py` resolves the
tree it may write into from the invoking CWD. It hardened *where the probe would
write* without noticing that the probe writes. That is #2940.

## 4. WHAT THE GATE REFUSES NOW

**A dirty `crates/` stops the run.** Exit **4** — its own code, because 2 is
usage, 3 is the disk preflight and 1 is a real gate failure, and a lane reading
exit codes must be able to tell *"your tree was not gradeable"* from *"the port
is wrong"*. Nothing is graded and nothing is touched; the files are named; the
opt-in is named.

The preflight sits **above** the hatch-red row, which is itself deliberately
first, because hatch-red is the row that writes. The identity it reads is
therefore the identity of the tree **as the caller supplied it**.

```
GATE: REFUSED (DIRTY crates/) — nothing was graded and nothing was touched.
  These files differ from HEAD:
    crates/c2-obj/src/lib.rs
  …
  Commit or stash, then re-run — a gate run is evidence about the tree it
  graded, and uncommitted work has no name to put on that evidence.
```

`--allow-dirty-crates` is the opt-in. It **does not re-enable the restore**: it
refuses the row that performs it (`DIRTY-ALLOWED`), and it does so on the basis
of the *flag*, not of the diff, so the row stays refused even if the tree is
clean at that instant. It names itself on the banner and again in the epilogue,
where it says outright that the commit id printed above it is not the tree that
was graded.

The refusal is on **tracked modifications** (`git diff --name-only HEAD --
crates/`) and not on `git status --porcelain`. Untracked files are not lost to a
checkout, and refusing every gate on this box over a stray `crates/scratch.txt`
is how a check stops being read. They are still covered — by §5's content hash,
which walks the filesystem rather than the index.

### 4.1 A defect the fix uncovered, in the fix's first run — #2946

The first `--allow-dirty-crates` run **failed the gate**:

```
ladder-red … FAIL  LADDER-RESIDUE the arms modified crates/, which they have
                   no path to do: crates/c2-obj/src/lib.rs
```

`ladder_red.py` has never written to `crates/` and its rung says so. The
postcondition asserting that was `git diff --name-only HEAD -- crates/`, which
reports every file that was *already* modified when the row started — so the
first tree that legitimately carried one convicted the row of a peer's edit.

Both red rows' residue postconditions are now **deltas**: a content hash of
`crates/` taken immediately before the arms, compared to one taken after. A
`git diff HEAD` also cannot see a **revert**, and a revert is these arms' bug of
record. Observed, not anticipated; it is in the PREREG as `POST` and unscored.

## 5. WHAT EVERY RUN PRINTS NOW

```
  graded tree: 8df4daab3052  (709 files under crates fixtures scripts, content-hashed)
```

Once **before any row can write**, once **after everything has**, over
`crates/` (the code under test), `fixtures/` (the corpus) and `scripts/` (the
graders, this file included). A hash of file **content** — `docs/STATUS.md`'s
generated block already pins a binary hash for the same reason; this is that
precedent applied to the inputs.

**Not `git rev-parse HEAD`, because HEAD is exactly what lied.** A commit id is
silent about uncommitted work, about a half-restored tree, and about a
concurrent writer — and a peer session has modified a lane's worktree mid-run on
this box. At one unchanged `HEAD` the identity reads `5691a3ed49dc` clean and
`fe898be5013b` with one edit; `git rev-parse HEAD` reads the same string for
both.

Two hashes that differ mean the tree moved under the run, the verdict was
produced partly from each, and the run **is evidence about neither end**. That
is said out loud and turns the run red. It is the first time this gate has been
able to say it.

The file **count** travels with the hash. A digest over three files and a digest
over seven hundred are both twelve hex characters, and a `find` that silently
returned almost nothing would otherwise print a confident, stable, meaningless
identity — this project's most-repeated defect aimed at the instrument built to
stop it.

## 6. THE REGRESSION TEST

Twelve arms, run by **both** `gate.sh --check` (the toolchain-free preflight)
and `gate.sh --selftest` (the mode whose one job is proving the gate fails when
it should). Three new `--selftest` cases govern them; the floor moves 138 → 141.

```
  PASS  hash-moves-when-content-moves      6df5faa203c3 -> a0f3c84c49e2 at one unchanged HEAD
  PASS  hash-reports-its-file-count        3 files, one in each graded directory
  PASS  hash-covers-crates                 editing crates/ moves the identity
  PASS  hash-covers-fixtures               editing fixtures/ moves the identity
  PASS  hash-covers-scripts                editing scripts/ moves the identity
  PASS  hash-is-deterministic              two reads of an unchanged tree agree
  PASS  list-probe-writes-nothing          an uncommitted crates/ edit survives --list
  PASS  dirty-tree-refused-and-preserved   REFUSED DIRTY-TREE, edit intact
  PASS  interlock-precedes-every-invocation interlock at body line 36, first invocation at 68
  PASS  counterfactual-list-probe-was-destructive 0d0a74d2's --list ate the edit; A2 is a real assertion
  PASS  counterfactual-row-now-preserves   with 0d0a74d2's file the row's own interlock now saves the edit
  PASS  counterfactual-interlock-was-second 0d0a74d2 ran the probe at body line 21, interlock at 30
  tree integrity: 12 arms, 0 failed (boards #2668 / #2907)
```

**They run against synthetic checkouts, and that is not squeamishness.** The arm
that matters asserts that a dirty `crates/` *survives*, and the pre-fix code
destroys it — so against the real tree a red arm would be indistinguishable from
the incident, and the test would have to eat a lane's work in order to report
that work gets eaten. Each arm builds a throwaway `git init` tree with a
`crates/`, a `fixtures/`, a `scripts/` and a copy of `hatch_red.py`, points
`repo_root` at it, and drives the **real** `hatch_red_run` / `graded_tree_hash`
/ `crates_dirty` — not a reimplementation, which would only prove the copy
agrees with itself.

**The proof that they fail on master's tree is built in and permanent.** `C1`,
`C2` and `C3` read `0d0a74d2`'s `hatch_red.py` and `gate.sh` **out of git** and
require the same arms to fail against them:

* `C1` — at `0d0a74d2`, `--list` **ate** the edit. `A2` is therefore asserting
  something.
* `C2` — with `0d0a74d2`'s file dropped into the tree, the *reordered* row now
  saves the edit anyway, which is what makes the interlock's position a second
  lock rather than the same lock twice.
* `C3` — at `0d0a74d2` the probe sat at body line **21** and the interlock at
  **30**. Today: interlock **36**, first invocation **68**.

A `SKIP` on any of the three is reported as *"NOT a pass"* and fails the
`--selftest` case that watches them. `TI_BASE` is a **fixed string** on purpose:
resolving it to `master` or `HEAD~n` would silently re-target the counterfactual
once this lands and compare the fix against the fix.

`A4` is a structural arm — no invocation of `$_hr_py` may appear above the
interlock in `hatch_red_run`'s source. It is not redundant with `A2`/`A3`: those
grade today's `hatch_red.py`, and `A4` grades the rule that survives that file
regaining a destructive path.

### 6.2 …and the same thing said the way a reader will ask for it

`C1`/`C2`/`C3` prove the *subjects* were defective. What a reader actually asks
is *"does the test fail on master?"*, and on master `gate.sh --check` has no such
arms at all, so it cannot fail — which is not an answer.
`work/w-gatefix/counterfactual.sh` gives the answer directly: it extracts
**`master`'s own `hatch_red_run`** and its helpers out of git, drives them
against a throwaway `git init` tree exactly as the gate drives them, and does the
same for the tip.

```
  BASE  0d0a74d2 : edit EATEN     <-- as required; the defect is real here
        tuple: NO-RESULT|0|14|0|0|UNRECOGNIZED …
  TIP         : edit SURVIVED  <-- as required; the row refused first
        tuple: REFUSED|0|0|0|0|DIRTY-TREE crates/ differs from HEAD …

COUNTERFACTUAL: PASS — the base eats, the tip refuses.
```

Note master's word: **not** `DIRTY-TREE`. The tree was dirty when the row was
called and the interlock still did not see it, because the `--list` probe two
lines above had already cleaned it. That single line is the whole of #2907.
The script exits non-zero on *either* half behaving the other way — a base that
preserves means the arms assert nothing, and a tip that eats means the fix did
not take.

### 6.1 And the offender itself

`hatch_red.py`'s `restore()` is **armed** now. `arm()` — the only writer — sets
the flag immediately before its first write. A mode that writes nothing restores
nothing. The flag is set before the write and not after: a crash between flag
and write costs one redundant checkout of a tree the guard has already proved
clean, while a crash the other way round leaves a hatched tree behind. The
failure modes are not symmetric and the ordering picks the survivable one.

## 7. THE AUDIT — IS ANY LANDED GATE CLAIM SUSPECT?

**No. And the reason is a conjunction of three things, each measured.**

`work/w-gatefix/audit.py`, `audit2.py`, `audit3.py`; frozen outputs beside them.
Board #2945.

### 7.1 The structural half — what `git checkout --` actually does

`git checkout -- <path>` restores the worktree **from the index**. Two
consequences that decide most of the audit:

* the edits destroyed are exactly the **unstaged** `crates/` modifications. A
  *staged* one survives, is still seen by `git diff HEAD`, and therefore still
  trips the interlock and refuses the row — which is why exactly one pre-lane
  transcript in the window reads `REFUSED DIRTY-TREE`;
* after the revert, `crates/` **is** the index's `crates/`, which on every lane
  here is `HEAD`'s. So every affected run **graded exactly the `crates/` of the
  commit it named**.

**The report was never false about what it graded.** It was silent about what it
discarded. Only a rung claiming its gate covers eaten work can be wrong.

### 7.2 The exposure window — a hard antecedent, not a heuristic

`hatch_red_run` entered `scripts/gate.sh` at **`378a3cae`** (2026-08-08, board
#1406) and was fixed at **`c6d6602e`** (this lane). A run whose named commit
lacks `378a3cae` as an ancestor ran a `gate.sh` with **no hatch-red row at
all** — nothing invoked `hatch_red.py`, and the defect is not merely absent from
the transcript, it did not exist in the code that produced it.

### P4 is the deciding row, and here is the antecedent it actually needs

Registered antecedent, as a conjunction of three and not one:

1. `git checkout -- <path>` restores from the **index**, so the graded `crates/`

2. the row that could invoke `hatch_red.py` **did not exist** before `378a3cae`;
3. therefore the only failure mode is a rung claiming coverage of eaten work,
   visible in git iff that work later landed.

All three were checked, not assumed. (1) is the reason the answer is decidable
at all rather than "unknowable from transcripts"; without it every one of the 36
in-window runs would be an open question.

**The falsifier, written before `audit2.py` and `audit3.py` ran**: *any*
in-window transcript whose lane landed a `crates/` delta touching a line outside
`#[cfg(test)]` and outside a comment. The population that could contain one is
5 lanes; it was enumerated and read line by line; it contains none. A second
falsifier was registered against the **antecedent** rather than the conclusion —
an in-window `REFUSED DIRTY-TREE` accompanied by evidence of a destroyed
unstaged edit, which would break clause (1) — and it did not fire either.

**Why P4 is not an unlosable row.** It has a named population (36 → 5), a
decision rule that could have returned "yes", and both falsifiers name artefacts
I could actually have found. `w-seclayout`'s P5 is the reason they are written
down: an antecedent that only makes the registered clause true is not the
antecedent the claim needs, and clause (1) — the index argument — is the one
doing the work here, not clause (2), which merely shrinks the population.

**And the thing P4 does not claim**: that the defect was harmless. §7.4.

## 12. FOUND AND NOT TAKEN

1. **`ladder_red_run`'s narrow interlock is still a `git diff`.** Its residue
   *postcondition* is a delta now (§4.1), but the interlock in front of it still
   reads `git diff --name-only HEAD -- <LADDER_SUBJECT>`. That is correct today
   and has the same blind spot in principle — it cannot see a revert of that one
   file. Unpriced; the row writes nothing there, so there is no path to it.
2. **`pin_harness`'s `-dirty` marker is still computed where it was.** It is now
   redundant beside the graded-tree hash and it is still misleading in the same
   way. Removing it is a change to a shared script four other callers read, and
   this lane declined to widen its blast radius. The hash sits above it and says
   the true thing.
3. **The graded-tree hash does not cover `work/`.** The red rows' subjects
   (`hatch.py`, `ladder.py`) live there and a mid-run edit to one would not move
   the identity. Including `work/` would make the hash move on every lane's
   scratch write and the check would stop being read — the same trade-off as
   §4's tracked-vs-untracked. Named, not taken.
4. **`hatch.py`'s five red arms** — §9, explicitly out of scope, seven lanes old.
5. **A gate transcript does not record the graded-tree hash of the corpus it
   compared against.** The hash covers `fixtures/`, not the generated
   `expr_sweep` corpus, which is regenerated per run from `sweep_gen.py` (itself
   under `scripts/`, so covered). Adequate today; a lane that starts caching the
   generated corpus across runs must revisit it.
