## 4. A13 — `FRAME_HEAD` IS ORPHANED, AND THE COMMIT THAT ORPHANED IT IS DATED

`crates/c2-core/src/codegen/frame.rs:34`

```rust
pub const FRAME_HEAD: u32 = 80;
```

**Zero references of any kind.** Code 0, doc 0, over a NUL-safe read of every
`.rs` file in `crates/`. It is the **only orphan among 235 `pub const` names
workspace-wide** (§8.1) — so the finding is an exception, not a pattern, and the
project's constants are otherwise in good order.

**Dated.** `git log -S FRAME_HEAD -- crates/` gives three commits:

| commit | date | what it did |
|---|---|---|
| `a7c0379e6` | 2026-07-30 | introduced it, with its consumer |
| **`a4bcab4c4`** | **2026-07-30** | *"codegen: generalize the frame rule to nOutSlots"* — **deleted the sole consumer**, `let raw = FRAME_HEAD + self.locals + 8 * self.save_slots();`, and left the constant and its nine-line doc standing |
| `8e18b9544` | later | split `codegen.rs` into `codegen/`; the orphan survived the move |

Six days after it was orphaned, `docs/rungs/2026-08-05-w-next.md:169` quoted it
as a fact of the frame model: *"(`FRAME_HEAD 80`, callee-saved GPRs
`r31 → −16(r1)`, `align16(80+8+saved)`)"*.

**Is the VALUE corroborated?** Yes, and this matters — an orphan whose number is
also unverified is a strictly worse row. `FrameLayout::locals_base()` computes
`align16(16 + 8·max(out_slots, 8))` = **80** for `out_slots ≤ 8`, and
`frame.rs:675` asserts exactly that: `FrameLayout::default().locals_base() == 80`.
So the live path independently arrives at the same number.

**Is the CLAIM corroborated?** **No — and it is refuted one line away.** The
doc's headline is *"Fixed head of every MSVC X360 stack frame"*. `frame.rs:674`,
the assertion immediately above the one that corroborates the value, reads:

```rust
assert_eq!(FrameLayout { out_slots: 9, ..Default::default() }.locals_base(), 96);
```

The head is **not fixed**; it is `16 + 8·max(out_slots, 8)`, and it is 96 as soon
as a call passes nine arguments. The constant's own doc body concedes this
(*"It is a floor on the parameter area, not a floor on the frame"*), which is
precisely the kind of correction that gets read past when the headline says
otherwise.

**So the row is: orphaned constant, right number, wrong sentence.** It cannot
produce a wrong emit — nothing reads it. It can only produce a **wrong belief**,
and it already has, once, in a rung.

**REPORTED, NOT REMOVED** (prereg §7.1). The edit that would fix it is one of
two, and this lane deliberately does not choose:

* **Re-wire it** — `param_area_end()` (`frame.rs`) computes `16 + 8·max(out_slots,
  FRAME_MIN_OUT_SLOTS as usize)`; the `16` is un-named and `FRAME_HEAD` is the
  name for the `out_slots ≤ 8` case. Call sites to change: **0** (there are none).
* **Delete it and amend the doc**, moving the corroborated `80` into
  `locals_base`'s own record.

Neither is this lane's to make, and an orphan with a nine-line doc may encode a
read somebody did once and nobody re-derived — worth recovering, not discarding.
`docs/rungs/2026-08-05-w-next.md` stays as written; the correction rides on the
board row (`#3512`), per the `#3495` amend-beside convention.

### 5.1 A04 / A05 / A06 — the inline decline bounds, and the question they pose about THE JUDGE

`comdat::INLINE_DECLINE_LOOP_BYTES` **80 → 8** and
`comdat::INLINE_DECLINE_BYTES` **128 → 16** are **byte-identical across the
entire workspace suite** — 1,866 passed / 0 failed / 1 ignored over 54 targets,
zero `SKIP: toolchain absent`, **including `tests/differential.rs`, the
differential against real `c2` over the fixtures**. Both are read on the live
decline path (`comdat.rs:432`, `:435`, `:1315`, `:1352`, `:1369`, `:302`), and
both decide the thing the port's correctness most depends on: **whether the port
keeps a call c2 dropped, or drops one c2 kept**.

**The first thing to check was whether the tests that exist for this even ask
the question, and the repo answers in its own words.** `crates/c2-harness/tests/
inline_fence.rs` and `noinline_boundary.rs` — 4 + 4 tests, both ran and both
passed under the mutation — are the workspace's inline tests, and
`inline_fence.rs`'s header says:

> *"Nothing here uses a size, a ceiling or a flag bit. … this fence uses only the
> categorical direction — **c2 cannot inline a body it does not have** — which
> needs no constant."*

**So the two purpose-built inline test files are categorical by design and
cannot discriminate any value of either constant.** That is not a defect in
them; it is the reason the greens are not surprising once read.

**The discriminating-cell count, so far, and it is a BOUND not a measurement.**
Of 391 fixtures, **305** define ≥ 2 functions and **~110** contain a call to a
name the same file defines — the shape the decline predicate sees. So the
population is **not** empty and "no cells" is not the explanation. What is not
yet measured is how many of those cells have a *lowered body size* inside the
band a mutation moves, which is the number that decides everything. The probe
for it is specified in §7 and is queued.

**The constant's own doc already scopes its insensitivity to the workload**, and
this lane will not report 16 as a refutation of it:

> *"any value in `(95,152]` produces the identical result **on this workload** —
> GRID-W's port-side table has no site at all between 47 B and 152 B."*

### 5.1a THE TWO-SIDED ARM RAN, AND IT SPLIT THE THREE CONSTANTS APART

Registered in `work/w-latent/axisA2.tsv` before it ran: each constant → **4096**,
the **acceptance-widening** direction, which `comdat.rs:483` itself names *"the
wrong-obj direction"*. **The three constants did not behave the same way, and
that is the result.**

| cell | tight arm | widening arm | verdict |
|---|---|---|---|
| **A05** `INLINE_DECLINE_BYTES` 128 | → 16 **GREEN** | → 4096 **RED, 2 tests** | **live, but the fence is ONE-SIDED** |
| **A04** `INLINE_DECLINE_LOOP_BYTES` 80 | → 8 **GREEN** | → 4096 **GREEN** | **LATENT at R1 in both directions** |
| **A06** `INLINE_UNBOUNDED_BYTES` 64 | → 8 **GREEN** | → 4096 **GREEN** | **LATENT at R1 in both directions** |

**So the answer is neither of the two worlds §5.1 posed — it is both, on
different constants, and only a two-sided probe could have told them apart.**

**A05 is fenced, and by exactly one test doing exactly one job.** The reds are
`comdat::inlfence_tests::the_size_is_the_only_field_that_moves_the_verdict` and
`comdat::inlfence_tests::n2_a_large_same_tu_callee_is_untouched` — a cell
**above** 128. There is no cell **between 16 and 128**, so the constant's whole
lower half is unfenced: any value in `[16, 128]` passes every test this project
runs. **The doc's `(95,152]` band is therefore under-verified rather than wrong,
and this lane does not report it as a refutation** — the widening arm says the
constant is live, which is the world the doc describes.

**AND THE ASYMMETRY IS THE RIGHT WAY ROUND, WHICH A BARE "ONE-SIDED" WOULD
MISREPRESENT.** The **fenced** side (→ 4096) is the **acceptance-widening,
wrong-obj** direction — the port inlines a body c2 kept, which is a **wrong
emit**. The **unfenced** side (→ 16) is *tightening*: more declines, a more
conservative port, and the worst it can produce is a **refusal**. Under
`docs/PROGRESS_METRIC.md` a wrong emit scores **strictly below the refusal it
replaces**, so the tests fence the expensive direction and miss the cheap one.
**That is the correct ordering to have, and the row says so.**

What the unfenced `[16, 128]` band actually is, then, is **a corpus-coverage
fact and not a code defect**: nothing in 391 fixtures discriminates the constant
anywhere below 128, so a future change inside that band ships unobserved. The
number that belongs beside this verdict is the **discriminating-cell count** —
how many fixtures reach the decision at all with a body in the band — and it is
`#3515`'s size-band probe, §7 item 2.

**A04 and A06 are the lane's live latency candidates.** `INLINE_DECLINE_LOOP_BYTES`
can be **8 or 4096** — a 512× range spanning the entire measured GRID-J bracket
`(56,80]` and the whole of GRID-W's `(80,96]` boundary — with **627 / 0** at R1
each time. `INLINE_UNBOUNDED_BYTES`, which licenses the port to *perform* an
expansion and whose doc says raising it *"would make the port inline bodies c2
keeps, which is the wrong-obj direction"*, is the same: **8 or 4096, both green.**
Their R2 and R3 verdicts are pending (§7); A06's first R2 was voided by §6.

   is exactly `calls.rs:1303`'s relationship to the write set.
2. **The quantity it bounds is identically zero on what is admitted, and the
   source says so in those words.** `leaf_store.rs:1445`:

   > *"**ONE base symbol.** With a single symbol every producer's `nsw` — the
   > symbol-group transitions before its value is first consumed — is
   > **identically 0**, so `MAX_SYMBOL_CROSSINGS` holds **by construction rather
   > than by check**."*

If that held generally then **no `usize` value of this constant could move an
observable** — `nsw > k` is false for every `k ≥ 0` when `nsw ≡ 0` — which is the
strongest form of latency a threshold can have.

**`MAX_SYMBOL_CROSSINGS` is NOT latent. Both edges fire, and the test that
catches the lower edge is the one literally named
`the_layout_guard_is_inert_on_what_the_parser_admits`** — the project already
built the control, and it works: at `k = 0` the guard stops being inert and the
test says so. `nsw` is **not** identically 0 on what is admitted; the
`leaf_store.rs:1445` comment is true of its own *one-base-symbol clause* and I
read it as a claim about the whole admitted population, which it is not.

**What survives is a smaller and more useful statement: the value is
under-determined between 1 and 2.** `k = 0` fires, `k = 99` fires, `k = 1` does
not — so `nsw` takes 0 and 1 and something ≥ 3 on the tested population, and
**never exactly 2**. The doc calls 2 *"the constant that separates the layout's
exact half from its 98.6 % half"* over `w-frame2`'s **62,365** cells; the tests
pin the *shape* of the guard and not that number, and **1 would pass all of
them.** That is a precision gap, not a latency, and it is a different and lesser
row.

**This is the single most important methodological result in the lane.** §5.2 as
first written — from a source comment, before the control ran — asserted the
strongest latency claim available. The control pair that the prereg required
**because a green is a claim about the control first** is what killed it. Had the
lane shipped only the `k = 1` green and the quotation, it would have published a
false latency finding with a citation attached.

**The interesting part is that this is HALF-declared, which is a category this
project does not yet have.** The declaration *"by construction rather than by
check"* lives in `crates/c2-il`, in a comment, on the parser side. The
constant's own doc, in `crates/c2-core`, reads the opposite way — *"the domain of
the **LAYOUT**, and it is an axis nothing else in this module uses … `w-frame2`
measured 62,365 cells and this is the constant that separates the layout's exact
half from its 98.6 % half"* — which is how a load-bearing decision point reads,
and it is what a permuter would be pointed at. **Honest in one crate, misleading
in the other, and the misleading half is the one on the emit path.**

### 5.4.1 B06 IS A MISS, AND THE PROJECT IS THE REASON

states** — so its decision point is not merely settable, it is **pinned across
its whole domain**. A permuter moving `pooled_data_phase_string` still cannot
move a byte today, but it is moving a number the project can defend.

**The honest verdict for B06 is `test-only`, not `latent`** — observable, but by
a test rather than by a byte — and the distinction matters for the permuter,
which is the consumer this parameter exists for.

### 8.2 Axis D — `pub` exempts an item from the compiler's own dead-code check, and the surface is 1,539 items

**Verified on this workspace rather than asserted.** `rustc 1.97.0`, a
`--crate-type=lib` control file with four items identical but for visibility and
none referenced:

```
warning: constant `PRIV_ORPHAN` is never used
warning: function `priv_orphan_fn` is never used
```

`PUB_ORPHAN` and `pub_orphan_fn` draw **nothing**. rustc's liveness analysis
stops at the crate boundary, so a `pub` item in a library crate is reachable *by
assumption*. Every crate here is a library target.

**The denominator — the size of the surface no automatic control covers:**

| crate | `pub const` | `pub fn` | `pub` types |
|---|---|---|---|
| `c2-core` | 151 | 411 | 96 |
| `c2-il` | 47 | 156 | 102 |
| `c2-obj` | 30 | 34 | 13 |
| `c2-reference` | 4 | 56 | 12 |
| `c2-harness` | 25 | 297 | 105 |
| **total** | **257** | **954** | **328** |

**1,539 declarations**, none of which rustc will ever warn about.

**This is what makes `#3428` and `#3469` read the wrong way.** Both were caught
by build warnings — and both were **non-`pub`**. They are not evidence that the
build catches this class; they are evidence that the build catches the **6 %** of
it that is private. The `pub` remainder is checked by nothing but a reference
count somebody chooses to run, and this lane is the first to run one.

**The cheapest available control, named and not built** (analysis-first fence):
the axis-C sweep is ~40 lines of Python over `crates/`, runs in under two
seconds, needs no build, and could be a `cargo test` in the workspace with a
frozen allowlist of the five known orphans — so the **next** one fails a test
instead of waiting for a lane to go looking. It is not built here because that
is a new instrument in `crates/c2-harness`, which `w-joint` owns this wave.

### 8.2a Axis E — "a `Vec` whose only read is its length" — ATTEMPTED, FOUND NOTHING, and the heuristic is the reason

The brief names *"`Vec`/set contents where only the length or emptiness is
read"* as a candidate class. A syntactic scan over `crates/c2-core` for local
`Vec`/`BTreeSet`/`HashSet` bindings whose only reads are `.len()`/`.is_empty()`
raised **4 candidates**. **All four are false positives**, each refuted by
reading:

| candidate | why it is not length-only |
|---|---|
| `coff/writer.rs:1115` `pdata_relocs` | iterated and written at `:1210` |
| `lib.rs:1619` `pairs` | returned at `:1688` |
| `codegen/json_utf8_copy.rs:735` `sites` | re-read at `:759` |
| `coff/dyninit.rs:132` `expected` | iterated at `:140` |

The scan's window truncates at the first column-0 `}`, so a use past that point
is invisible — **the same class of error as §1, one size down**, and it is
reported rather than quietly dropped because a scan that raises four and refutes
four has told you something: **no length-only collection was found in
`c2-core`.** That is a weak negative — the heuristic cannot see fields, only
locals, and cannot see a value passed by reference into a function that ignores
it, which is exactly `#3493`'s shape.

**Priced, not built**: the competent instrument is per-binding liveness, not
regex — either `rustc`'s own MIR (`-Z` flags, nightly, outside this toolchain) or
a mutation per binding, which for `c2-core`'s locals is a four-figure cell count
at 4.6 s each. **That is the honest price of extending axis E, and it is why this
lane's declared denominator is constants and parameters rather than values.**
